アジャイル、スクラム、スプリント、プロダクトオーナー……。開発手法の分野を勉強していると、似たようなカタカナの用語が次々に出てきて、どれが何を指しているのか混ざってしまわないでしょうか。

これらの用語は、<strong>大きな考え方 → その考え方を実行する枠組み → 枠組みの中の役割と行事</strong>という階層で整理すると、ぐっと覚えやすくなります。

この記事では、ITパスポートや基本情報技術者試験で問われるアジャイルとスクラムの用語を、ウォーターフォールとの違いから順に整理します。あわせて、開発と運用をつなぐDevOps、意思決定の枠組みであるOODAループとPDCAも、同じページで比べます。

## 用語の階層を先に押さえる

最初に、この記事で扱う用語の関係を表にまとめます。

| 階層 | 用語 | ひとことで言うと |
| --- | --- | --- |
| 考え方 | アジャイル開発 | 小さく作って、見せて、直すをくり返す開発の進め方 |
| 枠組み | スクラム | アジャイル開発を実行するための、代表的なルールの枠組み |
| 期間 | スプリント（イテレーション） | 1〜4週間ほどの、くり返しの単位 |
| 役割 | プロダクトオーナー、スクラムマスター、開発者 | スクラムのチームを構成する3つの役割 |
| 成果物 | プロダクトバックログ | 作りたい機能を、価値の高い順に並べた一覧 |

アジャイル開発は考え方の名前で、スクラムはそれを実行する方法のひとつです。<strong>「スクラムはアジャイル開発の一種」</strong>という関係を押さえておくと、選択肢を読み違えにくくなります。

## ウォーターフォール開発とアジャイル開発の違い

### ウォーターフォール開発

<strong>ウォーターフォール開発</strong>は、要件定義、設計、プログラミング、テストといった工程を、滝が上から下へ流れるように順番に進める開発手法です。前の工程が終わってから次の工程に進むのが原則です。

最初に全体の計画を細かく決めるので、進み具合やコストの見通しを立てやすいのが長所です。一方で、途中で要件が変わると、前の工程まで戻ってやり直す手間（手戻り）が大きくなります。

主な工程と、各工程で決めることは次のとおりです。

| 工程 | 決めること・やること |
| --- | --- |
| 要件定義 | 「何を作るか」をユーザーと合意する。機能だけでなく、性能やセキュリティなどの非機能要件も決める |
| 設計（外部設計・内部設計） | 「どう作るか」を決める。外部設計は操作画面や帳票などユーザーから見える部分、内部設計はプログラムの分割やデータ構造などの開発者側の詳細 |
| プログラミング | 設計書に基づいてソースコードを書く |
| テスト | 単体テスト、結合テスト、システムテスト、運用テスト（受入テスト）の順に確認する |
| 運用・保守 | 完成したシステムを使いながら、不具合の修正や機能の追加を行う |

工程が明確に分かれているので、進捗を管理しやすく、各工程の終わりに確認を入れて品質を保ちやすい点も長所です。試験では、<strong>手戻りのコスト</strong>（後の工程でミスが見つかるほど、修正の手間が大きくなる）と、設計書などのドキュメントを重視する点が問われます。銀行や公共インフラのように、高い信頼性が求められ、変更が許されにくい大規模なシステムで、今もウォーターフォール（またはその派生）が使われています。

テスト工程と設計工程の対応は、[ホワイトボックス・ブラックボックステストとV字モデル](/theory/white-black-box-testing/) で扱っています。

### アジャイル開発

<strong>アジャイル開発</strong>は、システムを小さな機能に分け、短い期間で「作る・見せる・直す」をくり返しながら進める開発手法です。アジャイル（agile）は「素早い」「機敏な」という意味です。

短い期間ごとに動くものを確かめるので、途中で要望が変わっても、次のくり返しで取り入れられます。ただし、目的や優先順位があいまいなまま進めると、くり返すたびに方向がぶれて、成果がまとまらなくなります。

### どちらが向いているか

試験では、「どんなプロジェクトにどちらが向いているか」がよく問われます。

| 比べる点 | ウォーターフォール開発 | アジャイル開発 |
| --- | --- | --- |
| 進め方 | 工程を順番に、1回で進める | 短い期間をくり返す |
| 要件 | 最初に決まっている | 途中で変わることを前提にする |
| 向いているプロジェクト | 要件がはっきりしていて、変更が少ない大規模な開発 | 新しいサービスなど、作りながら要望を確かめたい開発 |
| 弱点 | 途中の変更で手戻りが大きい | 全体の納期やコストの見通しを立てにくい |

## スクラムの3つの役割

スクラムのチームは、次の3つの役割で構成されます。試験では「誰が何に責任を持つか」が問われます。

| 役割 | 責任 | 覚え方 |
| --- | --- | --- |
| プロダクトオーナー | 何を作るかを決め、プロダクトバックログの優先順位を決める | 「何を」の責任者 |
| スクラムマスター | チームがスクラムをうまく進められるよう支援し、作業の妨げを取り除く | チームを支える役 |
| 開発者 | スプリントの中で、実際に動くものを作る | 「どう作るか」を自分たちで決める |

<strong>プロダクトオーナー</strong>は、顧客や利用者の声を代表して、製品の価値を最大にする役割です。作りたい機能の一覧であるプロダクトバックログを管理し、どれを先に作るかを決めます。

<strong>スクラムマスター</strong>は、メンバーに直接指示を出す管理者ではありません。チームが自分たちで問題を解決できるよう支え、作業の妨げになっていることを取り除く役割です。「仕えるリーダー」という意味の<strong>サーバントリーダー</strong>と呼ばれることもあります。

<strong>開発者</strong>は、設計・プログラミング・テストなど、動くものを作るのに必要なスキルをチームの中でそろえ、自分たちで作業の進め方を決めます。古い資料では「開発チーム」と書かれていることもあります。

### プロジェクトマネージャとの違いに注意

試験でまぎらわしいのが、スクラムマスターと、従来の開発でのプロジェクトマネージャの違いです。プロジェクトマネージャは計画を立ててメンバーに作業を割り振りますが、スクラムマスターは指示を出さず、チームが自分たちで決めて動けるように支援します。

## スプリントと4つのイベント

スクラムでは、<strong>スプリント</strong>と呼ばれる1〜4週間ほどの期間をくり返して開発を進めます。スプリントの中では、次のイベント（決まった場）が行われます。

| イベント | タイミング | 内容 |
| --- | --- | --- |
| スプリントプランニング | スプリントの最初 | このスプリントで何を作るか、どう進めるかを計画する |
| デイリースクラム | 毎日、15分ほど | 進み具合と、困っていることを共有する |
| スプリントレビュー | スプリントの終わり | できあがったものを関係者に見せ、意見をもらう |
| スプリントレトロスペクティブ | スプリントの終わり | チームの進め方をふり返り、次のスプリントの改善点を決める |

レビューとレトロスペクティブは、どちらもスプリントの終わりに行うので混ざりやすい組み合わせです。<strong>レビューは「作ったもの」を見直す場、レトロスペクティブは「進め方」を見直す場</strong>と覚えておきましょう。

## DevOps｜開発と運用をつなぐ文化と仕組み

<strong>DevOps</strong>は、Development（開発）とOperations（運用）が密に連携し、ビジネスの価値を速く、高い品質で届ける手法です。従来は、新機能を速く入れたい開発側と、システムを安定させたい運用側が対立しがちでした。DevOpsは、この対立をなくし、共通の目標に向かう体制を作ります。目的は、リリースの頻度（スピード）を上げながら、障害を減らす（安定性）ことの両立です。

| 用語 | 内容 |
| --- | --- |
| 継続的インテグレーション（CI） | コードの変更を頻繁に共有リポジトリへ統合し、そのたびに自動でビルドやテストを行う。問題を早く見つけ、終盤の大きな手戻りを防ぐ |
| 継続的デリバリー（CD） | CIで品質を確かめたソフトウェアを、いつでも本番にリリースできる状態に保つ。手動のデプロイを自動化する |
| 継続的デプロイメント | 手動の承認なしで、本番環境まで自動でデプロイする。CDをさらに進めたもの |

アジャイル開発とは相性がよく、アジャイルが「何を、どう開発するか」を扱うのに対し、DevOpsは「開発したものを、いかに早く安定して届けるか」を担います。試験では、「DevOpsはツールの導入ではなく、開発と運用が目標を共有する<strong>組織の文化</strong>である」という記述が、正解の選択肢になりやすい点に注意してください。

## OODAループとPDCA｜意思決定の回し方

開発の進め方とあわせて、変化への対応を問う形で、<strong>OODAループ</strong>とPDCAの違いも出題されます。

| 枠組み | 始まり | 向いている場面 |
| --- | --- | --- |
| PDCA | 計画（Plan）から | 目標が明確で、環境が安定している場面。品質管理や既存業務の改善 |
| OODA | 観察（Observe）から | 想定外の出来事が起きる場面。新規事業、サイバー攻撃への対応など、素早い状況判断が要る場面 |

OODAは、次の4ステップを素早く回します。

| ステップ | 内容 |
| --- | --- |
| Observe（観察） | 先入観を持たず、現場の状況やデータをありのままに集める |
| Orient（方向づけ） | 自分の経験や知識を使って、状況が何を意味するかを解釈する。同じ情報でも解釈が人によって違うため、最も重要とされる |
| Decide（決定） | 選択肢を絞り、何を、いつ、どうするかを決める |
| Act（実行） | 実行し、その結果をすぐに観察に戻して、次のループを始める |

対比は「まず計画を立てるのがPDCA、まず相手と状況を見て動くのがOODA」です。試験では、それぞれが効果を発揮する適用場面の違いが問われます。

## 試験に出るそのほかの用語

| 用語 | 意味 |
| --- | --- |
| イテレーション | 短い開発期間のくり返しの単位。スクラムではスプリントと呼ぶ |
| プロダクトバックログ | 作りたい機能や要望を、価値の高い順に並べた一覧 |
| XP（エクストリームプログラミング） | アジャイル開発の手法のひとつ。ペアプログラミングやテスト駆動開発など、技術的な実践を重視する |
| ペアプログラミング | 2人1組で、1台のコンピュータを使ってプログラムを作る |
| テスト駆動開発 | プログラムより先にテストを書き、テストに通るようにプログラムを作る |

## AIに役を演じてもらって覚える

役割やイベントの名前は、表で覚えるだけだと試験の場面で思い出しにくいことがあります。生成AIにスクラムの役を演じてもらい、やり取りしながら覚えると、場面と用語が結びつきます。

```text
あなたはスクラムマスターです。私は初めてスプリントに参加する開発者です。
次の場面で、それぞれ何をするのかを、短い会話の例で示してください。

- スプリントプランニング
- デイリースクラム
- スプリントレビュー
- スプリントレトロスペクティブ

最後に、**レビューとレトロスペクティブの違い**を1文でまとめてください。
```

```text
あるパン屋で、新商品を焼く人（開発）と店先で売る人（運用）がバラバラに動いていました。
この店を「DevOps化」すると、売れ残り（不具合）が減り、新商品がすぐ店頭に並ぶ仕組みを、
100文字以内で説明してください。
```

```text
SNSでトレンドを見て（観察）、自分の得意ジャンルと照らし合わせ（方向づけ）、
投稿のネタを1つに絞り（決定）、30分以内に投稿する（実行）。
この流れをOODAと呼ぶとき、PDCAと比べて優れている点を1行で答えてください。
```

会話の例を読んだら、「この場面で話しているのは誰か」「何を決めているのか」を自分で言えるか確かめてみてください。

## まとめ

アジャイルとスクラムの用語は、階層で整理すると混ざりにくくなります。

- アジャイル開発は「小さく作って、見せて、直す」をくり返す考え方。スクラムはそれを実行する代表的な枠組み
- ウォーターフォールは要件が決まっている開発、アジャイルは作りながら要望を確かめたい開発に向いている
- 役割は、何を作るかを決めるプロダクトオーナー、チームを支えるスクラムマスター、作る開発者の3つ
- レビューは作ったものを、レトロスペクティブは進め方を見直す場
- DevOpsは開発と運用の連携の文化で、CI/CDで自動化する。OODAは観察から始まり、変化の激しい場面に向く（PDCAは計画から始まる）

これで、開発手法の問題で出てくる用語を、どの階層の話なのかから判断できるはずです。まずは上の表の「ひとことで言うと」を隠して、5つの用語を自分の言葉で説明できるか試してみてください。
