## システムライフサイクルの基本概念と標準規格

システム及びソフトウェアの一連の工程を体系化した枠組みが<strong>システムライフサイクルプロセス</strong>とその中核をなす<strong>ソフトウェアライフサイクルプロセス（SLCP）</strong>で、国際規格<strong>JIS X 0170</strong>（システムライフサイクルプロセス）と<strong>JIS X 0160</strong>（ソフトウェアライフサイクルプロセス）で定められています。発注者と受注者が合意形成を行う<strong>合意プロセス</strong>、組織としてプロジェクトを支援する<strong>組織のプロジェクトイネーブリングプロセス</strong>、技術面をマネジメントする<strong>テクニカルマネジメントプロセス</strong>、実際の技術活動を行う<strong>テクニカルプロセス</strong>という大分類があり、対象システムと接続する<strong>インターフェーシングシステム</strong>、開発を支援する<strong>イネーブリングシステム</strong>、他システムと連携する<strong>相互運用システム</strong>を区別します。

規格をそのまま適用するのではなく、プロジェクトの規模や特性に応じて調整する<strong>プロセス修整（Tailoring）</strong>を行い、規格にそのまま従う<strong>完全適合</strong>か、一部を調整する<strong>修整適合</strong>かを選択します。これらを体系的に扱う専門分野が<strong>システムズエンジニアリング</strong>で、組織はプロジェクトごとにばらつきが出ないよう<strong>組織の標準プロセス</strong>を整備し、継続的な<strong>プロセス改善</strong>を行います。プロセスの成熟度を評価する規格として<strong>JIS X 33001</strong>・<strong>JIS X 33020</strong>があります。

**扱う用語（精選・19語）**

- システムライフサイクルプロセス／ソフトウェアライフサイクルプロセス（SLCP）／JIS X 0170／JIS X 0160
- 合意プロセス／組織のプロジェクトイネーブリングプロセス／テクニカルマネジメントプロセス／テクニカルプロセス
- インターフェーシングシステム／イネーブリングシステム／相互運用システム
- プロセス修整（Tailoring）／完全適合／修整適合
- システムズエンジニアリング／組織の標準プロセス／プロセス改善／JIS X 33001／JIS X 33020

## 要件定義

要件定義の出発点は、システムがどこまでを担うかという<strong>機能的な境界の定義</strong>です。<strong>利用の状況</strong>と<strong>運用シナリオ</strong>を洗い出し、外部システムとの接点となる<strong>API</strong>・<strong>GUI</strong>・<strong>インタフェースファイル</strong>を明確にして<strong>システムとサービスとの境界</strong>を定めます。<strong>システム化の目標</strong>と<strong>対象範囲</strong>（対象業務・対象部署）を確定したら、応答時間などの<strong>システムの性能要件</strong>と<strong>入出力情報要件</strong>を含む<strong>性能要件</strong>、<strong>データベース要件</strong>・<strong>テスト要件</strong>・<strong>セキュリティ要件</strong>・<strong>移行要件</strong>・<strong>運用要件</strong>・<strong>保守要件</strong>という多面的な要件を定義します。

データの生成・参照・更新・削除の対応関係を整理する<strong>CRUDマトリクス</strong>や、要件から成果物までの対応関係を保つ<strong>双方向のトレーサビリティ</strong>を使い、要件が実現可能かという<strong>システム設計の実現可能性</strong>と<strong>運用及び保守の実現可能性</strong>を検証します。安全性・信頼性の根拠を示す<strong>アシュアランスケース</strong>や、要件と成果物の対応を一覧化する<strong>トレーサビリティマトリクス</strong>も要件定義工程の重要な成果物です。

**扱う用語（精選・24語）**

- 機能的な境界の定義／利用の状況／運用シナリオ／API／GUI／インタフェースファイル／システムとサービスとの境界
- システム化の目標／対象範囲（対象業務・対象部署）
- システムの性能要件／入出力情報要件／性能要件／データベース要件／テスト要件／セキュリティ要件／移行要件／運用要件／保守要件
- CRUDマトリクス／双方向のトレーサビリティ
- システム設計の実現可能性／運用及び保守の実現可能性／アシュアランスケース／トレーサビリティマトリクス

## アーキテクチャ設計とシステム方式設計

要件が固まったら、システムを機能単位に分割する<strong>サブシステム分割</strong>を行い、それぞれの<strong>サブシステム機能仕様定義</strong>と、サブシステム間の関係を図示する<strong>サブシステム関連図</strong>を作成します。提供する機能を明確にする<strong>サービスの定義</strong>、<strong>セキュリティ要件の識別</strong>、将来の変更のしやすさを考える<strong>保守性の考慮</strong>、実現可能かを検証する<strong>ソフトウェアシステムの実現可能性</strong>を進めます。

システムを実現する手段には、ハードウェア・ソフトウェア・サービス・人手による作業（手作業）の組み合わせがあり、どこに何を割り当てるかを決める<strong>ハードウェア・ソフトウェア・サービス・手作業の機能分割</strong>を行います。ここまでで整理した<strong>機能要件</strong>と<strong>非機能要件</strong>をもとに、クラウドサービスの利用などを含めた<strong>ハードウェア構成の決定</strong>、ソフトウェアパッケージの利用などを含めた<strong>ソフトウェア構成の決定</strong>、マイクロサービスアーキテクチャ・サービスメッシュ・サーバレスアーキテクチャといった<strong>システム処理方式の決定</strong>を行います。この段階で<strong>システム統合テストの設計</strong>にも着手し、設計全体の<strong>一貫性</strong>と<strong>設計標準や方法の適切性</strong>を確認します。

**扱う用語（精選・16語）**

- サブシステム分割／サブシステム機能仕様定義／サブシステム関連図
- サービスの定義／セキュリティ要件の識別／保守性の考慮／ソフトウェアシステムの実現可能性
- ハードウェア・ソフトウェア・サービス・手作業の機能分割／機能要件／非機能要件
- ハードウェア構成の決定（クラウドサービスの利用 など）／ソフトウェア構成の決定（ソフトウェアパッケージの利用 など）／システム処理方式の決定（マイクロサービスアーキテクチャ・サービスメッシュ・サーバレスアーキテクチャ）
- システム統合テストの設計／一貫性／設計標準や方法の適切性

## ソフトウェア設計とモジュール分割

システム方式が決まったら、個々の<strong>ソフトウェア要素の実現可能性</strong>を検証しながら<strong>ソフトウェアユニット分割</strong>を進め、<strong>ソフトウェア設計書</strong>と<strong>インタフェース設計</strong>を作成します。この段階で<strong>ソフトウェアユニットのテストの設計</strong>と<strong>ソフトウェア統合テスト仕様</strong>も先に定めておき、<strong>ソフトウェア要素分割</strong>の基準となる<strong>プログラム分割基準</strong>、<strong>設計方法や作業標準の適切性</strong>、<strong>テストの実現可能性</strong>を確認します。

ソフトウェア品質の国際規格として、品質特性を定める<strong>JIS X 25010</strong>と利用時の品質を定める<strong>JIS X 25019</strong>があり、それぞれ<strong>品質特性モデル</strong>・<strong>利用時品質モデル</strong>として体系化されています。モジュールへの分割手法には論理設計・領域設計・再帰プログラムによる<strong>モジュール分割技法</strong>があり、モジュールの制御領域・影響領域・再分割という<strong>モジュール分割基準</strong>、決定表やプログラミングテーブルで仕様化する<strong>モジュール仕様の作成</strong>を行います。再利用可能な部品としては<strong>コンポーネントウェア</strong>・<strong>クラスライブラリ</strong>・市販ソフトウェアを活用する<strong>COTS</strong>があります。

**扱う用語（精選・20語）**

- ソフトウェア要素の実現可能性／ソフトウェアユニット分割／ソフトウェア設計書／インタフェース設計
- ソフトウェアユニットのテストの設計／ソフトウェア統合テスト仕様／ソフトウェア要素分割／プログラム分割基準
- 設計方法や作業標準の適切性／テストの実現可能性
- JIS X 25010／JIS X 25019／品質特性モデル／利用時品質モデル
- モジュール分割技法（論理設計・領域設計・再帰プログラム）／モジュール分割基準／モジュール仕様の作成
- コンポーネントウェア／クラスライブラリ／COTS（Commercial Off-The-Shelf）

### 仕組みを理解する: レビュー技法はなぜこんなに種類があるのか

次節で扱うコードレビュー・テスト仕様レビュー・利用者マニュアルレビューなど多数のレビューは、すべて「誰が」「何を」「どう確認するか」の掛け算で種類が分かれています。同僚同士がお互いの成果物を確認する<strong>ピアレビュー</strong>、設計の妥当性を確認する<strong>デザインレビュー</strong>、進行役（モデレーター）を立てて形式的に行う<strong>インスペクション</strong>、作成者が処理の流れを説明しながら参加者が指摘する<strong>ウォークスルー</strong>、複数の関係者が合同で行う<strong>共同レビュー</strong>という具合です。個別に暗記するより「対象（コード／テスト仕様／マニュアル）」×「形式（ピア／デザイン／インスペクション／ウォークスルー）」の2軸で位置づけると整理しやすくなります。

## コーディングとレビュー技法

設計が固まったら、あらかじめ定めた<strong>コーディング標準</strong>に沿って実装します。制御構造を単純化する<strong>構造化プログラミング</strong>、論理式でルールを記述する<strong>論理型プログラミング</strong>、複数処理を同時に進める<strong>並列処理プログラミング</strong>、横断的関心事を分離する<strong>アスペクト指向プログラミング</strong>というプログラミングパラダイムを使い分けます。

品質確保の手段としては、前節で紹介した<strong>コードレビュー</strong>・<strong>テスト仕様レビュー</strong>・<strong>利用者マニュアルレビュー</strong>・<strong>ピアレビュー</strong>・<strong>デザインレビュー</strong>・<strong>インスペクション</strong>（<strong>モデレーター</strong>が進行）・<strong>ウォークスルー</strong>・<strong>共同レビュー</strong>を行い、信頼性・操作性・運用の容易性・技術的整合性・開発の合理性という<strong>妥当性評価の項目</strong>で評価します。コードレビューはさらに、メトリクス計測・コードインスペクション・ウォークスルー・サイクロマティック複雑度・静的解析・動的テストといった具体的な観点を組み合わせて実施します。成果物が要件までさかのぼって確認できる<strong>追跡可能性</strong>と<strong>テスト網羅性</strong>、<strong>コーディング方法及び作業標準の適切性</strong>、<strong>ソフトウェア統合及びテストの実現可能性</strong>を継続的に確認します。

**扱う用語（精選・20語）**

- コーディング標準／構造化プログラミング／論理型プログラミング／並列処理プログラミング／アスペクト指向プログラミング
- コードレビュー／テスト仕様レビュー／利用者マニュアルレビュー／ピアレビュー／デザインレビュー／インスペクション／モデレーター／ウォークスルー／共同レビュー
- 妥当性評価の項目（信頼性・操作性・運用の容易性・技術的整合性・開発の合理性）
- コードレビュー（メトリクス計測・コードインスペクション・ウォークスルー・サイクロマティック複雑度・静的解析・動的テスト）
- 追跡可能性／テスト網羅性／コーディング方法及び作業標準の適切性／ソフトウェア統合及びテストの実現可能性

## テストの評価指標

テストを効率化・自動化する<strong>テスト自動化</strong>を土台に、テストがどれだけ網羅できているかを表す<strong>テストの網羅度</strong>、単位時間あたりのテスト実施量を表す<strong>テスト密度</strong>、コード量あたりの欠陥数を表す<strong>欠陥密度（バグ密度）</strong>で品質を定量的に把握します。網羅の基準には、条件式の真偽をそれぞれ確認する<strong>判定条件網羅</strong>、複数条件の組み合わせを確認する<strong>複数条件網羅</strong>、実行経路の組み合わせを確認する<strong>経路組合せ網羅</strong>があり、これらをまとめて<strong>網羅率（カバレージ）</strong>と呼びます。コードにわざと欠陥を仕込んでテストの有効性を検証する<strong>ミューテーションテスト</strong>、入力値の境界や領域に着目する<strong>ドメイン分析テスト</strong>という高度な技法もあります。

**扱う用語（精選・11語）**

- テスト自動化／テストの網羅度／テスト密度／欠陥密度（バグ密度）
- 判定条件網羅／複数条件網羅／経路組合せ網羅／網羅率／カバレージ
- ミューテーションテスト／ドメイン分析テスト

## 統合テストと検証テスト

ソフトウェア単位の統合では、<strong>ソフトウェア統合計画</strong>で<strong>統合する順序</strong>（トップダウンテスト・ボトムアップテストなど）を決め、変更が既存機能に影響していないか確認する<strong>再帰戦略（回帰戦略）</strong>のもとで<strong>ソフトウェア統合テスト</strong>を実施します。<strong>ソフトウェア検証テストの準備</strong>では、<strong>トップダウンテスト</strong>・<strong>ボトムアップテスト</strong>という統合方式や、テスト専用の実行環境である<strong>テストベッド</strong>を整え、<strong>ソフトウェア検証テストの評価</strong>を経て<strong>納入ソフトウェア製品の準備</strong>を進めます。

機能テスト・非機能要件テスト・性能テスト・負荷テスト・セキュリティテスト・回帰テスト（リグレッションテスト）などの<strong>テスト準備</strong>では、想定外の入力を大量に送る<strong>ファジング</strong>も活用し、結果を<strong>ソフトウェア検証テスト報告書</strong>にまとめ、<strong>テスト標準及び方法の適切性</strong>と<strong>ソフトウェア検証テストの実現可能性</strong>を確認します。

システム全体の統合では、<strong>システム統合計画</strong>に基づき<strong>システム統合</strong>・<strong>システム統合テスト</strong>を実施し、<strong>システム統合の評価</strong>と<strong>システム統合の共同レビュー</strong>を行います。<strong>システム検証テストの準備</strong>では、探索的テストを含む多様な<strong>テストの種類</strong>を組み合わせ、結果を<strong>システム検証テスト報告書</strong>にまとめて<strong>期待した結果への適合性</strong>を確認し、<strong>システム検証テストの実現可能性</strong>と<strong>レビュー</strong>を経て<strong>システム検証テストの評価</strong>を完了させます。

**扱う用語（精選・27語）**

- ソフトウェア統合計画／統合する順序／再帰戦略（回帰戦略）／ソフトウェア統合テスト
- ソフトウェア検証テストの準備／トップダウンテスト／ボトムアップテスト／テストベッド／ソフトウェア検証テストの評価
- 納入ソフトウェア製品の準備／テスト準備（機能・非機能要件・性能・負荷・セキュリティ・回帰テスト など）／ファジング
- ソフトウェア検証テスト報告書／テスト標準及び方法の適切性／ソフトウェア検証テストの実現可能性
- システム統合計画／システム統合／システム統合テスト／システム統合の評価／システム統合の共同レビュー
- システム検証テストの準備／テストの種類（機能・非機能要件・性能・負荷・セキュリティ・回帰・探索的テスト など）
- システム検証テスト報告書／期待した結果への適合性／システム検証テストの実現可能性／レビュー／システム検証テストの評価

## 移行と受け入れ

開発が完了したシステムを本番環境へ移す段階では、<strong>導入要件</strong>と、プロセス及びデータの移行方法・移行保守の取組方法及びスケジュールを定める<strong>移行要件</strong>を土台に、全体を一度に切り替える<strong>一斉移行</strong>と、段階的に切り替える<strong>段階移行</strong>を使い分けます。実務では、新環境に少量のトラフィックだけ流して安全性を確認する<strong>カナリアリリース</strong>、新旧環境を並行稼働させて切り替える<strong>ブルーグリーンデプロイメント</strong>という手法も広く使われます。教育訓練資料・教育訓練システム・e-Learning・Web Based Training・ロジスティクス支援パッケージを含む<strong>利用者支援</strong>も移行の重要な要素です。

利用者側の確認では、<strong>受入れ基準</strong>に沿って<strong>受入れテスト</strong>を行い、<strong>検収</strong>（<strong>検収基準</strong>・<strong>受入れ体制</strong>）を経て<strong>利害関係者の合意</strong>を得ます。<strong>教育訓練計画</strong>の効果測定には、反応・学習・行動・成果の4段階で評価する<strong>カークパトリックの教育効果の4段階モデル</strong>が使われます。整備すべき文書としては、<strong>運用規程</strong>、<strong>利用者用文書類</strong>、システムに組み込む<strong>組込文書類</strong>、独立して配布する<strong>分離形文書類</strong>があります。

最終確認では、要求事項として<strong>妥当性確認される要件</strong>を満たすか、施設・設備・機器を含む<strong>必要とするイネーブリングシステム</strong>が揃っているか、<strong>各妥当性確認テストを実施するための環境条件</strong>が整っているかを確認します。問題が見つかれば<strong>不具合の根本原因</strong>を特定して<strong>是正処置</strong>・<strong>欠陥修正</strong>・<strong>改善作業</strong>を行い、<strong>学んだ教訓の記録</strong>として蓄積します。実際の使いやすさを確認する<strong>使用性テスト</strong>や、限定的に使ってもらう<strong>ソフトウェアの試行利用</strong>も移行判断の材料になります。

**扱う用語（精選・29語）**

- 導入要件／移行要件（プロセス及びデータの移行・移行保守の取組方法及びスケジュール）／一斉移行／段階移行／カナリアリリース／ブルーグリーンデプロイメント
- 利用者支援（教育訓練資料・教育訓練システム・e-Learning・Web Based Training・ロジスティクス支援パッケージ）
- 受入れ基準／受入れテスト／検収／検収基準／受入れ体制／利害関係者の合意
- 教育訓練計画／カークパトリックの教育効果の4段階モデル
- 運用規程／利用者用文書類／組込文書類／分離形文書類
- 妥当性確認される要件（要求事項）／必要とするイネーブリングシステム（施設・設備・機器）／各妥当性確認テストを実施するための環境条件
- 不具合の根本原因／是正処置／欠陥修正／改善作業／学んだ教訓の記録
- 使用性テスト／ソフトウェアの試行利用

## 運用と保守

本番稼働後は、<strong>運用負荷低減のための改善計画</strong>のもと、要員などの人的資源とハードウェア・ソフトウェア・データ・ネットワークなどインフラの技術的資源を扱う<strong>運用の資源管理</strong>、<strong>仮想環境の運用管理</strong>、<strong>ジョブの管理</strong>、<strong>データ管理</strong>、<strong>利用者の管理</strong>を継続的に行います。AIを活用して運用業務を自動化・効率化する<strong>AIOps</strong>や、システムと業務双方の安全を扱う<strong>運用安全及び業務安全に関する安全戦略</strong>も現代的な運用の重要テーマです。

保守面では、<strong>保守手順</strong>・<strong>保守体制</strong>・<strong>保守の実現可能性</strong>・<strong>保守テスト</strong>を整備し、既存システムの仕様を解析する<strong>リバースエンジニアリング</strong>、外部委託時の<strong>保守契約</strong>、<strong>保守要件の定義</strong>、<strong>ハードウェア保守</strong>と<strong>日常点検</strong>を行います。保守の種類には、障害を修正する<strong>是正保守</strong>、機能を改良する<strong>改良保守</strong>、障害を未然に防ぐ<strong>予防保守</strong>、環境変化に対応する<strong>適応保守</strong>、潜在的な問題を根本的に解消する<strong>完全化保守</strong>があり、実施場所によって現地で行う<strong>オンサイト保守</strong>と遠隔で行う<strong>遠隔保守</strong>に分かれ、これら全体を<strong>保守プロセス</strong>として管理します。信頼性を分析する技法としては、故障の木構造で原因を追う<strong>FTA</strong>、故障モードと影響を分析する<strong>FMEA</strong>、社会技術システム全体の安全性を分析する<strong>STAMP/STPA</strong>などの<strong>システム信頼性のための解析技法</strong>があります。

**扱う用語（精選・26語）**

- 運用負荷低減のための改善計画／運用の資源管理（人的資源・技術的資源）／仮想環境の運用管理／ジョブの管理／データ管理／利用者の管理
- AIOps／運用安全及び業務安全に関する安全戦略
- 保守手順／保守体制／保守の実現可能性／保守テスト／リバースエンジニアリング／保守契約／保守要件の定義／ハードウェア保守／日常点検
- 是正保守／改良保守／予防保守／適応保守／完全化保守／オンサイト保守／遠隔保守／保守プロセス
- システム信頼性のための解析技法（FTA・FMEA・STAMP/STPA など）

## 廃棄

システムの役目が終わったら、<strong>廃棄計画の立案</strong>を行い、<strong>廃棄計画などの利用者への通知</strong>を経て、新旧環境を並行運用しながら利用者を教育訓練する<strong>新旧環境の並行運用と利用者の教育訓練</strong>を実施します。<strong>関係者全員への廃棄の通知</strong>を徹底し、法令や社内規程に従って<strong>廃棄関連データの保持とアクセス可能性の確保</strong>を行います。開発から廃棄までの全工程を通じて、最初の工程だけでなく最後の工程まで計画的に管理することが、システムライフサイクルプロセスの本質です。

**扱う用語（精選・5語）**

- 廃棄計画の立案／廃棄計画などの利用者への通知／新旧環境の並行運用と利用者の教育訓練／関係者全員への廃棄の通知／廃棄関連データの保持とアクセス可能性の確保

## AIで学ぶ

ここまでの用語は、ChatGPTやClaudeなどの生成AIに以下のプロンプトを投げかけると、比較表つきでさらに深く掘り下げて学習できます。コピーして使ってみましょう。

```
あなたはプロフェッショナルデジタルスキル（システム）試験の講師です。「システムライフサイクルプロセス」の範囲について、以下の用語を初学者向けに**関連づけながら**説明してください（単体の丸暗記より、用語同士のつながりを理解したほうが記憶に定着しやすく、試験本番で紛らわしい選択肢を見分ける力もつくためです）。用語同士の違いが分かる**比較表**を最後に付けてください。

【基本概念と標準規格】システムライフサイクルプロセス、ソフトウェアライフサイクルプロセス（SLCP）、JIS X 0170、プロセス修整（Tailoring）、システムズエンジニアリング
【要件定義】機能的な境界の定義、システムの性能要件、セキュリティ要件、移行要件、CRUDマトリクス、双方向のトレーサビリティ
【アーキテクチャ設計】サブシステム分割、機能要件、非機能要件、システム処理方式の決定（マイクロサービス・サーバレス）
【ソフトウェア設計とコーディング】モジュール分割技法、コーディング標準、構造化プログラミング、コードレビュー、ピアレビュー、デザインレビュー、インスペクション、ウォークスルー
【テストの評価指標】テストの網羅度、判定条件網羅、複数条件網羅、経路組合せ網羅、カバレージ、ミューテーションテスト
【統合テストと検証テスト】ソフトウェア統合テスト、トップダウンテスト、ボトムアップテスト、システム統合テスト、テストの種類（機能・非機能・性能・負荷・セキュリティ・回帰）
【移行と受け入れ】一斉移行、段階移行、カナリアリリース、ブルーグリーンデプロイメント、受入れテスト、検収
【運用と保守】AIOps、是正保守、改良保守、予防保守、適応保守、完全化保守、FTA、FMEA
```

AIに用語リストだけを渡すと、辞書をそのまま読み上げるような無機質な説明が返ってくることがあります。このプロンプトが<strong>役割</strong>（試験の講師）・<strong>関連づけの指示</strong>・<strong>出力形式（比較表）</strong>の3つを指定しているのはそれを避けるためです。特にこの章は用語数が多いため、まずは自分が弱いフェーズ（例: テスト工程）だけを抜き出してAIに投げると、消化しやすくなります。
