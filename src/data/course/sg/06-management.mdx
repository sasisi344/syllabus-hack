## この章で学ぶこと

情報セキュリティ担当者は、対策を「導入して終わり」にはできません。プロジェクトとして計画的に進め（<strong>プロジェクトマネジメント</strong>）、日々のサービスとして安定運用し（<strong>サービスマネジメント</strong>）、その運用が正しく回っているかを第三者の目でチェックする（<strong>システム監査</strong>）——この3つが揃って初めて、対策が形骸化せずに機能し続けます。

## プロジェクトマネジメント

新しいセキュリティ対策の導入や規程の改定は、多くの場合1つの<strong>プロジェクト</strong>として進みます。まず、プロジェクトが誰のために・何を目指すのかという方向性を示す<strong>プロジェクトガバナンス</strong>、立ち上げから終結までの一連の流れである<strong>プロジェクトライフサイクル</strong>を押さえます。関係者を把握する<strong>ステークホルダの特定</strong>とその調整、やるべき作業の範囲を決める<strong>スコープの定義</strong>、それを階層的に分解して洗い出す<strong>WBS（作業分解構造）</strong>という順序で計画を具体化していきます。

スケジュールは、作業の順序や依存関係を踏まえて所要時間を見積もる<strong>PERT</strong>で組み立て、コストは予算の基準線となる<strong>コストベースライン</strong>で管理します。プロジェクト全体に共通するリスクと個別作業のリスク（<strong>プロジェクトの全体リスクと個別リスク</strong>）を洗い出し、<strong>リスクへの対応</strong>を検討する点は、第2章で学んだリスクマネジメントの考え方がそのまま応用できます。外部のベンダーを使う場合は<strong>調達の計画</strong>と<strong>供給者の選定</strong>、関係者への報告・共有を行う<strong>コミュニケーションのマネジメント</strong>も欠かせません。

**扱う用語（精選・16語）**

- プロジェクト／プロジェクトガバナンス／プロジェクトライフサイクル
- ステークホルダの特定／ステークホルダのマネジメント
- スコープの定義／WBS（作業分解構造）
- PERT／コストベースライン
- プロジェクトの全体リスクと個別リスク／リスクへの対応
- 調達の計画／供給者の選定
- コミュニケーションのマネジメント／得た教訓の収集／プロジェクト憲章の作成

> 深掘り: [WBS・見積り・ガントチャート・クリティカルパスまで一気に整理](/theory/project-service-management-overview/)

## サービスマネジメント

対策を導入した後は、日々のサービスとして安定的に運用し続ける必要があります。サービス提供者と利用者の間で品質水準を合意する<strong>SLA（サービスレベル合意書）</strong>と、その中で定める具体的な数値目標である<strong>サービスレベル目標</strong>はセットで理解します。提供するサービスの一覧である<strong>サービスカタログ</strong>、構成品目（CI）を管理する<strong>構成管理</strong>、需要の変動に備える<strong>需要管理</strong>と<strong>容量・能力管理</strong>も運用の基本です。

システムに変更を加える際は、影響を事前に評価する<strong>変更管理</strong>を経てから<strong>リリース及び展開管理</strong>に進みます。障害対応の中心となるのが<strong>インシデント管理</strong>と<strong>問題管理</strong>で、この2つの違いは次のコラムで詳しく扱います。サービスが止まらないようにする備えとしては、目標復旧時間である<strong>RTO</strong>と目標復旧時点である<strong>RPO</strong>、常時稼働の予備系である<strong>ホットスタンバイ</strong>と障害時に起動する<strong>コールドスタンバイ</strong>を対比で押さえます。評価と改善は<strong>パフォーマンス評価</strong>と<strong>継続的改善</strong>という、第2章のISMSと同じPDCA発想で回します。利用者からの問い合わせ窓口である<strong>サービスデスク</strong>、電源や空調などの設備を管理する<strong>ファシリティマネジメント</strong>も押さえておきます。

**扱う用語（精選・21語）**

- SLA（サービスレベル合意書）／サービスレベル目標／サービスカタログ
- 構成管理（CI）／需要管理／容量・能力（キャパシティ）管理
- 変更管理／リリース及び展開管理
- インシデント管理／問題管理（既知の誤り，根本原因，予防処置）
- サービス可用性管理／サービス継続管理／RTO／RPO
- ホットスタンバイ／コールドスタンバイ
- パフォーマンス評価／継続的改善
- サービスデスク／ファシリティマネジメント

> 深掘り: [SLA・SLO・SLIとプロジェクト管理5用語まとめ](/theory/project-service-management-overview/)

### 現場のワンシーン: なぜ「インシデント管理」と「問題管理」は別物なのか

ある朝、社内システムにログインできないという問い合わせが複数の部署から相次いだとします。担当者はまず、利用者がすぐに業務を続けられるよう、パスワードの再発行や別環境への切り替えといった応急対応を行い、システムを復旧させます。これが<strong>インシデント管理</strong>の役割で、目的は「とにかく早く元に戻す」ことです。

しかし、応急対応をしただけでは、同じ問題が翌週また起きるかもしれません。そこで「そもそもなぜログインできなくなったのか」という根本原因を調査し、恒久的な対策を講じるのが<strong>問題管理</strong>の役割です。原因が判明するまでの暫定的な対処法は<strong>回避策</strong>として、根本原因が特定できた状態は<strong>既知の誤り</strong>として記録・管理します。

「インシデント管理は火を消す仕事、問題管理は火の原因を絶つ仕事」と分けて覚えると、なぜ同じような場面で2つの管理プロセスが必要なのかが理解できます。

## システム監査と内部統制

システムが適切に運用されているかを、運用者自身ではなく独立した立場から評価するのが<strong>システム監査</strong>です。監査を担う人には、対象部門から独立していることを示す<strong>監査の独立性と客観性の保持</strong>、公正に判断する<strong>監査人の倫理</strong>が求められ、結論の根拠となる<strong>監査証拠の入手と評価</strong>を経て報告に至ります。監査には目的別の種類があり、次の3つを区別しておくと出題対応がしやすくなります。

| 監査の種類 | 主に何を評価するか |
| --- | --- |
| システム監査 | 情報システムの信頼性・安全性・効率性全般 |
| 情報セキュリティ監査 | 情報セキュリティ管理策が基準（情報セキュリティ管理基準など）に沿って機能しているか |
| コンプライアンス監査 | 法令・社内規範・行動指針が順守されているか |

監査とあわせて理解しておきたいのが<strong>内部統制</strong>です。権限を1人に集中させず複数人で分担する<strong>職務分掌</strong>は、不正や誤りを一人では実行・隠蔽できない仕組みを作る代表的な統制活動です。日々の業務の中でルールが守られているかを継続的に見張る<strong>モニタリング</strong>、組織自身が自分の統制状況を点検する<strong>CSA（統制自己評価）</strong>もあわせて押さえておきます。

**扱う用語（精選・11語）**

- システム監査の目的と手順／監査の独立性と客観性の保持／監査人の倫理／監査証拠の入手と評価
- 情報セキュリティ監査基準／コンプライアンス監査
- 内部統制／職務分掌／統制活動／モニタリング
- CSA（統制自己評価）

ここまでの用語は、ChatGPTやClaudeなどの生成AIに以下のプロンプトを投げかけると、比較表つきでさらに深く掘り下げて学習できます。コピーして使ってみましょう。

```

【プロジェクトマネジメント】プロジェクトガバナンス、ステークホルダ、スコープの定義、WBS、PERT、コストベースライン、プロジェクトリスク、調達の計画
【サービスマネジメント】SLA、サービスレベル目標、構成管理、需要管理、変更管理、リリース及び展開管理、インシデント管理、問題管理、RTO、RPO、ホットスタンバイ、コールドスタンバイ

```

このプロンプトが「役割」「関連づけ」「出力形式」の3点を指定しているのは、AIに丸投げで質問すると単語の説明が羅列されるだけになりやすいからです。慣れてきたら、この3点（誰の立場で答えさせるか・どう説明させるか・どう受け取るか）を自分で組み立てられるようにしておくと、他の章や他の資格でも応用できます。
