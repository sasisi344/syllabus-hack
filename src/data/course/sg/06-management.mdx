## この章で学ぶこと

- 大分類1・中分類4「サービスマネジメント」: 合意したサービス水準から報告・改善につなげる。
- 中分類4: 障害の復旧、原因の解消、通常のサービス要求を区別する。
- 中分類4: 変更・構成・運用引継ぎを結び付け、変更後の影響を追う。
- 大分類3・中分類12「ガバナンス・監査」: 内部統制の限界と、独立した評価の根拠を読む。

本コースは基礎学習用であり、合格を保証するものではありません。

対応する分類は[IPAの2027年シラバス案Ver.0.1](https://www.ipa.go.jp/shiken/syllabus/minaoshi/rqr7mi00000068se-att/syllabus_sg_ver0_1.pdf)によります（2026年11月13日確認。今後変更される可能性があります）。旧版のプロジェクトマネジメントの独立した講義から、サービス提供者との連携と監査への対応へ重点を移しています。

## まず解いてみる

どの作業の目的を問われているかもメモしてください。導入問Aは「復旧と原因解消」、導入問Bは「独立した評価」で回収します。

- 導入問A: バックアップ回線へ切り替えてサービスは復旧した。翌日、主回線が繰り返し切れる原因を調べる活動は、ア インシデント管理／イ 問題管理／ウ サービス要求管理のどれか。
- 導入問B: 自分が設定・運用したアクセス管理を、その担当者自身が唯一の監査人として評価する。ア 独立性に問題がある／イ 詳しい担当者なので独立性に問題はない、のどちらか。

## 合意した品質を測定と改善につなげる

サービスマネジメントでは、何を提供し、どの水準を維持し、問題が起きたらどう連絡するかを揃えます。SLAはサービス提供者と利用者が品質水準などを合意するための文書・合意です。

「月間稼働率99.9%以上」の数値だけでは、測定時間や計画停止の扱いが分かりません。対象サービス、測定期間、除外条件、報告方法、未達時の対応まで読み取ると、同じ数値の選択肢を比較できます。

サービスレベル管理は、合意を置くだけでなく、実績を確認して必要な対応を調整する活動です。顧客満足やサービス満足度も、可用性の数値と同じものではありません。

| 確認するもの | 何の判断に使うか |
|---|---|
| サービスの要求事項 | 業務に必要な機能・品質が何か |
| SLAと測定条件 | どの基準で達成・未達を判断するか |
| サービスの報告 | 実績、未達の理由、対応状況がどうか |
| 継続的改善 | 次の期間に何を変えて確認するか |

供給者管理では、外部事業者に依頼したサービスが要求に合うかを継続して確認します。委託したことと、利用部門が実績を把握しなくてよいことを混同しないようにします。

<strong>判断の練習:</strong> 「営業時間内だけを測る」という合意なのに、担当者は夜間を含む稼働率で達成と報告した。改善すべきなのは、目標値と測定条件のどちらか。

<details>
<summary>答えと判断の理由</summary>

まず測定条件です。合意した対象時間で実績を再計算しないと、品質水準を達成したか比較できません。都合のよい指標へ置き換えることは改善になりません。

</details>

扱う用語: サービス／サービスマネジメント／SLA／サービスの要求事項／サービスレベル管理／供給者管理／サービスの報告／顧客満足／サービス満足度／継続的改善。

## 復旧と原因解消を別の目的として扱う

利用者からの連絡はサービスデスクで受け付け、影響と緊急性を確認します。サービスの中断などに対して、業務への影響を抑えて正常な状態へ戻すのがインシデント管理の目的です。

一方、繰り返す障害の根本原因を調べ、再発を減らすのが問題管理です。回避策で復旧できても、原因が取り除かれたとは限りません。

導入問Aは<strong>イの問題管理</strong>です。切替えによる復旧と、その後の原因調査では活動の目的が異なります。実際の運用では並行して進めることもあり、必ず一方が終わってから他方を始めるとは限りません。

<MermaidDiagram client:load chart={`flowchart TD
  A[サービスデスクで受付] --> B{中断や品質低下か}
  B -->|はい| C[インシデント管理で影響を抑え復旧]
  B -->|通常の依頼| D[サービス要求管理で処理]
  C --> E[復旧結果を記録]
  C --> F[問題管理で根本原因を調査]
  F --> G[予防処置と改善]
`} caption="受付後は依頼の種類と活動の目的を分ける" />

通常のアカウント発行依頼などはサービス要求管理の対象です。「問い合わせが来た」という共通点だけでは、すべてを障害に分類できません。

既知の誤りは、問題管理で原因などが把握され管理されている状態です。記録した回避策や傾向分析を使えば、同じ症状に毎回ゼロから対応せずに済みます。

担当者が解決できない場合や重大なインシデントは、定めた条件で上位者・専門担当へエスカレーションします。連絡先を増やすだけでなく、症状、影響範囲、発生時刻、実施済みの処置を渡すことが大切です。

<strong>判断の練習:</strong> 新入社員の標準的なアカウント発行申請が届いた。既存のサービス停止はなく、承認手順も決まっている。どの管理として扱うか。

<details>
<summary>答えと判断の理由</summary>

サービス要求管理です。インシデント管理は中断・品質低下への対応、問題管理は原因と再発への対応という目的で分けます。

</details>

## 変更前の判断と変更後の構成をつなぐ

変更管理は、システムの変更による影響やリスクを確認し、承認や実施条件を管理する活動です。リリース及び展開管理は、変更したものを利用環境へ届ける活動として区別します。

緊急の変更でも、緊急時の承認・記録・事後確認の手順が必要です。「急いでいるので記録を省く」という選択肢では、障害時に何を戻すか追えなくなります。

構成管理では、構成品目（CI）とその関係を把握します。資産管理が保有する機器や契約などを管理するのに対し、構成管理はサービスを支える要素の関係から変更や障害の影響を読む場面で役立ちます。

| 段階 | 残す判断材料の例 |
|---|---|
| 変更前 | 対象CI、影響するサービス、試験結果、承認、切戻し条件 |
| 移行・展開 | 実施記録、実施者、結果、予期しない影響 |
| 受入れ・引継ぎ | サービス受入れ基準の充足、監視、連絡先、復旧手順 |
| 運用後 | 構成の更新、障害の傾向、改善事項 |

需要管理は利用量の変化を把握し、業務の繁忙に備える視点です。継続利用の備えでは、ホットスタンバイは予備系を稼働させて待機、コールドスタンバイは必要時に起動するなどの違いがあり、切替え時間と費用を比較します。

ただし、予備機があるだけではサービス継続計画は完成しません。誰が切替えを判断し、利用部門がどの業務を優先するか、切替え後にデータと権限をどう確認するかまで必要です。

<strong>判断の練習:</strong> 更新プログラムの試験は成功したが、監視設定と障害時の連絡先を運用部門へ渡していない。このまま「運用引継ぎ完了」としてよいか。

<details>
<summary>答えと判断の理由</summary>

完了とできません。機能の試験だけでなく、合意した受入れ基準と、運用に必要な手順・責任の引継ぎを確認します。

</details>

## 統制の運用を独立した評価で確かめる

コーポレートガバナンスは、組織の経営を適切に方向付け、監督する仕組みです。その方向を日々の業務に落とし込む内部統制では、職務分掌、承認、処理結果の照合、モニタリングなどを組み合わせます。

申請者と承認者を分けるのが職務分掌の例です。AIが処理を行う場合も、誰が権限を与え、例外を確認し、結果に責任を持つかというITへの対応が必要になります。

<strong>内部統制の限界</strong>にも注目しましょう。判断の誤り、共謀、経営者による無効化などの可能性があり、統制があることから事故ゼロとは結論できません。合理的保証という考え方で、デジタル／AIリスクも考慮して運用を見ます。

システム監査は、対象の情報システムの利活用について、独立・客観的に検証・評価する活動です。監査・管理の用語は、[IPAのシステム監査基準等の改訂への対応資料](https://www.ipa.go.jp/shiken/syllabus/henkou/2023/20230710.html)でも整理されています（2023年改訂対応、2026年11月13日確認）。システム監査基準は監査人の行為や手続、システム管理基準は評価の判断尺度として区別します。

導入問Bは<strong>アの「独立性に問題がある」</strong>です。自分の運用を日常点検すること自体は有用ですが、その点検と独立した監査を同じものとして扱えません。

<MermaidDiagram client:load chart={`flowchart LR
  A[運用部門が統制を実施] --> B[記録と証拠を提供]
  B --> C[監査人が独立して評価]
  C --> D[監査報告書]
  D --> E[責任部門が改善]
  E --> F[改善提案のフォローアップ]
  F --> A
`} caption="運用・監査・改善の責任を分け、結果を次の運用へ戻す" />

監査では、規程の有無だけでなく、承認記録、設定変更履歴、アクセス記録などから実際の運用を確かめます。「問題はない」という担当者の説明は情報の一つですが、十分な監査証拠の代わりになるとは限りません。

情報セキュリティ監査、個人情報保護監査、コンプライアンス監査は注目する目的や基準を区別します。監査人が改善案を示しても、実際の設定変更や改善実施を担うのは責任部門です。

<strong>判断の練習:</strong> 「すべての管理者権限付与には事前承認がある」と説明された。運用を評価するため、何を追加で確かめるか。

<details>
<summary>答えと判断の理由</summary>

対象期間の権限付与記録と承認記録を照合し、付与前に適切な承認があるか確認します。規程の文章だけでは、実施されているか分かりません。

</details>

扱う用語: コーポレートガバナンス／職務分掌／統制活動／モニタリング／ITへの対応／内部統制の限界（合理的保証・デジタル／AIリスク考慮）／システム監査／情報セキュリティ監査／個人情報保護監査／コンプライアンス監査／システム監査人の権限と責任等／監査人の倫理／監査の独立性と客観性の保持／システム監査基準／システム管理基準／監査プロセス（予備調査，本調査，結論）／監査証拠の提供／監査報告書／改善提案のフォローアップ。

システム管理基準は管理状況を評価する際の判断尺度として用い、システム監査基準と区別します。予備調査で対象を把握し、本調査で証拠を集め、結論と報告につなげる流れを押さえてください。

## AIで学ぶ

ChatGPTやClaudeなどの生成AIに次のプロンプトを使うと、活動の目的と責任を区別する練習ができます。監査記録や実際の障害情報は入力せず、架空の状況を使いましょう。

```text
あなたは情報セキュリティマネジメントの学習を支える講師です。
「復旧、根本原因の調査、変更の承認、監査」の違いを理解したいです。
まず私が各活動の目的と責任者を説明するまで待ってください。
その後、**目的が混ざっている箇所**を指摘し、どんな記録で確かめられるか質問してください。
監査人が設定変更まで担当すると何が問題かも、私の説明から掘り下げてください。
制度上の事実に触れる場合は一次資料と版を示し、不明な点は断定しないでください。
```
{/* AI_EXAMPLE: 使うAI=ChatGPTまたはClaude / プロンプト=直前の活動の目的と責任の区別 / 見せたいこと=復旧・原因調査・承認・監査を説明し直す対話 */}
