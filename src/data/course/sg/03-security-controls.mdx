## この章で学ぶこと

- 脆弱性の番号・種類・深刻度を区別し、対処する優先順位を考える。

## まず解いてみる

選んだ理由をメモしてください。導入問Aは「認証・ログ・復旧」、導入問Bは「WebとAI」で回収します。

- 導入問A: バックアップを毎日取得しているが、本番環境と同じ管理者IDで全コピーを削除できる。ランサムウェア対策として、取得回数を増やすだけで十分か、不十分か。
- 導入問B: 文書検索AIの画面は一般社員向けだが、検索処理は全社文書を読める。プロンプトに「機密情報を出さないで」と書くだけでアクセス管理の代わりになるか、ならないか。

## 脆弱性情報を対処の優先順位に変える

セキュリティ評価では「問題を探す」「深刻度を測る」「対処を確かめる」を分けます。<strong>脆弱性診断</strong>は弱点を調べ、ペネトレーションテストは合意した範囲で侵入の可否や影響などを検証します。

実施には対象・期間・許される操作・中止条件などの合意が必要です。社内の担当者でも、許可なく本番環境への攻撃を試してよいわけではありません。

| 用語 | 答える問い | 使い方 |
|---|---|---|
| 共通脆弱性識別子（CVE） | どの脆弱性か | 製品情報や修正情報を照合する |
| 共通脆弱性タイプ一覧（CWE） | どんな種類の弱点か | 類似の設計・実装ミスを把握する |
| 共通脆弱性評価システム（CVSS） | 深刻度はどの程度か | スコアの版・評価条件も確認する |
| JVN（Japan Vulnerability Notes） | 関連情報はどこにあるか | 対象製品・影響・対処を調べる |

CVSSは脆弱性の深刻度を整理する仕組みです。点数をそのまま自組織の被害額や攻撃確率とみなしてはいけません（2026年11月13日確認。[FIRSTのCVSS公式情報](https://www.first.org/cvss/)）。

脆弱性情報の収集後は、資産台帳と製品・バージョンを照合します。インターネット公開、悪用状況、業務上の重要性、代替策の有無などを併せて、更新の優先順位を決めます。

<strong>脆弱性管理</strong>は診断の報告書を受け取って終わりではありません。修正プログラムの検証・適用・再確認を行い、適用できない間はアクセス制限などの暫定策と期限を決めます。

IoT製品の調達では、JC-STAR（セキュリティ要件適合評価及びラベリング制度）も確認の材料になります。ラベルだけで導入後の設定・更新が不要になるわけではありません（2026年11月13日確認。[IPAのJC-STAR説明](https://www.ipa.go.jp/security/jc-star/index.html)）。

### 判断の練習

公開中の顧客システムに悪用が確認された脆弱性がある。一方、外部と接続しない検証機にも別の脆弱性があり、そちらの基本スコアの方が少し高い。スコア順だけで対応を決めてよいでしょうか。

<details>
<summary>答えと判断の理由</summary>

適切ではありません。公開範囲、悪用状況、業務影響などを評価します。スコアは材料の一つであり、条件によって公開中のシステムへの対応が優先されます。

</details>

扱う用語: 共通脆弱性識別子（CVE）／共通脆弱性タイプ一覧（CWE）／共通脆弱性評価システム（CVSS）／脆弱性診断／ペネトレーションテスト／脆弱性情報の収集。

## 人と施設の対策を運用まで確かめる

機器の設定だけでは、誤送信や共連れ入室を防げません。情報セキュリティの意識向上・教育・訓練では「不審だと思ったら誰へ報告するか」を練習し、人的な行動と物理的な境界を組み合わせます。

<strong>情報セキュリティ訓練</strong>には標的型メールに関する訓練、机上演習などがあります。メールを開いた人を数えるだけでなく、報告率・報告までの時間・手順上の不足も振り返ります。

OSINT（公開情報）の利用では、自組織について公開されている情報を点検できます。採用情報や公開資料から技術構成を推測される場合もあるため、公開可否と組織のルールを守って扱います。

| 場所・行動 | 対策 | 残る注意点 |
|---|---|---|
| 入館証を人に渡して連続入場する | 入退管理システム・アンチパスバック | 他人の後ろから入る共連れには別の対策も必要 |
| 机の書類・離席中の画面を見る | クリアデスク・クリアスクリーン | 紙と画面の両方を対象にする |
| リモートワークで端末を紛失する | ストレージ暗号化、MDM、報告手順 | 遠隔消去は端末の通信状態などに左右される |
| 退職者が情報を使い続ける | アカウント停止・機器返却・秘密保持の確認 | 守秘契約だけでアクセス権は消えない |

アンチパスバックは、入退の記録の整合性から、入場済みのカードを使った再入場などを制限する仕組みです。カードを使わずに通過する行為を全て検出できるとは限りません。

モバイル機器（ノートPC，スマートフォン，タブレット端末など）のセキュリティでは、利用者エンドポイント機器の更新、画面ロック、端末紛失時の連絡を一緒に決めます。人的な管理策と技術的な管理策は併用するものです。

### 判断の練習

カードの貸し回しによる連続入場は減ったが、扉が開いた間に後ろから入る人がいた。アンチパスバックを入れたので追加対応は不要でしょうか。

<details>
<summary>答えと判断の理由</summary>

不要とはいえません。共連れ防止にはゲートや受付での確認、教育などを組み合わせます。カードを使った記録だけでは把握できない行動があります。

</details>

扱う用語: OSINT（公開情報）の利用／入退管理システム／アンチパスバック／クリアデスク・クリアスクリーン／MDM（Mobile Device Management）／リモートワーク。

## 通信・端末・ログのどこを守るか選ぶ

<strong>多層防御（Defense in Depth）</strong>は異なる場所の対策を組み合わせる考え方です。ファイアウォールを通過できたから、その通信や端末が安全だと確定するわけではありません。

<MermaidDiagram client:load chart={`flowchart TB
  A[外部ネットワーク] --> B[ファイアウォール]
  B --> C[公開サーバを置くDMZ]
  C --> D[許可した通信だけを内部へ]
  D --> E[内部システムと端末]
  C -. Web要求の検査 .-> F[WAF]
  E -. 端末の挙動 .-> G[EDR]
  B -. ログ .-> H[SIEMで関連付け]
  G -. 検知情報 .-> H
  H --> I[担当組織が調査・対応]
`} caption="防御対象と観測する場所の概念図。製品の接続順序を指定するものではない" />

| 対策 | 主に何を見るか・守るか | 選択時の手掛かり |
|---|---|---|
| ファイアウォール | 通信の許可・拒否 | 宛先やポート、通信状態などの規則 |
| WAF | Webアプリへの通信 | 不正なWeb要求の検査 |
| IDS／IPS | 不審な通信や侵入の兆候 | IDSは検知・通知、IPSは遮断も行う |
| EDR | 端末上の動作 | 侵入後の不審動作の検知・調査・封じ込め支援 |
| SIEM | 複数の機器などのログ | 関連付けて異常の全体像を見る |
| DLP | 機密情報などの持出し | データ漏えい防止のための検知・制御 |

ファイアウォールが見られる情報は製品や設定で異なり、常にIPアドレスとポート番号しか見ないとは限りません。設問では製品名だけでなく、求められている機能を読みます。

<strong>フォールスポジティブ</strong>は正常なものを不正と誤判定すること、フォールスネガティブは不正なものを見逃すことです。通知が多いからと検知機能を全面停止すると、見逃しを増やし得ます。

DMZは公開サーバなどを内部LANから分離する区域です。検疫ネットワークは更新状態などを確認して接続を制限する仕組みで、外部公開用の区域と同じ意味ではありません。

境界防御に加え、ゼロトラストではネットワークの内側にいることだけを信頼の根拠にせず、利用者・端末・要求の条件からアクセスを判断します。ファイアウォールを廃止することを意味しません。

### 判断の練習

正常な経費申請通信が攻撃と判定され、IPSに止められた。この判定はフォールスネガティブでしょうか。

<details>
<summary>答えと判断の理由</summary>

フォールスポジティブです。正常なものを不正と判定した誤検知です。不正なのに正常と判定する見逃しがフォールスネガティブです。

</details>

扱う用語: 境界防御／ファイアウォール／IDS（侵入検知システム）／IPS（侵入防止システム）／EDR（Endpoint Detection and Response）／SIEM（Security Information and Event Management）／WAF（Web Application Firewall）。

## 認証・ログ・復旧を一緒に設計する

本人確認を強くしても、承認済みの利用者が全情報を消せるなら被害は広がります。<strong>最小特権</strong>では通常業務の権限を必要な範囲に絞り、特権的アクセス権は承認・期限・記録などで管理します。

多要素認証では異なる種類の要素を組み合わせます。ワンタイムコードも、どこで生成・受信して何を証明するのかを確認し、「一度しか使えないから必ず多要素」とは判断しません。

パスキーでは公開鍵暗号を利用してサービスへ認証し、端末のPINや生体認証などで利用を承認します。パスワードや生体情報をそのままサービスへ渡す方式とは区別します（2026年11月13日確認。[FIDO Allianceのパスキー解説](https://fidoalliance.org/passkeys/)）。

生体認証の本人拒否率（FRR）は本人を拒否する割合、他人受入率（FAR）は他人を通す割合です。身体的特徴（静脈パターン認証，虹彩認証，顔認証など）や行動的特徴を使う場合も、利便性と不正受入れの両方を見ます。

マルウェアに対する保護では、定義済みの特徴と照合するパターンマッチング法、動作を見るビヘイビア法（振る舞い検知）、特徴などから推測するヒューリスティック法を区別します。既知パターンとの一致だけに依存しないことが重要です。

ログ取得は目的から設計します。誰がいつ何へアクセスしたかを確認するため、取得範囲・保存期間・閲覧権限を決め、時刻同期（NTP）とタイムスタンプによって機器間の出来事を関連付けやすくします。

バックアップでは3-2-1ルールに加え、攻撃者の権限で消されないことと復元できることを確かめます。イミュータブルバックアップは一定期間の変更・削除を制限するものですが、設定・保持期間・管理権限の確認が必要です。

導入問Aは<strong>不十分</strong>です。同じIDの侵害で本番と全コピーが消えるなら、取得回数を増やしても弱点は残ります。オフライン保管、権限分離、変更・削除の制限などを検討し、復元を試します。

<MermaidDiagram client:load chart={`flowchart TB
  A[情報のバックアップ] --> B[本番と管理権限を分離]
  B --> C[変更・削除への保護を確認]
  C --> D[別環境で復元を試す]
  D --> E[復元時間とデータの整合性を確認]
  E --> F[手順・保持期間を見直す]
  F --> A
`} caption="コピーの取得から復元の検証までを運用する" />

インシデントハンドリングは、検知・連絡受付、優先順位の判断、対応、報告などを扱う一連の活動です。事故対応では証拠を消さずに隔離や連絡を進め、定めた権限で復旧を判断します。法令に基づく報告及び本人への通知、関係機関への届出も検討対象です。個人データの報告対象や手順は[個人情報保護委員会の漏えい対応案内](https://www.ppc.go.jp/personalinfo/legal/leakAction/)で確認します（2026年11月13日確認）。

### 判断の練習

端末の時計が10分ずれ、認証サーバのログと順序を比べられなかった。ログを増やす以外に、まず何を見直すべきでしょう。

<details>
<summary>答えと判断の理由</summary>

時刻同期です。記録が大量にあっても基準時刻がそろわなければ関連付けを誤ります。取得範囲と保存期間も目的に合っているか確認します。

</details>

扱う用語: 最小特権／パスキー／ワンタイムコード／イミュータブルバックアップ／取得範囲／保存期間／時刻同期（NTP）とタイムスタンプ／情報のバックアップ。

## WebとAIの処理に権限制御を組み込む

通信を暗号化しても、送信する相手や処理の権限が誤っていれば情報は漏れます。TLSは通信路を保護するもので、Webサイトの内容や業務処理の正しさを保証する機能ではありません。

VPN・IPsec、無線LANのWPA3、メールの送信ドメイン認証（SPF，DKIM）は、使う場所と守る対象を区別します。SPFは送信元のIPアドレスなどを検証し、DKIMは署名を検証しますが、それだけでメールの内容が安全だと判断することはできません。

セキュリティバイデザインは、設計段階から安全性を組み込む考え方です。完成後の診断だけに頼らず、何を守り、どの権限を与えるかを先に決めます。

<strong>セキュアプログラミング</strong>では、攻撃を受けても不正な処理が成立しないよう実装します。SQLインジェクション対策は値をSQL命令と分けて扱うプレースホルダなど、クロスサイトスクリプティング対策は出力先に応じたエスケープなどを使います。

WAFは補助的な防御であり、アプリの欠陥を修正する工程と併用します。具体的な実装を確認するときは[IPA「安全なウェブサイトの作り方」](https://www.ipa.go.jp/security/vuln/websecurity/index.html)を参照してください（2026年11月13日確認）。

生成AIでも、<strong>プロンプトインジェクション対策</strong>を注意文だけに任せないことが重要です。参照文書を命令として信用しない設計、ツール実行の権限制限、重要操作での人の承認などを組み合わせます。

RAGは外部の文書などを検索して回答に使う方式です。RAG用のデータ及びデータストアへのアクセス制御では、利用者が読める文書だけを検索・参照できるようにし、索引や検索結果を経由した漏えいも防ぎます。

導入問Bは<strong>代わりになりません</strong>。AIへ「秘密を出すな」と指示しても、読み取れる範囲そのものは変わりません。データ側と検索処理側で、利用者に対応した権限を適用する必要があります。

### 判断の練習

部署ごとに文書の権限が異なるのに、AI検索用の索引は全社員共通で全件参照できる。画面から文書名だけ隠せば十分でしょうか。

<details>
<summary>答えと判断の理由</summary>

不十分です。本文が回答に混ざる経路もあります。データストアと検索処理にアクセス制御を適用し、権限外の情報が検索・生成へ渡らないことを検証します。

</details>

扱う用語: TLS／WPA3／送信ドメイン認証（SPF，DKIM）／安全なウェブサイトの作り方／SQLインジェクション対策／クロスサイトスクリプティング対策／RAG用のデータ及びデータストアへのアクセス制御。

防御の仕組みを補うには[暗号・通信保護とセキュリティ対策の基礎](/theory/security-controls-crypto-incident-basics/)へ進んでください。

## AIで学ぶ

ChatGPTやClaudeなどの生成AIを使い、対策があっても残る弱点を探す練習をしましょう。実環境の設定やログを貼り付けず、架空条件で行います。

```text
あなたは情報セキュリティマネジメント試験の講師です。
架空の会社について次の条件を使ってください。
・WAFはあるが、端末の不審動作を監視していない。
・バックアップはあるが、本番と同じIDで削除できる。
・文書検索AIは、全社の文書を同じ権限で検索している。
**1条件ずつ、残る弱点と対策を私に質問し、回答を待ってください。**
回答後、製品名だけでなく「守る場所・必要な権限・確認する記録」を表にしてください。
```
