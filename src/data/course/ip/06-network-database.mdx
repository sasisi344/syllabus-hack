## 宛先を見つけ、ネットワークをまたぐ

オフィスや家庭など限られた範囲を結ぶLANと、離れた拠点のネットワークを結ぶWANを区別します。インターネットサービスプロバイダ（ISP）はインターネットへの接続などを提供します。

同じLANの機器を中継するスイッチングハブと、異なるネットワークの間でパケットを転送するルータは、接続する範囲が違います。無線LANアクセスポイントは、端末の無線接続をLANへつなぐ役割です。

家庭のWi-Fiルータはこれらを一つの筐体に備えることがあります。機器の外見や商品名で判断せず、問題文の「ネットワーク間をつなぐ」「無線端末をつなぐ」という機能で選びます。

IPアドレスは通信先などを指定するためのアドレスです。IPv4は32ビット、IPv6は128ビットという長さの違いを押さえ、数字が大きいから単純に通信速度が速いとは考えません。

プライベートIPアドレスは組織内などで使い、異なる組織で同じ値を利用できます。グローバルIPアドレスはインターネット上で一意に扱うために管理されますが、常に同じ端末へ固定される意味ではありません。

IPv4環境などでアドレスを変換するNATは、ドメイン名を調べる仕組みとは別です。プライベートIPアドレスを持つ複数端末が外部へ接続する場面で、アドレス変換という役割に注目します。

<strong>DHCPは端末へ設定を配り、DNSは名前に対応する情報を調べる</strong>仕組みです。DHCPではIPアドレスのほか、DNSサーバなどの設定を配ることもありますが、名前を解決する役割自体がDHCPになるわけではありません。

冒頭問1は<strong>ア：DNS</strong>です。「IPアドレスを取得する」のか、「既に知っている名前から宛先を調べる」のかが分かれ目です。DNSの基本は[RFC 1034](https://www.rfc-editor.org/rfc/rfc1034)でも確認できます（2026年11月10日確認）。

図はキャッシュや固定設定などを省いた例です。ページを開くたびに必ずDHCPで新しい設定を取り直すわけではありません。

サブネットマスクは、IPv4アドレスのうちネットワークを示す部分を判別するために使います。例えば192.168.10.0/24では、先頭24ビットをネットワーク部分として扱い、マスクは255.255.255.0です。

この条件で192.168.10.20と192.168.10.30は同じサブネットに属し、192.168.11.20は別です。末尾の数字の近さで判断せず、どこまでがネットワーク部分かを確認します。

## 通信規約を届け方と用途で分ける

宛先へ届く経路が分かっても、どのアプリへ渡すか、欠けたデータをどう扱うかは別の問題です。ポート番号は同じ端末上の通信の窓口を区別するために使います。

TCPは到達確認や再送、順序の制御を行い、信頼性のあるデータ転送を提供します。UDPはそれらをプロトコル自体では備えない、データグラム単位の通信を提供します。

UDPを使うアプリが必要に応じて再送などを実装する場合もあります。「UDPなら必ず速い」「TCPなら絶対に途切れない」という保証ではなく、どの層でどの機能を持つかを読みます。

TCPの基本的な転送機能は[RFC 9293](https://www.rfc-editor.org/rfc/rfc9293)に基づきます（2026年11月10日確認）。TCP・UDPは届け方の軸、Webやメールの規約は用途の軸なので、同じ階層の候補として混同しないようにします。

| 用途・目的 | 規約や仕組み | 混同しやすい点 |
|---|---|---|
| Webの要求と応答 | HTTP | 接続先の安全性を自動的に保証する意味ではない |
| Web通信の保護 | HTTP over TLS（HTTPS） | 暗号化された通信でも偽サイトはあり得る |
| メールの送信・転送 | SMTP | 受信箱を同期して読む役割とは違う |
| メールの受信 | POP3 | 取得後に必ずサーバから削除するとは限らない |
| サーバのメールボックスとの同期・操作 | IMAP | 複数端末で状態を共有する用途を考える |

HTTPSの「S」はサイトの内容が真実である印ではありません。TLSによる通信の保護と、そこで相手へ送ってよい情報かという判断を分けます。

cookieは、サーバから渡された情報をブラウザが保存し、条件に合う後続のリクエストで送る仕組みです。ログイン状態の維持などにも使われますが、cookieそのものがウイルスを指すわけではありません。

無線の選択でも、Wi-Fiや5Gの名称だけで決めず、使う範囲、移動の有無、通信量、消費電力を読みます。LPWAは、小さなデータを低い消費電力で広い範囲から送るセンサーなどが候補です。

SIMカードとeSIMは、携帯回線の利用者情報などを扱うための仕組みです。eSIMは端末に組み込まれた形で利用するため、物理カードを差し替えることだけが契約切替の方法ではありません。

### 判断の練習：サーバの受信箱を複数端末で使う

PCとスマートフォンで、サーバ上の同じメールボックスの既読状態やフォルダを同期したい。SMTPとIMAPのどちらが目的に合うでしょうか。

<details>

IMAPです。SMTPは送信・転送のための規約で、サーバ上のメールボックスを操作・同期する役割とは違います。

「メールを使う規約」という大きな括りから、送るのか、受信箱を読むのかへ条件を絞ります。

</details>

扱う用語：TCP／UDP／ポート番号／HTTP／HTTP over TLS（HTTPS）／SMTP／POP3／IMAP／cookie／5G（第5世代移動通信システム）／LPWA／SIMカード／eSIM（embedded SIM）。

## データの重複と取り出す操作を見分ける

データベースの関係モデルでは、データを表の形で捉えます。その管理システムがRDBMSで、行を一意に識別するために選ぶ列や列の組合せが主キーです。

同姓同名の人がいるなら氏名だけでは主キーにできません。顧客IDなど、重複せず各行を識別できる値を選びます。

注文表のすべての行に「顧客ID・顧客名・顧客住所」を繰り返し入れると、転居のとき一部の行だけを直して住所が食い違うおそれがあります。顧客の情報と注文の情報を分け、顧客IDで対応づけると、その不整合を抑えられます。

<strong>正規化の目的は、データの重複に伴う更新時の矛盾などを防ぐこと</strong>です。表を分ければ必ず検索が速くなる、という性能上の保証ではありません。

例えば注文表に「注文ID・顧客ID・注文日」、顧客表に「顧客ID・氏名・住所」を置きます。住所の変更は顧客表に集約し、注文のたびに同じ住所を修正する必要を減らせます。

正規形は、まず一つの欄に値を繰り返し詰め込まないこと、次に複合キーの一部だけに依存する項目を分けること、さらにキー以外の項目を経由して決まる項目を分けること、と段階の目的を追います。第1〜第3正規形という補助語は、この整理の目印です。

必要な情報を取り出す操作は、行を絞る「選択」、列を取り出す「射影」、関連する表を対応づける「結合」で区別します。問題文の「選ぶ」という日常語だけで「選択」と決めず、行か列かを見てください。

| やりたいこと | 関係演算 | 何に注目するか |
|---|---|---|
| 注文日の条件に合う注文だけに絞る | 選択 | 行の条件 |
| 注文IDと顧客IDだけを取り出す | 射影 | 必要な列 |
| 注文へ顧客名を対応づける | 結合 | 表同士を結ぶ条件 |

結合条件を省くと、意図しない組合せまでできることがあります。顧客IDが一致するという条件を確認し、氏名の見た目が似ているだけで結びつけないようにします。

### 判断の練習：表を分けた後の注文一覧

顧客名と住所を顧客表へ分離した。顧客名付きの注文一覧を作るには、注文表から列を取り出す「射影」だけで十分でしょうか。

<details>
<summary>答えと判断の根拠</summary>

十分ではありません。注文表には顧客名がないため、まず顧客IDなどを条件に顧客表と結合する必要があります。

その後、必要な列だけを射影できます。表を分ける設計と、分けた表を利用する操作はセットです。

</details>

## 複数の更新を一まとまりで確定する

注文の保存と在庫の減算が別々に確定すると、「注文だけできたのに在庫が確保されていない」といった状態が残ります。複数の更新を一まとまりに扱う処理単位がトランザクションです。

処理全体を成功として確定するのがコミット、途中で失敗した処理などを取り消して元の状態へ戻すのがロールバックです。トランザクションは、この二つの判断と関連づけて覚える補助語です。

<MermaidDiagram client:load chart={`flowchart TB
  A["トランザクション開始"] --> B["在庫を確認・更新"]
  B --> C["注文を登録"]
  C --> D{"全処理が成功したか"}
  D -->|"成功"| E["コミットして確定"]
  D -->|"失敗"| F["ロールバックして取消"]
  E --> G["整合する状態を残す"]
  F --> G`} caption="在庫更新と注文登録を一まとまりにする学習用の例" />

この基本は[PostgreSQL公式文書のトランザクション解説](https://www.postgresql.org/docs/current/tutorial-transactions.html)でも確認できます（2026年11月10日確認）。ここでは製品ごとのコマンド構文より、まとめて確定・取消する考え方を押さえます。

複数の利用者が同時に更新するときは、トランザクションを使うだけであらゆる競合が解消するわけではありません。同時実行制御（排他制御）で、同じデータの変更が不整合を生まないよう調整します。

例えば在庫が残り1個のとき、二人が古い「1個」を読んでそれぞれ注文を確定すると過剰な受注につながります。必要な更新をロックなどで適切に調整することが重要です。

ただし、一方が商品Aをロックし他方が商品Bをロックしたまま、互いに相手のデータを待つことがあります。この循環した待ち状態がデッドロックで、冒頭問2の答えは<strong>イ</strong>です。

ロックは競合を防ぐための手段、デッドロックは待ちが循環して進まない状態なので同義ではありません。ロックを取得する順序を統一することなどが対策となり、発生時は処理の取消・再試行が必要になる場合があります。

### 判断の練習：片方だけ成功した処理

一つのトランザクションとして在庫減算と注文登録を行ったが、注文登録でエラーが起きた。全体を取り消すとき、コミットとロールバックのどちらを選ぶでしょうか。

<details>
<summary>答えと判断の根拠</summary>

ロールバックです。確定前の一まとまりの処理を取り消し、在庫だけが減った状態を残さないようにします。

コミットは成功した処理を確定する操作です。確定済みの過去の処理を、いつでも通常のロールバックで取り消せるという意味ではありません。

</details>

{/* LEARNER_NOTE: 候補=排他制御とデッドロック、確定前の取消と確定後の修正の区別 / 種類=think / 筆者の実体験で記入 */}

扱う用語：同時実行制御（排他制御）／コミット／ロールバック／デッドロック。

## AIで学ぶ

ChatGPTやClaudeなどの生成AIに次のプロンプトを使うと、表を分ける理由と更新をまとめる理由を、別の軸として掘り下げられます。実データを貼らず、架空の注文を使ってください。

```text
あなたはITパスポートの学習を支える講師です。
私は「注文表を正規化すれば、同時注文でも在庫不足は起きない」と説明しました。
**表の設計**と**同時更新の制御**を分けて理解したいです。
まず、住所の重複更新と、残り1個の在庫への同時注文では何が違うか、私に質問を一つしてください。
私の返答後、正規化・排他制御・コミット・ロールバックの役割を整理し、説明の穴を指摘してください。
最後に、私がデッドロックを自分の言葉で説明するので、待ちの循環があるか確認してください。
```
{/* AI_EXAMPLE: 使うAI=ChatGPTまたはClaude / プロンプト=表の設計と同時更新の制御 / 見せたいこと=正規化ですべての競合を防げるという混同を対話で修正する過程 */}

AIの説明は、行・列・更新単位を自分で書き分けて点検します。「安全になる」という一言で異なる仕組みをまとめていないか確かめましょう。
