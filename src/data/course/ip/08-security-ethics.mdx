## 攻撃の名前を対象と手口から見分ける

偽のログイン画面へ誘導して認証情報を盗むフィッシングは、人をだます手口です。特定組織を狙う標的型攻撃や、取引先などを装って送金先の変更を求めるビジネスメール詐欺（BEC）も、本文の自然さだけでは見破れません。

ソーシャルエンジニアリングは、人の心理や行動の隙を利用する手口です。メールに書かれた電話番号で確認するだけでは、確認先も攻撃者という可能性があるため、既知の連絡先など別の経路を使います。

ランサムウェアは、暗号化などでデータを使えなくしたり、盗んだ情報の公開を脅したりして金銭を要求します。トロイの木馬は正規のものを装う不正プログラム、スパイウェアやキーロガーは情報収集やキー入力の記録という働きに注目します。

これらの名前は、すべてが互いに排他的な分類とは限りません。正規ソフトを装って侵入し、情報を盗むなど、複数の特徴が同じ攻撃に含まれる場合があります。

| 問題文の手掛かり | 主に考える脅威 | 区別する点 |
|---|---|---|
| 入力を通じて不正なSQLを実行させる | SQLインジェクション | データベース操作に介入する |
| 悪意あるスクリプトを他の利用者のブラウザで動かす | クロスサイトスクリプティング | ブラウザ側での実行に注目する |
| 多数の端末から大量の通信を送る | DDoS攻撃 | 分散した送信元でサービスを妨害する |
| 修正プログラムが提供される前などに脆弱性を悪用する | ゼロデイ攻撃 | 既知の修正を未適用の状態とは区別する |
| 外部資料の指示でAIの本来の動作を変えようとする | プロンプトインジェクション | 参照データを命令として扱わせる |

第7章のRAGは外部資料を回答へ利用するので、検索先へ悪意ある指示が混ざることにも注意が必要です。冒頭問2は<strong>ア：プロンプトインジェクション</strong>で、自然に誤った内容が出るハルシネーションとは原因が違います。

この脅威は[AISIのAIセーフティに関するレッドチーミング手法ガイド](https://www.ipa.go.jp/digital/ai/begoj90000004szb-att/ai_safety_rt_v1.00_ja.pdf)でも扱われています（第1.00版、2026年11月10日確認）。資料を検索して渡すだけで、そこに含まれる指示まで信頼してよいわけではありません。

## 守る資産と組織の責任から対策を決める

セキュリティの対象はサーバだけではありません。顧客データ、紙の契約書、担当者が持つ端末なども情報資産に含まれ、何を誰が管理するかを台帳などで把握します。

機密性は許可された人だけが情報へアクセスできること、完全性は情報が不正に改変・破壊されないこと、可用性は必要なときに使えることです。同じ事故が複数の性質へ影響する場合もあります。

たとえば顧客情報の漏えいは機密性、送金額の改ざんは完全性、システム停止は可用性に関係します。暗号化で機密性を高めても、サービス停止まで解決できるわけではありません。

リスクアセスメントでは、リスクを特定し、発生の可能性と影響などを分析し、基準と比べて評価します。「危険そう」という印象だけで対策製品を選ぶ前に、何をどの程度守るかを明らかにします。

| 対応の考え方 | 行動例 | 残る注意点 |
|---|---|---|
| リスク回避 | 危険が許容できない業務を中止する | その業務の便益も失う |
| リスク低減 | 権限の見直しや更新で可能性・影響を減らす | リスクがゼロになるとは限らない |
| リスク共有 | 保険や契約などで影響を分担する | 委託しても自社の責任がすべて消えるとは限らない |
| リスク保有 | 基準と照合し、把握した残余リスクを受け入れる | 未認識のまま放置することとは違う |

リスク共有にはリスク移転やリスク分散という捉え方もあります。用語を覚えるときは、「どんな行動を取ったか」を対応づけ、外部委託なら必ず安全という説明を避けます。

情報セキュリティ方針（情報セキュリティポリシー）は組織としての方針、情報セキュリティ対策基準はそれを具体化する基準として整理します。SOCは監視・分析、CSIRTはインシデント対応の調整などに注目し、組織ごとの分担に従います。

ゼロトラストは、社内ネットワークにいることだけを信用の根拠にせず、利用者・端末・アクセス先などを確認して権限を制御する考え方です。「社内は無条件で安全」という前提を置きません。

セキュリティバイデザイン、プライバシーバイデザインは、守る仕組みを企画や設計の段階から組み込む考え方です。完成してから注意書きを足すことだけでは、過剰な権限や不要な情報収集を解決できません。

### 判断の練習：保険があれば何もしなくてよいか

情報漏えいに備えて保険に加入したので、アクセス権の管理と事故対応体制を廃止する案が出た。リスク共有の考え方として適切でしょうか。

<details>
<summary>答えと判断の根拠</summary>

適切ではありません。保険は損失の一部を分担する手段で、漏えいの発生や信用低下、対応の義務までなくすものではないからです。

リスクの対応方法は一つだけに限らず、低減策や対応体制を組み合わせます。

</details>

## 認証・本人確認・暗号の目的を分ける

利用者が誰かを確かめる認証と、その人に何を許すかというアクセス管理は別です。正しくログインできても、担当外の顧客データまで見られる設定なら問題が残ります。

多要素認証では、記憶・所有・生体という<strong>異なる種類の要素</strong>を組み合わせます。パスワードと秘密の質問は両方とも記憶要素なので、冒頭問1は<strong>イ</strong>です。

二回の操作を求める多段階認証と、多要素認証は同義ではありません。ワンタイムパスワードという名称だけでも判断せず、それを受け取る端末など何を所持している必要があるかまで読みます。

パスキーは公開鍵暗号を使うFIDO認証に基づく仕組みで、利用するサイトなどに結びついた認証情報を使います。端末のPINコードや生体認証で利用を承認しても、指紋そのものをサイトへ送るという説明ではありません。

[FIDOアライアンスのパスキー解説](https://fidoalliance.org/passkeys/?lang=ja)では、フィッシングなどへの耐性を説明しています（2026年11月10日確認）。アカウント復旧の方法や端末管理も含めて考え、パスキーだけであらゆる被害が消えるとはしません。

eKYCはオンラインで本人確認を行う仕組みを指し、身元の確認に注目します。一度の認証で複数サービスを利用するシングルサインオンとは目的が違い、eKYCがあれば以後のアクセス管理が不要になるわけではありません。

暗号では、共通鍵暗号方式は同じ鍵を暗号化・復号に使い、鍵を秘密に共有する方法が課題になります。公開鍵暗号方式では、公開鍵と秘密鍵の対を使い、処理の目的で鍵の使い方が変わります。

図は鍵の役割を比べる模式図で、実際の暗号通信の全手順ではありません。デジタル署名は通常ハッシュ値などを利用し、署名だけでは内容を秘密にできません。

ハッシュ関数はデータから一定長の値を求めるなどの性質を持ち、改ざんの検知などに使います。ハッシュ値から元の内容へ「復号」する仕組みではなく、ハッシュ値の比較だけでは作成者の身元まで証明できません。

認証局（CA）が発行するデジタル証明書は、公開鍵と主体の対応を確認するために使います。公開鍵基盤（PKI）はその信頼を支える枠組みで、「公開鍵だから誰の鍵か確かめなくてよい」という意味ではありません。

耐量子計算機暗号（PQC）は、量子コンピュータを使った攻撃にも耐えられるよう設計する暗号技術です。量子通信の別名ではなく、通常のコンピュータで利用する方式も含みます。

[NISTは2024年8月に最初のPQC標準3件を公表](https://www.nist.gov/news-events/news/2024/08/nist-releases-first-3-finalized-post-quantum-encryption-standards)しています（2026年11月10日確認）。ここでは方式名の暗記より、将来の攻撃に備えて暗号方式を見直す目的を押さえます。

### 判断の練習：署名があれば内容は読めないか

見積書にデジタル署名を付けたので、暗号化しなくても第三者は内容を読めない、という説明は正しいでしょうか。

<details>
<summary>答えと判断の根拠</summary>

誤りです。デジタル署名は作成者や改ざんの有無の確認に使い、内容の秘匿は暗号化の目的です。

誰の公開鍵・秘密鍵を使い、何を確かめたいのかを分けると、暗号化との混同を避けられます。

</details>

## 予防・検知・復旧を組み合わせる

OSやソフトウェアの更新、脆弱性修正プログラムの適用は、既知の弱点を減らす予防策です。脆弱性管理は、情報の収集や対象の把握、優先順位づけ、修正の確認まで含めて考えます。

ファイアウォールは通信の条件に基づく制御、WAFはWebアプリケーションへの攻撃を想定した通信の検査・制御に注目します。WAFを置けば、アプリ自体の安全な実装や更新が不要になるわけではありません。

IDSは侵入などの検知、IPSは検知に加えて遮断などの防止を目的にします。EDRは端末での不審な動作を検知し、調査・対応を支援する仕組みです。

同じ「防御製品」でも、観測する場所や対応できる段階が違います。誤検知や見逃しもあり得るため、製品名を一つ選べばすべてを防げるという選択肢には注意します。

バックアップでは、取得したことだけでなく復元できることを確認します。普段使う端末から自由に書き換えられる保存先しかなければ、ランサムウェアで一緒に被害を受けるおそれがあります。

バックアップ分離や、一定期間の書換え・削除を制限するイミュータブルバックアップは、復旧用データを守る選択肢です。第5章のRAIDのミラーリングは、誤削除や暗号化まで複製される可能性があり、別時点からの復元とは役割が違います。

事故が疑われたら、組織の手順に従って担当窓口へ報告し、感染端末のネットワーク隔離などで拡大を防ぎます。自己判断でログを消したり初期化したりすると調査の妨げになるので、証拠保全と復旧を調整します。

予防から事故対応までの基礎は[IPA「中小企業の情報セキュリティ対策ガイドライン」](https://www.ipa.go.jp/security/guide/sme/about.html)を参照してください（2026年11月10日確認）。復旧後は原因や対応の経緯を点検し、設定・手順の改善へ戻します。

### 判断の練習：毎日コピーしていれば復元できるか

業務端末からいつでも変更・削除できる共有フォルダへ、毎日データをコピーしている。これだけでランサムウェア後の復旧に十分だといえるでしょうか。

<details>
<summary>答えと判断の根拠</summary>

十分とはいえません。攻撃がその共有フォルダまで及び、コピーも暗号化・削除される可能性があるからです。

分離や変更制限、世代の保持、復元の確認を組み合わせます。「バックアップあり」という名称ではなく、攻撃後にも使える状態かを考えます。

</details>

扱う用語：脆弱性管理（OSアップデート，脆弱性修正プログラム（セキュリティパッチ）の適用）／脆弱性検査／ファイアウォール／WAF（Web Application Firewall）／侵入検知システム（IDS）／侵入防止システム（IPS）／EDR（Endpoint Detection and Response）／マルウェア対策ソフト／ランサムウェア対策（データのバックアップ，バックアップ分離，イミュータブルバックアップ）／マルウェア感染時の対応。

## 正しさと公開してよいかを別々に確認する

情報倫理では、違法でないかという確認に加えて、他者の権利や不利益、社会への影響を考えます。デジタルシティズンシップはデジタル社会へ責任を持って参加する考え方で、ネチケット（ネットマナー）もその行動に関係します。

撮影時・録音時・配信時の同意は、撮影を許されたことと、不特定多数へ公開してよいことを分けて確認します。同報メールでも、互いのアドレスを開示する必要がない相手へTOやCCで送ると、情報を漏らすおそれがあります。

一度公開した情報が複製や拡散によって残るデジタルタトゥーも、投稿前に考えたい論点です。事実だったとしても、本人が望まない個人情報を拡散してよいとは限りません。

| 用語 | 判断する軸 |
|---|---|
| 偽情報（ディスインフォメーション） | 意図的に人を誤らせる情報か |
| 誤情報（ミスインフォメーション） | 誤りを含み、誤らせる意図なく広まる情報か |
| 悪意ある情報（マルインフォメーション） | 事実を害する目的で利用・公開していないか |
| エコーチェンバー | 似た意見が集まる交流の中で意見が増幅されていないか |
| フィルターバブル | 個人向けの選別で見える情報が偏っていないか |

見た目のリアルさだけでは、画像や音声の真偽は判断できません。ディープフェイクはAIなどを使った合成・改変に関係する語で、一次資料、公開元、日時、別の独立した証拠を確認します。

ハルシネーションは、生成AIが根拠のない内容や事実と違う内容をもっともらしく出力することです。古い出力情報、根拠・出典不明の出力情報、差別的表現なども、公開前に点検します。

説明可能なAI（XAI）は人が判断根拠を理解できるようにする考え方や技術です。ヒューマンインザループ（HITL）は人が判断や確認の過程に関わることで、説明を表示する機能と、人が止められる仕組みは同じではありません。

トロッコ問題のように、複数の価値や不利益が衝突する問いでは、正解率だけでは方針を決められません。誰がどの基準で判断し、結果に責任を持つかまで考えるための論点です。

AIサービスのオプトアウトポリシーは、入力内容の学習利用などを拒否できる条件を確かめる際に使います。対象範囲はサービスごとに異なり、設定を変えれば保存も漏えいリスクもすべてなくなる、という意味ではありません。

個人情報を含む資料では、利用目的や外部への提供などの条件も確認します。個人情報保護法の判断は[個人情報保護委員会の通則編](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)を基準とし（2026年11月10日確認）、詳しい法令の切り分けは第1章で扱います。

### 判断の練習：AIの引用が実在すれば公開できるか

生成AIが示した人物名と発言の出典を確認できた。出典が実在するので、非公開の個人情報を含む資料もそのままSNSへ載せてよい、という判断は適切でしょうか。

<details>
<summary>答えと判断の根拠</summary>

適切ではありません。出典や内容の真偽の確認と、その情報を利用・公開してよいかという確認は別だからです。

本人の同意や公開範囲、利用目的、組織の規程などを確かめます。AIの回答が正しいことだけで公開の根拠にはなりません。

</details>
