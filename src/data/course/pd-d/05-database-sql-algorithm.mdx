## データベースを意味・制約・操作から設計する

同じ販売記録でも、注文を確定する業務と月次分析では必要な更新速度や整合性が異なります。[PD-S第4章](/course/pd-s/04-database-security-implementation/)で共通の内部動作を補い、ここでは技能3-2・3-3・4-1に沿って、モデルとクエリを選ぶ根拠を練習します。

### データモデルと方式を業務から選ぶ

小売チェーンが「顧客の注文を確定したい」と「顧客間の紹介関係をたどりたい」を一つのDBへ求めています。先に必要な関係と操作を整理するのが、データアーキテクチャからデータモデルへ進む入口です。

関係モデルは表と表の対応でデータを表します。グラフ型のデータモデルは対象と関係をたどる表現で、紹介の連鎖などでは関係そのものが問い合わせの中心になります。

ドキュメント指向データベースは文書、列指向データベースは列中心の集計、グラフデータベースは関係の探索に位置づけます。

キーバリュー型データベースはキー検索、インメモリデータベースはメモリ中心の処理の候補です。特徴は重なり、方式名だけで永続性等の保証を決めません。

試験では：対象の関係、検索・更新、既存環境、予算の条件から方式を比較する観点です。混同注意：「データ量が多いからNoSQL」と一つの条件だけで決めることです。

判断の練習：注文と明細の対応を厳密に保ちたい担当者が、自由な項目追加だけを理由に方式を決めています。何を比較へ足しますか。

答え：参照関係、複数行の更新単位、問い合わせ、運用費を足します。データエンジニアは架空の注文登録・取消しを試し、整合性が要件を満たすかを選定資料に残します。

### 概念から論理・物理へ具体化する

販売部門が「一つの注文には複数の商品があり、商品は多くの注文へ現れる」と説明しました。概念データモデルは、この業務の対象と意味上の関係を、製品や格納場所へ依存せずに表します。

論理データモデルでは、注文・明細・商品をどの表とキーで表すかを具体化します。物理データモデルでは、データ型、配置、索引などを実装先の条件へ落とし込みます。

答え：不十分です。識別の範囲を確認し、店舗と注文番号の組等で識別する論理設計へ直します。索引はその後の実装です。

### 識別と参照の制約を定める

店舗Aと店舗Bに注文番号100が存在します。主キーは一行を一意に識別するためのキーで、外部キーは別の表などのキーを参照する関係を表します。

サロゲートキーは業務上の番号とは別に付ける識別子です。これを追加しても、店舗と注文番号の重複を許してよいわけではありません。業務上の一意性は別の制約として残します。

一貫性制約（一意性制約，参照制約，検査制約 など）は不正な状態を防ぎます。一意性制約は重複、参照制約は参照先、検査制約は値の条件を検査します。

明細を注文と商品へ結びます。数量が必須なら、正数の検査と未設定を許さない定義が必要です。

| 表 | 一行の意味 | 識別と参照の案 |
|---|---|---|
| orders | 一つの店舗注文 | 主キーはstore_idとorder_no |
| products | 一つの商品 | 主キーはproduct_id |
| order_lines | 一注文の一明細行 | store_id・order_no・line_noで識別し、注文と商品を参照 |

試験では：どの不正状態をどの制約で止めるかを選びます。混同注意：画面で検査しているからDB側の制約は不要とする説明です。

判断の練習：存在しない商品番号の明細が、CSV取込みから入ります。商品名の入力必須だけで防げますか。

答え：防げません。商品表への参照制約と取込み時の照合を設計します。不一致行は推測で商品へ割り当てず、元の値と理由を残して確認へ回します。

### 重複の解消と読取り性能を両立する

一枚の販売表に顧客名を何度も書くと、改名時に更新漏れが生じます。正規化は、データの依存関係を基に表を分け、更新時の不整合を減らす設計です。導入問Aはイで、顧客の情報を顧客として管理する関係を先に見直します。

部分関数従属は複合キーの一部だけで値が決まる関係、推移関数従属はキーから別の非キー項目を経由して値が決まる関係です。明細のキーが注文番号と行番号の組なのに、注文日が注文番号だけで決まるなら、注文日を明細ごとに持つ設計を点検します。

完全関数従属は複合キーの一部では値が決まらない依存です。分解後も元の意味と制約を保てるかを確認します。

非正規化は、読み取りを速くするなどの目的で意図的に重複を持たせる選択です。更新する正本、反映の方法、許容する遅延、照合方法が必要で、単に表をまとめればよいとは限りません。

試験では：更新異常を減らす設計と、測定した性能を改善する設計を分けます。混同注意：遅い原因を測らずに正規化を全部やめることです。

判断の練習：月次集計だけが遅いため、顧客名を全明細へ複製する案です。何を先に確かめますか。

答え：遅いクエリと実行計画、索引、集計頻度を確認します。集計専用のデータを作る場合も、正本と更新経路を定めて整合性を検証します。分解の手計算は[正規化の練習](/method/db-normalization-hack/)へ進めます。

### 物理設計を測定へつなぐ

全店舗の売上明細が増え、日付別集計の待ち時間が長くなりました。索引は検索経路を作る仕組み、性能評価は条件を固定して実際の応答や資源使用を測ること、チューニングは測った原因へ調整を施すことです。

論理データ構造のマッピング、配置モード、ファイル編成、最適ブロック設計は、論理設計を格納・アクセスへ具体化する検討に位置づけます。

ディスク容量見積りは索引・一時領域・ログ・増加分も含めます。データベースの性能評価は本番の量と分布に近い条件で行います。

B木インデックスは範囲検索、ハッシュインデックスは等値検索の候補として比較します。カバリングインデックスは、問い合わせに必要な項目を索引から得られるようにする設計です。

ユニークインデックスは一意性、クラスタ化インデックスは格納と検索順、ビットマップインデックスは値のビット表現、転置インデックスは語等の出現先に位置づけます。

インデックス数を増やすほど更新時の仕事や容量も増えます。再編成は物理配置などを整え直す操作で、業務の意味の誤りを直す正規化とは目的が異なります。

試験では：検索条件と更新頻度を両方見て索引を選びます。混同注意：「索引がある」だけで必ず使われる、必ず速くなるとする判断です。

判断の練習：日付範囲を指定する集計へ、商品コードの等値検索用索引だけを追加しました。改善を判断するには何を見ますか。

答え：対象クエリの条件、データ分布、実行計画と計測結果を見ます。索引の目的が問い合わせに合っているか、更新の負担が許容範囲かも比較します。

### SQLで取り出す粒度を決める

担当者が「店舗ごとの売上合計が500以上の店舗を出してほしい」と依頼しました。SQLでは、まず一行の意味を定め、その後で集計前と集計後の条件を分けます。

SELECT文は必要な列や計算結果を取り出す操作です。集合関数は複数行の合計などを求め、ウィンドウ関数は明細行を残したまま区切り内の計算を付けられます。

架空のsales表は、返品等を考慮しない売上明細です。金額は数値型で未設定を許さず、一行が一つの売上記録を表す前提にします。

| sale_id | store_id | amount |
|---|---|---:|
| 1 | A | 200 |
| 2 | A | 400 |
| 3 | B | 300 |

```sql
SELECT store_id, SUM(amount) AS total_amount
FROM sales
GROUP BY store_id
HAVING SUM(amount) >= 500;
```

結果はA、600の一行です。WHERE amount >= 500では先に全明細が除かれ、店舗合計を求められません。

```sql
SELECT sale_id, store_id, amount,
       SUM(amount) OVER (PARTITION BY store_id) AS store_total
FROM sales;
```

こちらは3行を残し、Aの各行へ600、Bへ300を付けます。店舗一行への集約とは粒度が異なります。

集合演算は和・共通部分、関係演算・関係代数は選択・射影・結合等の基礎です。SQLでは重複・未設定値も確認し、数学の集合と同一視しません。

試験では：WHERE・GROUP BY・HAVINGと、行を残す計算の違いを読みます。混同注意：「合計を表示する」だけを見て、求める行数を確かめないことです。

判断の練習：各明細に店舗合計と各明細の金額を並べたい場合、最初のSQLと二つ目のSQLのどちらが目的に合いますか。

答え：二つ目です。ウィンドウ関数を使う例では明細の粒度を維持できます。必要なら順序と計算範囲も明示し、累積値と区切り全体の合計を取り違えないようにします。

### 結合と副問合せで件数を確かめる

顧客表と注文表を結合すると、一人が3件注文していれば顧客が3行現れます。副問合せは別の問合せを中へ組み込み、相関副問合せは外側の行を参照しながら条件を調べる形です。

「注文がある顧客を一人一行で出す」なら、存在の判定を選べます。customersのcustomer_idは一意、ordersは複数注文を持てる前提です。

```sql
SELECT c.customer_id
FROM customers AS c
WHERE EXISTS (
  SELECT 1 FROM orders AS o
  WHERE o.customer_id = c.customer_id
);
```

存在の判定なので、注文が3件でも顧客は一行です。金額を付ける要件なら、集計と結合の順序も検討します。

ビュー表は問合せで定義した見え方、実表はデータを格納する表です。ビューを使っていても、結合先の一意性や利用権限の確認を省けるとは限りません。

試験では：一対多の結合で集計値や件数が増えないかを確認します。混同注意：DISTINCTを後から付ければ、間違った合計まで直るという説明です。

判断の練習：注文表を明細表へ結合した後、注文表の注文総額を足したら売上が増えました。どこを疑いますか。

答え：明細件数分だけ注文総額が繰り返された可能性です。明細の金額を集計するか、注文一行の粒度で集計してから必要な表へ結合します。

### CRUDと制約で安全に変更する

誤って登録した一つの売上を訂正します。INSERT文は行の追加、UPDATE文は既存行の更新、DELETE文は行の削除です。どれも対象・件数・制約を確認して扱います。

```sql
INSERT INTO sales (sale_id, store_id, amount)
VALUES (4, 'B', 100);

UPDATE sales
SET amount = 120
WHERE sale_id = 4;

DELETE FROM sales
WHERE sale_id = 4;
```

順に実行すると追加行だけを削除する教材です。更新前に同じ条件のSELECTで対象を調べ、実行後は件数と結果を照合します。実データへ貼り付けません。

DDL（データ定義言語）は表などの定義、DML（データ操作言語）は行の操作、DCL（データ制御言語）は権限の制御に位置づけます。GRANT文は権限の付与、REVOKE文は取り消しであり、参照だけの担当へ全操作を与える理由にはなりません。

CASCADEは参照に沿う連動、TRIGGERは所定の操作等に伴う処理です。変更の伝わる先と内容を検証します。

会話型SQLは対話利用、埋込みSQLと親言語との接続はプログラム利用です。カーソル操作は行ごと、非カーソル操作は集合での処理として比較します。

試験では：CRUDの要件と命令、権限、変更範囲を対応させます。混同注意：WHEREのないUPDATEやDELETEを一行だけの変更と思い込むことです。

判断の練習：B店舗の誤った1件を直したいのに、WHERE store_id = 'B' と書きました。この教材表なら安全でしょうか。

答え：目的の一行を保証しません。Bに複数行があるので、sale_idなどで対象を一意に指定します。対象件数を確認し、承認された変更の範囲と一致させます。

### 同時更新・回復・分散の境界を決める

在庫が残り1個の商品を二人が同時に買おうとしています。ACID特性は更新のまとまり、整合性、隔離性、永続性を考える基礎です。同時実行制御（排他制御）と隔離性水準は、同時処理にどの干渉を許すかの設計へつながります。

ロック方式の共有ロック・専有ロック等でアクセスを調整します。ロック粒度は行・表等の単位で、競合と管理負担を整合性・待ち時間から比較します。

多版同時実行制御（MVCC）は複数の版で同時処理を支えます。読取りの待ちが減っても、業務制約が全て守られるとは限りません。

| 現象 | 業務での読み方 |
|---|---|
| ダーティリード | まだ確定していない変更を読んでしまう |
| ノンリピータブルリード | 同じ行を再読すると値が変わる |
| ファントムリード | 同じ条件で再検索すると該当行の集合が変わる |
| ライトスキュー（write skew） | 別々の行を更新しても、複数行にまたがる業務条件が崩れ得る |

二人が別々の当番行を「不在」へ変えると、「少なくとも一人在席」を破り得ます。行が異なっても業務の整合性は崩れます。

2相ロッキングプロトコルはロックの獲得と解放の段階を分ける制御、デッドロックは互いの資源を待ち続ける状態です。Wait-Die方式とWound-Wait方式は、トランザクションの新旧等を使って待機・中止を調整する方式として位置づけます。セマフォ方式も共有資源へのアクセス調整に関する用語です。

コミットメント制御は確定・取消しを管理します。2相コミットメントは分散する参加者の確定を調整する方式で、2相ロッキングと目的が違います。補償トランザクションは、すでに実施した業務の影響を打ち消す処理であり、時間を戻して全て無かったことにする仕組みではありません。

  D -->|不成立| F["取消し・再試行判断"]
  E --> G["バックアップとログから回復を検証"]
`} caption="更新前の整合性、確定、障害後の回復を別の確認にする" />

ダンプファイルは保存したデータ、ジャーナルファイル（ログファイル）は更新の記録に関わり、リストアはバックアップからの復元です。データディレクトリは定義等の管理情報、チェックポイントは回復処理の基準点として位置づけます。

フォワードリカバリ（ロールフォワード）は更新の適用、バックワードリカバリ（ロールバック）は未確定更新の取消しです。必要な時点への復旧も試験します。

試験では：守るべき業務条件から制御と復旧を組み合わせます。混同注意：バックアップを同時更新の対策にすることや、MVCCだけで全制約を守れるとすることです。

判断の練習：当番の二行を別々に変更して、両者とも不在になりました。行ごとの一意性制約だけで十分でしょうか。

答え：不十分です。当番条件を守る更新単位と競合制御を設計し、同時処理を再現して検証します。

### 分散で許す遅延と障害を決める

店舗の通信が切れても、売上記録を受け付けたい一方、在庫は全店で二重に売りたくありません。レプリケーションは複製、シャーディングはデータを分割して担当を分ける方法、結果整合性は更新が伝わって最終的に一致する性質です。

在庫確定と集計で必要な一致時点を分けます。表の分散（水平，垂直）は行・列の分割、分散問合せは複数箇所の参照、分散トランザクションは複数箇所の更新です。

CAP定理はネットワーク分断時の一貫性と可用性の両立に関する制約、BASE特性は分散での可用性や最終的な一致を考える際の性質です。スプリットブレインは複数の側が自らを正として動く状態で、複製があれば解決するとは限りません。

分散処理フレームワーク（Apache Hadoop，Apache Sparkなど）は複数の資源で処理を分担する基盤です。分散ファイルシステム（HDFS（Hadoop Distributed File System），Ceph，GlusterFSなど）はデータの分散保存、大規模データセットのクエリエンジン（Apache Hive，Prestoなど）は問合せ処理の位置にあります。製品の版や性能値はここでは比較しません。

ブロックチェーンにおけるデータベース関連技術（コンセンサスアルゴリズム，ファイナリティ など）は、記録の合意・確定を考える技術です。小売の統合DBの要件と同じとは限らず、採用目的を先に確かめます。

試験では：処理の分散と、複製後の一致、障害時の更新を分けます。混同注意：結果整合性を「不整合を放置してよい」と読むことです。

判断の練習：翌朝の販売レポートは遅延を許せますが、最後の一個の販売確定は重複を許せません。全て同じ複製方針にしますか。

答え：要件を分けます。集計の許容遅延と在庫確定の制約を明文化し、通信断・競合時に何を止めるかも決めます。共通技術の整理は前掲のPD-S第4章で補えます。

## アルゴリズムとプログラミングを処理条件から選ぶ

入力条件と操作から選ぶ技能4-2・4-3を練習します。式の導出や実装は20時間の外で続けます。

### 数値計算を前処理の条件として読む

店舗別・商品別の売上を分析へ渡します。行列は行と列に値を並べた表現、転置行列は行列の入替え、線形代数はその計算の基礎です。行・列の意味、単位、欠測を先にそろえます。

固有値・固有ベクトルは変換の方向と大きさ、単位行列は元を保つ変換、逆行列・掃出法は連立方程式等に関わる語です。近似解法・数値解析は数値による近似、二分法・ニュートン法は解の探索、補間法は点の間の推定、数値積分・シンプソン法は面積等の近似、オイラー法は微分方程式の近似に位置づけます。

試験では：計算に必要な入力条件を読みます。混同注意：数式の二分法と整列済みデータの2分探索法です。

判断の練習：商品列の並びが店舗ごとに違うまま平均を取りました。何を直しますか。

答え：商品と列の対応、単位、欠測を統一します。計算できることと正しく比較できることは別です。

### 入力の条件と計算量を確認する

毎晩増える販売記録を照合します。計算量（オーダ記法）は入力増加に対する仕事の増え方で、実測の秒数ではありません。全行の全組合せの比較は件数とともに急増します。

符号理論は情報表現や誤り、述語論理（演繹推論，帰納推論）は条件と推論、形式言語・オートマトンは入力構造と状態を扱う基礎です。形式と業務上の妥当性を別に検査します。

試験では：件数増加の負担と検査を選びます。混同注意：文法が正しければ品質もよいとする判断です。

判断の練習：JSONとして読めても数量が負、商品が未登録です。分析へ渡しますか。

答え：渡しません。型・範囲・参照先・重複を検査し、不合格理由を残します。

### 処理順と検索条件でデータ構造を選ぶ

店舗から届くファイルを到着順に処理する場合と、直前の操作を取り消す場合を比べます。スタックとキューは、後入れ先出しと先入れ先出しの違いで用途を判断します。

商品コード検索ならハッシュ表が候補ですが、格納先の衝突やキーなしの処理も必要です。

多次元配列は店舗×日付等の表現、静的配列・動的配列はサイズ、リスト（環状リスト，連結リスト）は要素のつながりで比較します。連結リストの任意位置へのアクセスは配列と異なります。

木構造（順序木，多分木，探索木）は階層や検索、グラフは複数の対象間の関係を表す構造として位置づけます。商品の分類階層と配送拠点間の道路では、必要な関係の表現が異なります。

試験では：到着順、取消し、キー検索、階層などの条件を構造へ対応させます。混同注意：格納できるというだけで頻繁な操作の費用を無視することです。

判断の練習：ファイルを到着順に取り出したいのに、配列の末尾へ追加し末尾から取り出しています。どの性質になりますか。

答え：後入れ先出しになり、スタックに相当します。到着順ならキューの性質が必要です。空の場合と一件の場合も確かめます。

### 整列の費用も含めて探索を選ぶ

一度だけ届いた未整列の一覧から、指定商品を探します。線形探索法は順に調べ、2分探索法は整列済みの範囲を半分ずつ絞ります。導入問Bは「必ずとは言えない」が答えです。

探索前の整列費用、検索回数、更新頻度、整列状態を保つ費用まで比較します。

整列のアルゴリズムは並び順を作り、併合のアルゴリズムは複数の列などをまとめます。探索のアルゴリズムは対象を探す処理で、再帰は自分と同じ形の処理を小さな問題へ適用する記述、分割統治は問題を分けて解を組み合わせる考え方です。

試験では：手法の前提と一連の処理全体を見ます。混同注意：2分探索法へ渡す前の整列条件や、重複した値がある場合の仕様を省くことです。

判断の練習：商品の価格が同額の場合、元の登録順を保つ必要があります。速いという理由だけで整列手法を決められますか。

答え：決められません。同じ値の順序を保つ性質も条件に含め、データ量、メモリ、更新方法で比較します。トレースの反復は[FEアルゴリズムの学び方](/method/fe-algorithm-roadmap/)で続けられます。

### 文字列とファイルの処理を分ける

商品名に指定語を含む記録を探し、複数ファイルをまとめます。ファイル処理のアルゴリズムでは、全件をメモリへ載せるか、一部ずつ読むか、途中失敗からどう再開するかを考えます。

KMP法（クヌース・モリス・プラット法）とBM法（ボイヤ・ムーア法）は文字列探索の方法です。字面の一致を探すことと、文章の意味が近い記録を探すことを区別します。

自然言語処理のアルゴリズム（形態素解析，構文解析，意味解析，文脈解析，係り受け解析，n-gram，文章間類似度）は、文章を分けたり関係や類似を扱ったりする技術に位置づけます。データ圧縮のアルゴリズムは表現量を減らす処理で、比較前の文字正規化とは別です。

近似アルゴリズムは厳密な最適解に対して近い解を求める方法、確率アルゴリズムは乱数などを使う方法です。どちらも「誤ったデータを放置してよい」という意味にはしません。

試験では：文字一致、意味の類似、入出力の負担を分けます。混同注意：商品名の類似だけで同一商品を確定してしまうことです。

判断の練習：似た名前の二商品を自動で同一商品へ統合する案です。文字列探索ができれば確定できますか。

答え：できません。商品コード、規格、容量などの照合条件が必要です。疑わしい組は候補として出し、判断根拠を残して確認へ回します。

### 経路と接続の最適化を区別する

倉庫から店舗への配送経路を選ぶ場合と、全拠点を安く結ぶ回線を選ぶ場合を比べます。ダイクストラ法は辺の重みが非負のときの最短経路、最小全域木（MST）は全頂点をつなぐ木の重みの合計を最小にする問題です。

全拠点の接続費用が最小でも、各店舗への経路は最短とは限りません。何を最小にするかを読みます。

ベルマン・フォード法は負の重みを含む最短経路の検討、ワーシャル・フロイド法は全頂点対の最短経路、クラスカル法とプリム法は最小全域木を求める方法として位置づけます。負の閉路が関わる場合などは成立条件を別に確認します。

最大フロー問題は、辺などの容量制約の下で流せる量を考える問題です。道路の距離と、一日に運べる量は異なる条件なので、最短経路の計算だけでは処理能力を決められません。

試験では：距離、接続費用、容量のどれを最適化するかを選びます。混同注意：ダイクストラ法を負の重みも含む全条件で使えるとする説明です。

判断の練習：全店舗をネットワークへつなぐ総費用を小さくしたい場合、まず最短経路問題と最小全域木のどちらを考えますか。

答え：最小全域木です。ただし、障害時の代替経路が必要なら、木だけでは冗長性が足りない点も要件へ戻って確認します。

### 変換処理を分けて検証する

店舗ごとに異なる売上ファイルを共通形式へ変換します。モジュール分割は処理を責務ごとに分けること、独立性は変更が他へ波及しにくい関係、データ型は値の表し方と操作の条件です。

CSVは区切り形式の表、JSONは入れ子等を表現する形式、XMLは要素と属性、YAMLは設定等にも使われる記述形式として位置づけます。拡張子だけで、文字コード・日付・桁・未設定値の意味が統一されるわけではありません。

取込み、型変換、照合、検査、格納を分け、値が変わる段階を追えるようにします。丸め方の不一致も合計の差を生みます。

オーバーライドは継承先での動作の再定義、オーバーロードは同名で引数等が異なる定義として位置づけます。データ分析・AI（Python，Rなど）と科学技術計算（Fortran，Juliaなど）は用途の例で、言語の名前だけで品質が保証されるわけではありません。

試験では：変換の責任と入出力、異常値の検証を対応させます。混同注意：正常な一件が通っただけで全入力を検証したとすることです。

判断の練習：商品コード「0012」が数値12へ変わり、別システムのコードと一致しなくなりました。何を修正しますか。

答え：識別子を文字列として扱う型と変換仕様を定め、先頭ゼロ・空欄・重複・未登録・桁超過を検証します。元データ、変換ルール、結果件数も対応させます。
