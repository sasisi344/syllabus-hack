## データ基盤と業務分析

### 保存と提供の役割を分ける

小売会社が注文、店舗ログ、画像をまとめて分析したい場面です。データレイクは多様な形式のデータを蓄積する場所、データウェアハウス（DWH）は分析向けに統合・整備したデータを提供する基盤です。

データマートは、部門や目的に合わせた利用範囲のデータを用意するものです。基礎は[DM第3章](/course/dm/03-data-platform-tools/)で確認し、ここではどの段階で意味と品質を確かめるかを考えます。

レイクハウスは、データレイクとDWHの特徴を組み合わせる構成の考え方として位置づけます。名前を選んだだけで、利用条件、品質、カタログ、更新責任まで自動的に決まるわけではありません。

導入問Bの答えはイです。未加工のデータを残す役割と、共通の売上定義で提供する役割を分けます。

<MermaidDiagram client:load chart={`flowchart LR
 A[注文・ログなどの収集元] --> B[受入れと検査]
 B --> C[未加工データの蓄積]
 C --> D[統一・加工・品質確認]
 D --> E[分析向けDWH]
 E --> F[目的別マート・BI]
 B --> G[不適合データの隔離と通知]
 D --> G
`} caption="データ基盤の一例。各段階で定義・件数・品質と利用条件を引き継ぐ" />

試験では、保存できることと分析に使えることを取り違えません。DWHへ入れたという事実だけで元データの誤りが消えるわけでもありません。

判断の練習：画像ログを保管できる基盤を導入したが、経営の売上報告が一致しない。保存先だけを増強すべきでしょうか。

答え：まず売上の定義、元データ、粒度と変換を確認します。保存容量と、分析用の意味・品質を整える処理は別の課題です。

### 加工と問合せの場所を選ぶ

分析者が毎回、税や返品の処理を別々に行っている場面です。ETL/ELTは、抽出・変換・格納のどこで変換するかを示します。ETLは格納前、ELTは格納後に主な変換を行います。

スキーマオンライトは書込み時に構造へ合わせ、スキーマオンリードは読み出す際に構造を解釈する考え方です。後者でも、利用時の定義・品質確認がなくなるわけではありません。

スタースキーマは、出来事の数値を持つ中心の表と、商品・日付などの分析軸の表を結ぶ形です。スノーフレークスキーマは分析軸側をさらに分割する形として、参照の単純さと冗長性・保守の負担を比較します。

データ仮想化は、複数の所在を利用者から統合的に扱う仕組み、フェデレーションクエリは複数のデータ源にまたがる問合せとして位置づけます。コピーを減らせても、接続元の性能や停止の影響を受ける場合があります。

OLAP（オンライン分析処理）は集計・多次元分析、HTAP（Hybrid Transactional/Analytical Processing）は取引と分析を合わせて扱う処理の考え方です。MPP（大規模並列処理）は処理を分散して並列化する方式として認識します。

ストレージとコンピュートの分離は、保存と計算の資源を分けて調整する考え方です。データコネクタはデータ源への接続、データファブリックは分散したデータを横断的に扱う統合・管理の考え方として位置づけます。

試験では、コピーがないことを常に最適と取り違えません。問合せの負荷と複製の鮮度を比較します。

判断の練習：大きな分析クエリで受注処理が遅くなる。常に元の業務表へ直接問い合わせる方式を続けてよいでしょうか。

答え：要求される鮮度と負荷を整理し、分析用の複製や資源の分離を比較します。最新性だけを優先して取引の継続性を損なわないようにします。

### 到着と更新を分けて設計する

注文は順次届きますが、通信切断で遅れた記録もあります。バッチ処理／ストリーム処理は、一定のまとまりで処理するか、流れてくるデータを継続的に処理するかの違いです。

変更データキャプチャ（CDC）は、元システムの変更を捉えて連携する方式です。全件を取り直す方法とは異なりますが、初期データ、更新順序、削除の反映などの設計は残ります。

ウィンドウ処理は、流れるデータを時間などの範囲で区切って計算します。発生時刻で集計するのか、基盤へ到着した時刻で集計するのかを決め、遅れて届く記録をどう扱うかも定めます。

配信保証は、データがどのように届けられるかの性質です。少なくとも一回の配信を保証する方式でも、受信後の再実行で同じ注文を二度加算する可能性があるため、業務上の重複対策が必要です。

| 要求 | 設計で確かめること |
|---|---|
| 翌朝の確定値でよい | 締切り、欠落の検知、再取込みの余裕 |
| 数分の変化を追いたい | 到着遅延、処理能力、ウィンドウの扱い |
| 元の更新だけを反映したい | CDCの初期状態、更新・削除の整合 |
| 遅着を後から反映したい | 確定時点、訂正値の再配布、利用者への通知 |

試験では、ストリーム処理なら遅延が一切なく、常に完全な確定値を出せると取り違えません。

判断の練習：店舗で発生した注文が翌日に届くことがある。到着日の売上として集計すると、店舗の営業日別の実績に使えるでしょうか。

答え：そのままでは目的に合わない可能性があります。発生時刻と到着時刻を区別し、営業日の定義、遅着の反映、報告の確定条件を決めます。

### 再実行しても結果を壊さない

受信した注文を保存した直後に応答が途切れ、送信元が同じ注文を再送しました。べき等性は、同じ操作を繰り返しても結果が変わらない性質です。

導入問Aの答えはアです。注文を識別し、反映済みなら二重に加算しないようにします。新しい行番号を毎回付けるだけでは、同じ注文だと判定できません。

リトライは失敗した処理を再試行することです。バックフィルは、欠けた過去の期間などを後から埋める処理です。二つとも、対象範囲と反映済みの結果を確認してから実施します。

<MermaidDiagram client:load chart={`flowchart TB
 A[処理失敗を検知] --> B[反映済みの範囲を確認]
 B --> C[対象の識別子・期間を指定]
 C --> D[べき等な反映で再実行]
 D --> E[件数・金額・欠落・重複を確認]
 E --> F{整合しているか}
 F -->|はい| G[下流処理を再開・結果を通知]
 F -->|いいえ| H[配布を保留し原因を調査]
`} caption="リトライ・バックフィルの例。再実行の成功後も整合確認が必要" />

ワークフロー制御は、処理の依存関係に従って実行や再開を調整します。顧客マスターの取込みが終わる前に注文を結合すると、未登録の顧客が欠落する可能性があります。

試験では、配信側の保証と、受信側の反映の一意性を同じものと取り違えません。「もう一度流せば直る」でなく、同じ対象をどう識別するかを読みます。

判断の練習：三日分を再取込みしたいが、そのうち一日は正常に反映済みだった。全件を無条件で追記してよいでしょうか。

答え：いけません。対象期間と識別子を決め、置換や反映済み判定などで重複を防ぎます。再実行後は件数と金額、下流への影響も確認します。

### 受入れと履歴を管理する

海外拠点から届いた表で、金額の単位と日付の解釈が国内と違っていたとします。データ受入れ検査は、入ってきたデータが決めた仕様・品質に合うか確かめる工程です。

コード・単位・日時の統一は、比較や結合に先立って意味をそろえる処理です。数値だけを合わせても通貨が違えば比較できず、時差を無視すれば日別件数がずれます。

突合による欠落・重複の検知では、送信側と受信側で件数や合計などを照らします。件数が合っていても、一行の欠落と別の一行の重複が相殺する場合があるため、識別子や金額も目的に応じて確認します。

取込み単位は、ファイル、日付、注文など、成功・失敗を管理するまとまりです。どこまで受け入れたかを記録し、エラー行の隔離と正常分の提供を認めるかも仕様で決めます。

履歴管理では、スナップショットで時点の状態を残す方法や、緩やかに変化するディメンションで属性の変化を扱う方法があります。現在の商品分類で過去を見たいか、当時の分類を再現したいかで設計が変わります。

スキーマエボリューションはデータ構造の変化への対応です。列の追加だけでなく型・意味・必須条件の変更を捉え、下流の処理やカタログへ反映します。

試験では、正常な受信と、仕様どおりのデータの受入れを取り違えません。

判断の練習：提供元が金額の単位を円から千円に変えたが、列名は同じだった。型の検査だけで検出できるでしょうか。

答え：できるとは限りません。単位と意味を含む仕様変更の連絡、値の範囲や合計の確認、受入れ検査の更新が必要です。列の型が同じことは意味の同一性を保証しません。

### 業務の意味をBIへ渡す

同じBI画面で、売上を別々の担当者が違う式で計算している場面です。セマンティックレイヤーは、業務の指標や意味を共通に扱うための層です。

オントロジーは対象となる概念と関係を整理する枠組み、ナレッジグラフは実体と関係をグラフで表す仕組みとして位置づけます。意味をそろえる設計と、表を一か所へ置く設計を分けます。

SoIとしてのBIツール活用は、データを集計・可視化し、洞察と意思決定につなぐ使い方です。

多次元分析では、ドリルダウンで細かく、ドリルアップで粗く見ます。スライスはある軸の値で切り、ダイスは複数の条件で範囲を絞り、ドリルスルーは元の明細などへ進む操作です。

データブレンディングは分析に使うデータを組み合わせ、データプレパレーションは分析前に整える作業として認識します。基礎の操作はDM第3章で補い、ここでは粒度と結合条件を優先します。

試験では、きれいなグラフを作れば意味の統一も済むと取り違えません。自動更新する画面ほど、指標の定義変更と利用条件をどこへ反映するかを決めます。

判断の練習：店舗の売上を月別から日別へ見たい場合と、ある日の注文一件まで確かめたい場合は、どの操作を区別するべきでしょう。

答え：前者はドリルダウン、後者は明細へ進むドリルスルーです。軸の詳細化と個々の記録への移動を分け、明細を見る権限も確認します。

### 業務の制約からモデルを選ぶ

工場が材料と作業時間に上限のある中で生産量を決めたいとします。線形計画法は、目的と制約を線形の式で表して最適化する方法です。

モンテカルロ法は、確率的な変動を乱数による試行で扱う方法です。確定モデルと確率モデルは、入力や変化を確定した条件で扱うか、不確実性を含めて扱うかという違いです。

| 解きたいこと | 方法の位置づけ |
|---|---|
| 材料の制約内で利益を最大にしたい | 線形計画法で表せる条件か確認 |
| 他社の選択も結果へ影響する | ゲーム理論で相互作用を考える |
| 作業の時間配分を知りたい | IE分析手法（ワークサンプリング法など） |
| 不良の分布や原因を整理したい | QC七つ道具、言語的な課題の整理には新QC七つ道具 |
| 専門家の判断を段階的に集めたい | デルファイ法 |
| 需要変動による損失の幅を知りたい | モンテカルロ法で条件を変えて試行 |

基礎の業務分析は[DM第4章](/course/dm/04-statistics-analysis/)で補えます。

試験では、過去の関係を予測することと、制約の下で行動を選ぶ最適化を取り違えません。

判断の練習：生産案の利益は最大だが、夜間に稼働できない設備を終日使う計算になっていた。計算結果をそのまま採用してよいでしょうか。

答え：いけません。設備の利用可能時間という制約を追加して比較し直します。

## クラウド

クラウドの共通語は[PD-S第2章](/course/pd-s/02-system-architecture-cloud/)で復習できます。ここでは中分類15を、分析基盤の責任・継続性・費用を決める材料として短く扱います。

### 責任範囲と停止範囲を確認する

運用を任せる基盤でも、売上の定義や閲覧権限の検討は利用側に残ります。共有責任モデルは、事業者と利用者の責任範囲を分ける考え方です。

クラウドサービス（XaaS）は、パブリッククラウド、プライベートクラウド、コミュニティクラウド、ハイブリッドクラウドなどの利用形態で区別します。アンマネージドモデル、マネージドモデル、フルマネージドモデルは運用の関与度の違いとして、詳細はPD-S第2章で確認します。

リージョンは地理的な単位、アベイラビリティゾーン（AZ）はその中の設備群です。マルチAZ構成、マルチリージョン構成は備える障害範囲で選び、利用者に近いエッジロケーションや、地域間の複製であるクロスリージョンレプリケーション（CRR）と区別します。

クラウドによるディザスタリカバリ（DR）では、RTOは復旧時間、RPOは戻すデータの時点、RLOは復旧する機能の範囲・水準の目標です。技能3-4では基盤の起動だけでなく、パイプラインの整合と提供の再開条件へ結び付けます。

試験では、複製と過去への復元を取り違えません。誤更新も複製されるなら、複製先があるだけで正しい過去の状態へ戻れるとは限りません。

判断の練習：別リージョンへ切り替わったが、顧客表と注文表の反映時点が異なっていた。起動だけで復旧完了としてよいでしょうか。

答え：いけません。要求する復旧時点とデータ間の整合を確認し、必要な再処理と品質確認を行ってから提供を再開します。

### 費用と移行の条件を絞る

月末だけ計算量が増える分析で、常時最大の資源を確保すると費用が膨らみます。ライトサイジングは資源の適正化、FinOpsは費用と価値の継続的な管理です。

従量課金、リザーブド利用（RI）、スポット型利用は、利用の安定性と中断の許容条件で比較します。ストレージ階層化はホットバケット、ウォームバケット、コールドバケットなど利用頻度で配置を変え、タグベースのコスト配分とコストの可視化で処理や部門ごとの費用を追います。

クラウドポータビリティは移しやすさ、クラウド移行アセスメントは現状評価です。移行の戦略的なアプローチであるRehost、Replatform、Refactor、Retain、Retireを比較し、モダナイゼーションの範囲を決めます。

ランディングゾーンは共通の管理・ネットワークなどの土台、IaC（Infrastructure as Code）は構成、Policy as Code（PaC）はルールをコードで扱う考え方です。

サーバ仮想化、ネットワーク仮想化、ストレージ仮想化は資源を論理的に扱う技術です。コンテナイメージは実行環境のまとまり、コンテナレジストリはその保管先、コンテナネットワークは実行単位間の通信として、Xen、KVM、Ceph、Docker、Kubernetes、OpenStackなどのOSSと合わせてPD-S第2章で補います。

試験では、計算費用だけの削減を全体最適と取り違えません。再取込み、転送、保管、復旧も含めて要求品質と比較します。

判断の練習：中断してもやり直せる夜間分析を低費用の方式へ移したい。価格だけで決めてよいでしょうか。

答え：いけません。中断時の再実行、べき等性、締切り、転送・保管費用を確認し、総費用と要求品質を比較します。
