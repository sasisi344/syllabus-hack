## この章で学ぶこと

「企画書を作って」とAIに頼むと、それらしい文章が長々と返ってきます。
ところが読んでみると、一般論ばかりで、自分の職場の話になっていない。数字は根拠がない。こうした経験をした人は多いはずです。

大きな成果物は、一度に作らせるほど失敗します。
この章では、資料づくりを題材に、次の3つを練習します。

- <strong>構成を先に決め、段階的に作る</strong>（アウトライン → 本文の順）
- 根拠のない数字・事例をAIに作らせない制約の書き方
- 読み手が違うとき、同じ内容を書き分ける依頼の組み立て方

第1章の5要素（目的・入力・制約・出力形式・検証）は、この章でも使います。
素材はすべて架空のデータです。実務で使うときは、社外秘の情報を伏せてから貼ってください。
本コースは実務練習用の教材です。AIの出力は必ず人が検証してください。

## このユースケースが起きる場面

社内勉強会の提案、新しいツールの導入検討、部署の改善案。
資料づくりは、書く前に「何を決めてもらう資料か」が曖昧だと、後で必ず手戻りします。

AIを使うと、次のような失敗が起きます。

- 目的が決まっていないので、どの読み手にも刺さらない一般論になる
- 「参加率80%」「コスト30%削減」のような、根拠のない数字が入る
- 全体を一度に作らせるので、途中の修正が難しくなる

これらは、AIの性能ではなく、<strong>依頼の分け方</strong>で防げます。

## プロンプト設計シート（再掲）

```
**目的**：誰に・何のために・何を作るか
**入力**：AIに渡す素材は何か（機密は伏せたか）
**制約**：やってはいけないこと・守るルール
**出力形式**：表・箇条書き・文字数など
**検証**：出力が正しいか、何と突き合わせるか
```

この章では、さらに次の考え方を加えます。

<strong>大きな成果物は、「構成案 → 人が確認 → 本文」の2段階に分けて依頼する。</strong>
構成の段階で方向がずれていれば、そこで直せます。本文まで作った後の修正よりも、はるかに安く済みます。

## 実例：社内勉強会の提案書を作る

### 状況と素材

あなたは、部署で「月1回の社内勉強会」を始めたいと考えています。
部長に提案する資料を作ります。手元にあるのは、次のメモです。

```
【提案メモ】
- 目的：部署内で知識を共有し、担当者が変わっても業務が回るようにしたい
- 対象：営業部の全員（約20名）
- 頻度：月1回、昼休み後の45分
- 内容のイメージ：各回、担当者が事例や学びを15分話し、残りを質疑にする
- 費用：会議室を使うので、ほぼゼロ。資料づくりの時間は各自の業務時間内
- 懸念：忙しくて参加できない人が出るかもしれない
- 部長に決めてほしいこと：まず3か月、試行として実施してよいか
```

### 悪い指示とその失敗

```
社内勉強会の提案書を作って。
```

返ってくるのは、次のような文章です。

> 社内勉強会は、社員のスキルアップと組織の活性化に大きく貢献します。導入企業では平均して業務効率が30%向上したという報告もあります。参加率は80%が見込まれ、費用対効果は非常に高いと考えられます。

失敗が3つあります。

- 「30%向上」「参加率80%」という、メモにない根拠のない数字が作られている
- 「部署内で知識を共有し、担当者が変わっても回るように」という、提案の固有の目的が消えている
- 「部長に決めてほしいこと」が、どこにも書かれていない

### 改善したプロンプト（1段階目：構成案）

```
あなたは社内提案書の作成を支援する担当です。以下の「提案メモ」から、部長に提出する提案書の構成案（アウトライン）を作成してください。この段階では本文は書かず、構成のみを出力します。

**目的**
部長が「まず3か月、試行として実施してよいか」を判断できる提案書にする。

**制約**
- 「提案メモ」にない数字・事例・他社の実績を書かない。数字が必要な箇所は「【要確認：〇〇】」と書く
- 冒頭に「部長に決めてほしいこと」を置く
- 「懸念」と、その対策（メモにない場合は「対策案：要検討」）を含める

**出力形式**
見出し（大項目）ごとに、その節で書く内容を1行で添える。全体で6〜8項目。

**提案メモ**
（ここにメモを貼る）
```

### AIの出力（構成案）と、人が確認した点

> 1. 決めていただきたいこと（まず3か月の試行実施の可否）
> 2. 背景と目的（担当者が変わっても業務が回る体制づくり）
> 3. 提案内容（対象・頻度・進め方）
> 4. 費用と工数（会議室利用。準備は業務時間内）
> 5. 期待する効果【要確認：効果の測り方】
> 6. 懸念と対策（参加できない人への対応：対策案は要検討）
> 7. 3か月後の判断基準【要確認：継続の基準】

人が確認する点は、次のとおりです。

- 「期待する効果」の測り方が「要確認」になっている。メモに根拠がないので、自分で考えるか、参加者アンケートなどの案を決める
- 「懸念と対策」の対策が空欄なので、たとえば「録画の共有」など、自分で案を出す
- 構成の順序が、部長の判断の流れに沿っているか

構成案を確認したら、2段階目で本文を作ります。

```
上の構成案の「6. 懸念と対策」について、次の内容で本文を書いてください。

**追加の情報**
対策案：勉強会の資料と要点を、社内の共有フォルダに掲載する（参加できなかった人も後から確認できる）

**制約**
- 追加の情報にない対策を、新しく作らない
- 200字以内
```

このように、節ごとに本文を作れば、修正も節単位で済みます。

### 設計メモ：なぜこの書き方か

| 要素 | 実例での書き方 | 効いた理由 |
| --- | --- | --- |
| 目的 | 「部長が判断できる提案書」 | 読み手と、読んだ後の行動が決まる |
| 入力 | 提案メモ（素材） | 書く内容が素材から外れない |
| 制約 | 「数字・事例を作らない」「要確認と書く」 | 根拠のない数字の混入を防ぎ、人が埋める箇所を可視化した |
| 出力形式 | 構成案のみ（本文は書かない） | 方向のずれを、早い段階で見つけられる |
| 検証 | 「要確認」の箇所を人が埋める | AIの穴と、人の判断が必要な点が一目で分かる |

<strong>「分からないことは、分からないと書け（要確認と書け）」</strong>という指示は、資料づくり全般で使えます。
AIは、空欄を埋めたがります。空欄のまま残す指示を、意識して入れてください。

## 練習問題

進め方は全問共通です。

1. 素材を読み、プロンプト設計シートの5要素を自分で埋める（AIはまだ使わない）
2. 埋めた内容をもとにプロンプトを書き、普段使うAIで実行する
3. 出力をルーブリックで自己採点する
4. 解説を開き、自分の設計と比べる

### 問1 要件メモから、構成案を作る

<strong>状況</strong>：営業部で、顧客リストの管理ルールを見直す提案をします。提出先は課長です。

<strong>成果物</strong>：提案書の構成案（大項目6〜8個、各項目に1行の説明）。

```
【要件メモ】
- 現状：顧客リストが、担当者ごとのExcelに分散している。更新のタイミングもバラバラ
- 困りごと：担当者が休むと、顧客の履歴が分からない。二重連絡も起きた
- 案：共有のスプレッドシートを1つ作り、全員が同じ列構成で入力する
- 期間：来月から試行運用（1か月）
- 課長に決めてほしいこと：共有スプレッドシートへの移行を、来月から試行してよいか
- 未確認：入力ルール（誰がいつ更新するか）は、まだ決まっていない
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 冒頭の項目が「課長に決めてほしいこと」になっている
- [ ] 現状の困りごと（分散、二重連絡）が構成に含まれている
- [ ] 「入力ルールが未決定」という点が、「要確認」として扱われている（AIが勝手に決めていない）
- [ ] メモにない数字・他社事例が含まれていない
- [ ] 本文ではなく、構成のみが出力されている

</details>

<details>
<summary>よくある失敗と解説</summary>

「構成案を作って」という依頼で、AIが本文まで書き始めることがあります。
出力形式に「この段階では本文を書かない」と明記してください。

もう一つのポイントは、メモの<strong>「未確認」の扱い</strong>です。
AIは、入力ルールを「毎週金曜に更新する」のように、それらしく決めてしまいがちです。
制約に、「メモで未確定の事項は、決めずに『要確認』と書く」と入れます。

</details>

### 問2 比較表を作る（評価軸を自分で決める）

<strong>状況</strong>：部署でチャットツールの導入を検討しています。3つの候補を比べる表を作ります。

<strong>成果物</strong>：比較表（評価軸は3〜5個。素材にない項目は「記載なし」）と、結論を1文。

```
ツールA：月額1,200円/ユーザー。チャットとファイル共有。モバイルアプリあり。日本語サポートはメールのみ。
ツールB：月額800円/ユーザー。チャットとビデオ会議。モバイルアプリあり。サポートについての記載なし。
ツールC：月額1,500円/ユーザー。チャット・ファイル共有・ビデオ会議。モバイルアプリの有無は記載なし。日本語サポートは電話とメール。
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 評価軸（料金・機能・モバイル・サポートなど）が、素材の情報から選ばれている
- [ ] 素材にない項目（Bのサポート、Cのモバイル）が「記載なし」になっている。AIが推測で埋めていない
- [ ] 料金の数字が、素材と一致している
- [ ] 結論の1文が、比較表の根拠から導かれている（素材にない理由を追加していない）
- [ ] 評価軸を自分で決めた理由を、設計シートに書いた

</details>

<details>
<summary>よくある失敗と解説</summary>

比較表で最も多い失敗は、<strong>「記載なし」を、AIが推測で埋めてしまう</strong>ことです。
「Bのサポートは、おそらくメールです」のように、それらしく補います。

制約に「素材に書かれていない項目は『記載なし』と書く。推測で埋めない」と入れます。
また、結論の文には、「どの評価軸を重視するか」で結論が変わることを一言添えさせると、判断の材料になります。

評価軸をAIに決めさせる場合は、「軸の候補を5つ挙げ、それぞれ、素材から判断できるかを示して」と頼む方法もあります。
判断できない軸は、比較表に入れないのが安全です。

</details>

### 問3 手順の説明を、図（Mermaid）にする

<strong>状況</strong>：経費精算の流れを、新人向けの資料にします。文章の説明を、フローチャートにします。

<strong>成果物</strong>：Mermaid記法のフローチャート。

```
【経費精算の流れ】
申請者が、経費精算システムで申請する。
上長が内容を確認して、承認する。差し戻す場合は、申請者が修正して再申請する。
金額が10万円を超える場合は、さらに部長が承認する。
承認後、経理が内容を確認して、支払いを行う。
```

Mermaidは、テキストで図を書く記法です。次のような形をしています。

```
flowchart TD
    A[申請] --> B{上長の承認}
    B -->|承認| C[経理の確認]
    B -->|差し戻し| A
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 「10万円を超えるか」の分岐が、図の中にある
- [ ] 「差し戻し → 修正して再申請」の矢印がある
- [ ] 文章にない工程（例：領収書の提出、システム入力）が追加されていない
- [ ] Mermaid記法に対応したツールや、ブラウザで、実際に図が表示されることを確認した
- [ ] プロンプトに、出力形式（Mermaid記法のflowchart）と、図の向きを指定した

</details>

<details>
<summary>よくある失敗と解説</summary>

図の依頼で注意する点は2つです。

1つ目は、<strong>図を出力する形式をはっきり指定する</strong>こと。
「図にして」だけでは、文章の箇条書きが返ってくることがあります。
「Mermaid記法のflowchart TDで、コードのみを出力して」のように書きます。

2つ目は、<strong>出力したコードを、実際に表示して確認する</strong>こと。
記法の誤りで表示されないことがあります。その場合は、エラーメッセージをそのままAIに渡し、修正を依頼します。

図は、文章では見落とす「分岐の抜け」を見つけるのにも役立ちます。
図にしてみて、「10万円以下の場合の流れが抜けている」と気づくこともあります。

</details>

Mermaid記法は、AIと組み合わせると、手書きのメモや文章の説明から、図を素早く作れます。
さらに学びたい方は、次の記事も参考にしてください。

### 問4 同じ内容を、読み手に合わせて書き分ける

<strong>状況</strong>：問1で作った提案の内容を、役員会にも報告することになりました。課長向けの詳細な提案書とは別に、役員向けの1枚要約が必要です。

<strong>成果物</strong>：役員向けの1枚要約（5行以内）。

```
【提案の概要（課長向けの内容）】
- 現状：顧客リストが担当者ごとのExcelに分散し、更新も不揃い。担当者が休むと履歴が分からず、二重連絡が発生した
- 提案：共有のスプレッドシートを1つ作り、全員が同じ列構成で入力する
- 実施：来月から1か月の試行運用
- 入力ルール：誰がいつ更新するかは、未決定
- 費用：既存のスプレッドシートを利用するため、追加費用なし
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 5行以内に収まっている
- [ ] 冒頭に「何を決めてほしいか／何を報告するか」がある
- [ ] 専門用語やExcel運用の細かい説明が省かれている
- [ ] 「入力ルールが未決定」という点が、隠されずに書かれている（試行の中で決める、などの扱いでもよい）
- [ ] 課長向けの内容にない事実・数字が追加されていない

</details>

<details>
<summary>よくある失敗と解説</summary>

読み手が変わると、必要な情報が変わります。
課長は「どう運用するか」を知りたく、役員は「何をして、いくらかかり、何が起きるのか」を知りたい。

プロンプトには、<strong>読み手の立場と、その人が知りたいこと</strong>を明記します。
「役員向け。専門用語は使わず、判断に必要な情報のみ」のように書きます。

注意したいのは、「短くしろ」と言われたAIが、<strong>都合の悪い情報（未決定の点）を削ってしまう</strong>ことです。
未決定の事項は、隠さず残す制約を入れてください。
「要約しても、未決定の事項は省かない」の一文が、役員への正直な報告になります。

</details>

## 繰り返し使う制約は、AIに登録して短くする

この章のプロンプトは、制約を毎回書き込む形で練習しました。
同じ業務を繰り返すなら、<strong>変わらない制約は、AIにあらかじめ登録しておく</strong>ことで、依頼を短くできます。

この章で登録しておくとよいのは、「素材にない数字・事例は書かず、要確認と書く」という制約と、構成案から本文へ進める2段階の進め方です。
ChatGPT・Claude・Geminiでの登録手順は、[生成AIに社内ルールを覚えさせるスキル設定のやり方](/method/ai-skill-rules-setup/)で解説しています。
登録しても、最終確認は人が行うことに変わりはありません。

## 自分の職場に置き換える

この章の型を、自分の仕事に当てはめます。

1. 提案したいこと（またはこれから作る資料）を1つ選ぶ
2. 実際の数字や固有名詞は伏せる。使わない場合は、架空の提案を作る
3. 「決めてほしいこと」を1文で書き、その資料の目的にする
4. 構成案だけをAIに作らせ、「要確認」の箇所を自分で埋めてから、本文を節ごとに作る

仕上げに、S.E.L.F.ループの「F（Forge it）」として、<strong>完成した資料の要点を、AIに向かって口頭で説明するつもりで書き出し</strong>、説明できない箇所（＝まだ理解が浅い点）を確認します。

## この章のまとめ

- 大きな成果物は、「構成案 → 人が確認 → 本文」の順に、段階を分けて依頼する
- 根拠のない数字・事例は、「素材にない数字は書かず、『要確認』と書く」で防ぐ
- 「記載なし」は「記載なし」のままにする。AIは推測で埋めたがる
- 図は、出力形式（Mermaidなど）を指定し、実際に表示して確認する
- 読み手を明記して書き分ける。短くするときも、未決定の点は省かない

次の章では、調査・情報収集とファクトチェックを題材に、AIが「もっともらしい嘘」をつくときの対処を練習します。
