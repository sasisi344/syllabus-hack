## この章で学ぶこと

ここまでの7章で、個々の場面でAIを使う型を練習しました。
最終章では、それを<strong>「毎回、自分の思いつきで頼む」から「誰がやっても、一定の品質で回る仕組み」に変える</strong>練習をします。

扱う力は、次の4つです。

- 繰り返しの業務を、工程に分け、AIが担う部分と人が判断する部分を分ける
- 毎回使えるように、プロンプトをテンプレートにする
- AIの出力を、別のAIに採点させる（ただし、限界を理解する）
- 職場のAI利用のルール（ガイド）を作る

第1章の5要素（目的・入力・制約・出力形式・検証）は、この章でも土台になります。
素材はすべて架空のものです。
本コースは実務練習用の教材です。AIの出力は必ず人が検証してください。

## このユースケースが起きる場面

毎週の報告書づくり、定型の問い合わせ対応、月次の集計。
一度うまくいったAIの使い方も、次のような理由で、続かないことが多くあります。

- 自分だけが、うまいプロンプトを知っている（引き継げない）
- 毎回、頼み方が変わり、出来がばらつく
- 誰がどこまで確認したか、記録が残らない
- 職場の中で、AIに入力してよい情報の基準が、人によって違う

<strong>個人のコツを、チームの仕組みにする</strong>ことが、この章のテーマです。

## プロンプト設計シート（再掲）

```
**目的**：誰に・何のために・何を作るか
**入力**：AIに渡す素材は何か（機密は伏せたか）
**制約**：やってはいけないこと・守るルール
**出力形式**：表・箇条書き・文字数など
**検証**：出力が正しいか、何と突き合わせるか
```

この章では、この5要素を、<strong>工程ごとに、1回ずつ設計する</strong>ことになります。
1つのプロンプトで、すべてを頼むのではなく、工程ごとに分けます。

## 実例：日報から週報を作る仕組み

### 状況と素材

あなたは営業課の課長（田中）です。部下は、山田・井上・中村・佐藤・鈴木の5人です。
毎週月曜に、部下の日報（週5日分、合計25本）を読み、営業部長に出す週報を作っています。
1回に、約90分かかります。これをAIと一緒に、短く、安定して回したいと考えています。

手元にあるのは、次の3つです（ZIPに入っています）。

- 日報25本
- 課長（あなた）の、月間のPDCA目標
- 週報のひな形

日報には、前日に書いた「本日の目標」と、当日の「実行結果」、経費が書かれています。
金曜の日報には、週の目標（新規訪問3件以上、見積提出1件以上）に対する結果もあります。
この週は、<strong>3人が達成、2人が未達成</strong>でした。経費の記録がある人は、3人います。

日報の例（中村さんの10/5）です。

```
【日報】2026-10-05（月）　営業課　中村
■ 本日の目標（前日に記入）
・新規訪問：1件（H社）
・見積提出：0件
■ 本日の実行結果
・新規訪問：0件
・見積提出：0件
・内容：H社の訪問は、先方の都合でキャンセルになった。日程を再調整する。
■ 経費
・なし
```

課長の月間PDCA目標（2026年10月）は、次のとおりです。
週報では、この目標と照らして、達成の状況と遅れを報告します。

| 項目 | 月間の目標 | 週の目安 |
| --- | --- | --- |
| 新規訪問 | 60件 | 15件（1人あたり週3件） |
| 見積提出 | 20件 | 5件（1人あたり週1件） |
| 新規受注 | 6件 | （週の目安は、設定なし） |
| 営業経費 | 50,000円以内 | （週の目安は、設定なし） |

週報では、目標に対する達成の状況、遅れている点、来週の対策案を、部長に報告します。
対策案は、課長が決めます。

### 悪い進め方とその失敗

毎週、次のように頼んでいたとします。

```
日報から週報を作って。
```

失敗は、次のとおりです。

- 週ごとに、週報の形式や粒度が変わってしまう
- 件数や経費の合計を、AIが計算して、間違える（日報にない数字が混ざることもある）
- 課長の月間目標が入力に入っていないので、目標との差異を見られない
- 課長が、どこまで確認したのか、記録が残らない

1つの依頼で、「読む・要約する・リスクを拾う・書く」をすべて任せているため、どこで間違えたかも分かりません。

### 改善した進め方：工程に分ける

| 工程 | 担当 | 入力 | 出力 | 人の確認ポイント |
| --- | --- | --- | --- | --- |
| 1. 事実の抽出 | AI | 日報25本 | 担当者ごとの目標・結果・経費の一覧（事実のみ、根拠つき） | 日報と突き合わせ。数字・日付が正しいか |
| 2. 数字の集計 | 人（表計算） | 工程1の一覧 | 訪問・見積・受注・経費の合計 | 合計を、日報の数字と照合 |
| 3. 目標との差異・遅れの候補出し | AI | 工程1の一覧、工程2の合計、課長の月間PDCA目標 | 差異・遅れ（根拠つき）、課長への確認事項 | 本当に上に報告すべきかを判断。対策案は課長が決める |
| 4. 週報のドラフト | AI | 工程1〜3の出力、週報のひな形 | 週報のドラフト | 表現・数字。断定的な予測がないか |
| 5. 承認と提出 | 人 | ドラフト | 完成した週報 | 最終責任は課長 |

ポイントは、2つです。

- 「何を報告するか」の判断（工程3の取捨選択、対策案、工程5）は、人が持つ
- <strong>数字の合計は、AIに任せず、人が表計算で出す</strong>（工程2）。AIには、その合計を、入力として渡す

AIに任せるのは、読む・整理する・下書きする作業です。

### 工程1のプロンプト（テンプレート化）

毎週使えるよう、変わる部分だけを、【】で示します。

```
あなたは営業課の日報を整理する担当です。以下の日報（5人・週5日分）から、担当者ごとの目標と結果を整理してください。

**目的**
【対象週】の日報から、課長が上長への報告の元にする、担当者ごとの目標と結果の事実を一覧にする。

**制約**
- 日報に書かれている事実のみを使う。日報にない数字・予定・担当者は書かない
- 件数や金額は、日報に書かれている数字をそのまま使う。合計や割合は、自分で計算しない
- 各記述の末尾に、根拠となる日報の日付と担当者名を付ける（例：［10/6 山田］）
- 分からない点は「日報に記載なし」と書く

**出力形式**
1. 担当者ごとの表（担当者／日付／目標／結果／経費）
2. 週の目標に対する結果（金曜の記入のとおり、担当者ごとに「達成／未達成」）
3. 日報に書かれている、キャンセル・遅れ・受注などの出来事の一覧（根拠つき）

**日報**
【ここに日報を貼る】
```

### 工程3のプロンプト（目標との差異）

工程2で、人が表計算で出した合計を、入力に加えます。

```
あなたは営業課の週報作成を支援する担当です。次の資料を使って、目標との差異と、上長への報告の候補を整理してください。

**入力**
- 日報の整理結果（工程1）：【ここに貼る】
- 課長の月間PDCA目標：【ここに貼る】
- 人が表計算で集計した、今週の合計：新規訪問【　】件、見積提出【　】件、新規受注【　】件、営業経費【　】円

**制約**
- 資料に書かれていないことは書かない。理由が日報に書かれていない場合は、「日報に記載なし」と書く
- 合計は、上の「人が集計した今週の合計」を使い、自分で計算し直さない。割合や達成率は、書かない
- 各項目に、根拠（目標のどの項目か、日報の日付と担当者）を付ける
- 対策案は書かない（対策案は課長が決める）。確認が必要な点は、質問の形で挙げる

**出力形式**
1. 目標との対比の表（項目／今週の目標の目安／今週の実績／メモ）
2. 差異・遅れ（根拠つき）
3. 課長に確認したい点
```

### 実際に試した結果

工程1と工程3を、この素材で、Claude Codeで試しました（出力は、実行のたびに変わります）。

<strong>工程1（事実の抽出）</strong>

- 担当者ごとの表を、日付順に作り、各記述に［10/6 山田］のような根拠を付けた
- 件数や金額は、日報のとおりに書き、合計は計算しなかった（経費についても、「合計は計算していません」と明記した）
- 週の目標に対する結果を、達成は山田・井上・鈴木、未達成は中村（訪問2件）・佐藤（見積0件）と、正しく整理した
- キャンセル2件（中村：H社・K社）、見積の遅れ（佐藤：L社）、受注（鈴木：S社、480,000円）を、根拠つきで抜き出した

次に、人が表計算で、合計を出します（新規訪問15件、見積提出5件、営業経費7,690円。新規受注は1件）。
この数字を、工程3の入力に渡しました。

<strong>工程3（目標との差異・遅れの候補出し）</strong>

- 課の合計は、新規訪問15件・見積提出5件で、週の目安と同じだった。一方で、個人別では、中村（訪問2件）と佐藤（見積0件）が届いていないと、指摘した
- 新規受注と営業経費は、「週の目安は資料になし」と書き、目安を作り話で補わなかった
- 理由が日報にない点（佐藤の価格の確認先など）は、「日報に記載なし」と書いた
- 課長への確認事項を、7つ挙げた（キャンセルの書き方、経費が業務に必要かの判断、対策案は課長が決めるため空欄でよいか、など）

人が確認する点は、次のとおりです。

- 個人別の結果が、金曜の日報の記入と一致しているか
- 合計が、人が出した数字のまま使われているか
- 「日報に記載なし」とされた点を、本人に確認するか

### 記録の残し方

仕組みにするときは、次の2つを記録しておくと、引き継ぎや改善に役立ちます。

- 使ったプロンプトのバージョン（いつ、何を変えたか）
- AIの出力に対して、人が修正した点（何を直したか）

修正の記録が溜まると、「AIがよく間違える点」が分かり、制約を追加できます。
これが、仕組みが育っていくということです。

### 設計メモ：なぜこの書き方か

| 要素 | 実例での書き方 | 効いた理由 |
| --- | --- | --- |
| 目的 | 工程ごとに、1つの役割 | 1回の依頼を、小さく、確認しやすくした |
| 入力 | 前工程の出力と、人が集計した数字を、次の入力にする | どの工程で間違えたかが、特定できる |
| 制約 | 「合計は人が出す」「根拠を付ける」「記載なしと書く」 | 第1〜7章で学んだ失敗の防ぎ方を、テンプレートに組み込んだ |
| 出力形式 | 表で固定 | 毎週、同じ形式で出力される |
| 検証 | 工程ごとに、人の確認ポイントを決める | 人が判断する場所が、明確になる |

<strong>各章で学んだ制約（補わない、根拠を付ける、要確認と書く）を、テンプレートに組み込む</strong>のが、仕組み化の中核です。
一度書けば、毎回思い出さなくて済みます。

## 練習問題

進め方は全問共通です。

1. 素材を読み、プロンプト設計シートの5要素を自分で埋める（AIはまだ使わない）
2. 埋めた内容をもとにプロンプトを書き、普段使うAIで実行する
3. 出力をルーブリックで自己採点する
4. 解説を開き、自分の設計と比べる

### 問1 業務を工程に分ける

<strong>状況</strong>：営業事務のあなたは、顧客からの見積依頼への対応を、AIと一緒に効率化したいと考えています。見積依頼は、顧客によって、届き方が違います。

<strong>成果物</strong>：工程表（工程／担当（AIか人か）／入力／出力／人の確認ポイント）。3工程以上。
発展課題（任意）として、届いた4件の依頼を、統一の形式（品目・数量・希望納期）にそろえる作業を、AIで試します。

素材は、ZIPに入っています。

- price-list.csv：当社の価格表（納品できる商品）
- request-1-email.txt：メール（丁寧で、内容が明確）
- request-2-email.txt：メール（言い方が曖昧）
- request-3-fax.txt：FAXの定型票（「商品名：個数」）
- request-4-phone-memo.txt：電話を受けた社員のメモ（略記）

```
【現在の業務の流れ】
1. 顧客から、メール・FAX・電話で、見積依頼が届く（メールは自由な文章、FAXは「商品名：個数」の定型票、電話は社員が書いたメモ）
2. 依頼内容（品目・数量・希望納期）を読み取り、社内の見積依頼フォームに転記する
3. 価格表を見て、見積金額を計算する
4. 特別値引きが必要な場合は、課長に相談して決める
5. 見積書を作成し、顧客にメールで送る
```

依頼の届き方の違いは、たとえば次のようなものです。

```
【メール（request-2）】椅子を5〜6脚と、ホワイトボードを1枚ほしいです。いくらになりますか？　できるだけ早くほしいです。
【FAX（request-3）】商品名：コピー用紙A4　個数：30
【電話メモ（request-4）】・ペン　黒　箱で2　／　希望：10/9まで（至急）
```

<details>
<summary>よくある失敗と解説</summary>

工程分解の判断は、<strong>「間違えたときの被害の大きさ」と「判断が必要か」</strong>で行います。

- 入力の形式をそろえる工程（工程2）：メール・FAX・電話メモは、書き方がバラバラです。最初に、統一の形式にそろえてから、後の工程に渡します。AIが得意な作業ですが、数量や納期の読み違いは起きるので、人が確認します
- 例外の判断：取扱のない商品、曖昧な数量、間に合わない納期、最小注文数の不足は、人が判断して、顧客に確認します
- 計算：AIは、計算を間違えることがあるため、AIの計算を信用せず、価格表と表計算で確かめます
- 値引きの判断：権限と責任が関わるので、人が判断します
- 顧客への送信：外部に出る最後の関門なので、人が必ず確認します

このサンプルを、Claude Codeで試したところ、次の点を、要確認として挙げました。
取扱のない商品、「椅子」の言い換え、数量の幅、間に合わない納期、最小注文数の不足です。
一方で、納期を数えるときの休日の扱い（土日と10/12の祝日）は、AIが自分で仮定していました（AI自身が、前提として注記しています）。
納期の数え方のような、社内のルールは、AIの仮定に任せず、人が決めて、指示に書きます。

AIに「見積書まで全部作って、送って」と頼むのは、確認の機会を、すべて飛ばす設計です。
工程ごとに、人が確認する場所を残してください。

</details>

### 問2 プロンプトをテンプレートにする

<strong>状況</strong>：第1章で作った議事録のプロンプトを、部署のみんなが使えるよう、テンプレートにします。社内向けの会議にも、社外向けの会議にも使えるようにします。

<strong>成果物</strong>：テンプレート（変わる部分を【】で示す）と、使い方の説明。

```
【元のプロンプト（第1章より）】
あなたは社内の会議記録を整理する事務担当です。以下の「会議メモ」から、共有用の議事録を作成してください。

目的：会議に参加していない部長にも、決まったこと・決まっていないこと・次に誰が何をするかが一目で分かる議事録を作る。

制約：
- メモに書かれていない事実（担当者・期限・金額など）を補わない。不明な項目は「未定」と書く
- 雑談や業務に関係のない話題は含めない
- 断定できない発言は「決定事項」に入れず、「未決事項」に入れる

出力形式：決定事項／未決事項／担当・期限 の3区分
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 変わる部分（読み手・会議名・メモ・社内か社外か）が、【】で示されている
- [ ] 社外向けのときだけ追加する制約（社内の原価・個人の連絡先などを含めない）が、条件つきで組み込まれている
- [ ] 元のプロンプトの制約（補わない・雑談を除く・曖昧な発言は未決）が、削られていない
- [ ] 使い方の説明に、「機密情報は伏せてから貼る」が含まれている
- [ ] テンプレートを、実際に、社内向けと社外向けの両方の例で試した

</details>

<details>
<summary>よくある失敗と解説</summary>

テンプレート化で最も多い失敗は、<strong>変数を増やしすぎる</strong>ことです。
変わる部分が多すぎると、使う人が、何を入れるべきか迷います。

変数は、本当に毎回変わるものだけに絞ります。
今回の例なら、次の4つで十分です。

- 【会議名】
- 【読み手】（例：参加していない部長）
- 【社外共有か】（はい／いいえ）
- 【会議メモ】

「社外共有か」で内容が変わる部分は、テンプレートの中に、条件を書いておきます。

```
**追加の制約（【社外共有か】が「はい」の場合のみ）**
- 原価・社内の方針・個人の連絡先・競合他社の名前を含めない
```

もう一つ大切なのは、<strong>第1章〜第7章で学んだ制約を、削らずに引き継ぐ</strong>ことです。
「短くしよう」として、大事な制約が消えると、元の失敗が戻ってきます。

</details>

### 問3 AIに、出力を採点させる

<strong>状況</strong>：議事録のAI出力を、毎回、目で確認するのは大変です。採点の一次チェックを、別のAIに頼みたいと考えています。

<strong>成果物</strong>：採点用のプロンプトと、採点の限界についてのメモ。

```
【元メモ】
【システム更改 打ち合わせ 10/3】出席：森、大野、清水
- 現行サーバは来年3月で保守終了。更改は必須
- 移行先はクラウドとオンプレの2案。どちらにするかは次回までに大野さんが比較表を作る
- 予算枠は来週の経営会議で確認（森さん）
- 新システムの稼働時期は、来年4月か5月ごろ

【AIが作った議事録】
決定事項
・現行サーバは来年3月で保守終了のため更改する
・移行先はクラウドに決定
・新システムは来年4月に稼働開始
担当・期限
大野｜比較表の作成｜10/10
森｜予算枠の確認｜来週の経営会議

【採点の基準（ルーブリック）】
1. 未決の事項を、決定事項に入れていない
2. 幅のある表現（4月か5月）を、1つに絞っていない
3. 元メモにない日付・数字を、追加していない
4. 担当者が、元メモのとおりである
5. 元メモの決定事項が、漏れなく入っている
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 採点用のプロンプトに、「各基準について、〇か×か」「根拠として、元メモと議事録の該当箇所を引用する」を指示した
- [ ] 判断が難しい場合は、「要確認」とする出口を用意した
- [ ] 基準1〜3が、×になる結果が得られた（クラウドに決定、来年4月、10/10）
- [ ] 「総合点」ではなく、基準ごとの結果を出すようにした
- [ ] 採点AIの限界（採点も間違える）に触れ、人が一定の割合で抜き取り確認する運用を書いた

</details>

<details>
<summary>よくある失敗と解説</summary>

「AIにAIを採点させる」のは便利ですが、<strong>採点するAIも、間違えます</strong>。
甘く採点することも、厳しすぎることもあります。

採点プロンプトの設計の型です。

```
以下の「元メモ」「議事録」「採点の基準」を使って、議事録を採点してください。

**制約**
- 基準ごとに、〇・×・要確認のいずれかを付ける
- 各判定に、根拠となる元メモと議事録の該当箇所を、そのまま引用する
- 判断できない場合は、無理に〇×を付けず、「要確認」とする
- 総合点は出さない。修正案も出さない
```

採点結果の使い方には、注意が必要です。

- 採点AIは、あくまで<strong>一次チェック</strong>。最終確認は、人が行う
- 定期的に、AIの採点結果を人が抜き取って検証し、採点AIの癖を把握する
- ×が付いた項目だけでなく、〇が付いた項目にも、間違いが混ざる可能性がある

「採点AIが〇を付けたから大丈夫」と考えてしまうと、確認がなくなり、第1章から学んだ、最終責任は人にあるという原則が崩れます。

</details>

### 問4 職場のAI利用ガイドを作る

<strong>状況</strong>：部署でAIを使う人が増え、ルールがないことが、不安材料になっています。事故の事例を素材に、1枚のガイドを作ります。

<strong>成果物</strong>：AI利用ガイド（1枚）。会社の規定が分からない部分は、勝手に書かず、「要確認」とする。

```
【最近あった、ヒヤリハットの事例（架空）】
事例1：顧客名と金額が入った一覧表を、そのままAIに貼り付けて、要約させた
事例2：AIが計算した見積の合計金額を、確認せずに見積書に書き、顧客に送りそうになった
事例3：AIが書いた集計スクリプトを、コピーを取らずに共有フォルダで実行し、一部のファイルが消えた
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 3つの事例それぞれに対応するルール（入力してよい情報の基準／AI出力の検証の義務／実行前のテスト）が、ガイドに含まれている
- [ ] 会社の実際のAI利用規定が分からない箇所（利用してよいツール、社内の許可の要否など）を、AIが勝手に書かず、「【要確認：〇〇】」としている
- [ ] 「困ったときの相談先」の欄が、空欄または「要確認」になっている（AIが架空の窓口を作っていない）
- [ ] 「AIの出力は、必ず人が確認する。最終責任は人にある」が、明記されている
- [ ] ガイドが、1枚（箇条書きで、20項目以内）に収まっている

</details>

<details>
<summary>よくある失敗と解説</summary>

この問題では、<strong>AIが、実在しない社内規定を、それらしく作ってしまう</strong>ことが最大の罠です。
「情報セキュリティ部への事前申請が必要です」のような一文が、実際にはない部署や手続きとして、書かれてしまうことがあります。

制約の型です。

```
**制約**
- 事例から導けるルールのみを書く。会社の規定・部署名・申請手続き・利用可能なツールは、書かない
- 会社の規定に関わる箇所は、「【要確認：〇〇】」と書く
- 各ルールの末尾に、どの事例に対応するかを書く（例：［事例1］）
```

ガイドは、AIが作ったものを、そのまま配るのではなく、必ず、情報システム部門や上長と一緒に、実際の規定と照らして確認します。
ここまでの各章で、「補わない」「要確認と書く」「根拠を示す」と練習してきたことが、そのまま、ルールづくりにも使えます。

</details>

## 繰り返し使う制約は、AIに登録して短くする

この章のプロンプトは、制約を毎回書き込む形で練習しました。
同じ業務を繰り返すなら、<strong>変わらない制約は、AIにあらかじめ登録しておく</strong>ことで、依頼を短くできます。

この章で登録しておくとよいのは、工程ごとのテンプレート、採点の基準、社内のAI利用ルールです。
ChatGPT・Claude・Geminiでの登録手順は、[生成AIに社内ルールを覚えさせるスキル設定のやり方](/method/ai-skill-rules-setup/)で解説しています。
登録しても、最終確認は人が行うことに変わりはありません。

## 自分の職場に置き換える

最後の課題は、コース全体の集大成です。

1. 自分の仕事で、毎週または毎月繰り返している業務を1つ選ぶ
2. 業務を3〜5工程に分け、各工程を「AI／人」に割り当てる。人が判断する工程と、確認ポイントを決める
3. 最初の工程のプロンプトを、テンプレート（変わる部分は【】）として書く。第1〜7章の制約から、2つ以上を組み込む
4. 1回試し、AIの出力に対して人が修正した点を、記録する。次回、その修正を防ぐ制約を1つ追加する

仕上げに、S.E.L.F.ループの「F（Forge it）」として、<strong>このコースで学んだ型を、同僚に説明するつもりで、1枚にまとめて</strong>みてください。
説明できる型は、あなたの仕事の中で、繰り返し使える道具になっています。

## この章のまとめ

- 繰り返しの業務は、工程に分け、AIが担う部分と、人が判断する部分を分ける
- 工程ごとに、5要素で設計する。前の工程の出力を、次の工程の入力にすると、間違いの場所が特定できる
- プロンプトのテンプレートは、変数を絞り、これまでの章の制約を削らずに組み込む
- AIによる採点は、一次チェックにとどめる。人が、抜き取りで検証する
- AI利用のルールは、事例から導ける範囲を書き、会社の規定は、AIに作らせず、「要確認」とする
- 使ったプロンプトのバージョンと、人が直した点を記録すると、仕組みが育つ

## コース全体を通して

8章を通して、繰り返し出てきた原則は、次の5つです。

- <strong>投げる前に設計する</strong>：目的・入力・制約・出力形式・検証を、先に決める
- <strong>補わせない</strong>：素材にないことは、「未定」「要確認」「記載なし」と書かせる
- <strong>根拠を出させる</strong>：出典・行番号・引用で、人が確かめられる状態にする
- <strong>最終責任は人にある</strong>：AIの出力は、元の素材と突き合わせて確認する
- <strong>機密は、貼る前に伏せる</strong>：AIに渡さないことが、最も確実な防御になる

これらは、どの業務でも、使える型です。
次は、あなたの職場の、具体的な1つの業務から、始めてみてください。
