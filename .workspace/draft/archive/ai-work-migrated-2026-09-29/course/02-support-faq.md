## この章で学ぶこと

顧客からの問い合わせに返信する仕事は、書く速さより「何を言ってよくて、何を言ってはいけないか」の判断が重い仕事です。
急いで返そうとすると、社内で決まっていないことまで約束してしまう危険があります。

この章では、返信文とFAQをAIに手伝わせながら、次の3つを練習します。

- 相手の感情と社内ルールを、制約として明文化する
- AIが勝手に「約束」してしまう失敗を防ぐ
- 大量の問い合わせを分類し、FAQの種を見つける
- 毎回変わらない社内規定を、AIにあらかじめ登録して、入力の手間を減らす

第1章で学んだ5要素（目的・入力・制約・出力形式・検証）は、この章でもそのまま使います。
素材はすべて架空のデータです。実際の顧客の氏名・注文番号・メールアドレスは、AIに貼る前に必ず伏せてください。
本コースは実務練習用の教材です。AIの出力は必ず人が検証してください。

## このユースケースが起きる場面

ECサイト、SaaS、店舗の予約窓口など、問い合わせを受ける仕事は業種を問わず存在します。
担当者が悩むのは、たとえば次の場面です。

- 怒っている顧客に、誠実に、しかし社内で決まっていないことは言わずに返信したい
- 同じような問い合わせが毎日来るので、FAQにまとめたい
- 新人でも一定の品質で返信できるよう、型を作りたい

AIは文章の丁寧さを整えるのが得意です。
一方で、丁寧に書こうとするあまり、<strong>社内で決まっていない返金や納期を「お約束」してしまう</strong>ことがあります。
顧客対応では、これが最も高くつく失敗です。

## プロンプト設計シート（再掲）

```
**目的**：誰に・何のために・何を作るか
**入力**：AIに渡す素材は何か（機密は伏せたか）
**制約**：やってはいけないこと・守るルール
**出力形式**：表・箇条書き・文字数など
**検証**：出力が正しいか、何と突き合わせるか
```

この章で特に効くのは、<strong>「制約」に社内ルールを書く</strong>ことです。
AIは、あなたの会社の返金規定を知りません。書かなければ、一般的な会社の対応を想像で補います。

## 実例：配送遅延のクレームに返信する

### 状況と素材

あなたはオンラインショップのサポート担当です。
顧客から次のメールが届きました。

```
件名：注文した商品が届きません

ミナト商店 ご担当者様

9月20日に注文した掃除機（注文番号 A-10482）が、まだ届きません。
到着予定は9月25日と聞いていましたが、今日は9月29日です。
連絡もなく、とても困っています。いつ届くのか、至急教えてください。
```

社内では、次の状況が分かっています。

```
【社内メモ】
- 配送業者のシステムでは、9/26に配送センターに到着。以降の追跡情報が更新されていない
- 配送業者に調査を依頼中。回答は最短で明日
- 返品・返金は、商品未着から14日を過ぎた場合に検討する（社内規定）
- お詫びのクーポン提供は、担当者の判断ではできない（上長の承認が必要）
```

### 悪い指示とその失敗

```
この顧客に返信メールを書いて。
```

返ってくるのは、たとえば次のような文章です。

> このたびは大変なご迷惑をおかけし、誠に申し訳ございません。明日には必ず商品をお届けいたします。ご希望であれば全額返金いたしますので、ご安心ください。

失敗が3つあります。

- 「明日には必ず届ける」という、確認できていない納期を約束している
- 規定（14日）を超えていないのに、返金を約束している
- 社内メモの調査状況（追跡が止まっている）が、返信に反映されていない

指示に社内ルールが書かれていないので、AIは「丁寧で安心させる返信」という一般的な型に流れました。

### 改善したプロンプト

```
あなたはオンラインショップのサポート担当です。以下の「顧客のメール」への返信案を作成してください。

**目的**
配送の遅れに困っている顧客に、誠実に状況を伝え、次にこちらが何をするかを示す。

**制約**
- 「社内メモ」に書かれていない事実や約束（納期・返金・クーポンなど）を書かない
- 納期は、確定するまで断定しない。「確認でき次第ご連絡します」の形にする
- 返金・クーポンは「社内メモ」の規定にない限り、提案しない
- 顧客の不安と不便に共感する文を一文入れる。謝罪は1回にとどめる
- 顧客に渡してよいのは、社内メモのうち事実部分のみ（社内規定の詳細は書かない）

**出力形式**
1. 件名
2. 本文（250字程度、敬体）
3. 【社内向け】この返信案で意図的に書かなかったこと（約束を避けた点）を箇条書きで

**顧客のメール**
（ここにメールを貼る）

**社内メモ**
（ここに社内メモを貼る）
```

### AIの出力と、人が確認した点

このプロンプトからは、次のような出力が得られます。

> <strong>件名</strong>：Re: 注文した商品が届きません（注文番号 A-10482）
>
> <strong>本文</strong>：ミナト商店です。ご連絡ありがとうございます。ご到着予定日を過ぎてもお届けできておらず、ご不安とご不便をおかけしております。申し訳ございません。配送状況を確認したところ、9月26日に配送センターに到着した記録があり、その後の状況は配送業者に調査を依頼しております。調査の結果が分かり次第、改めてご連絡いたします。
>
> <strong>【社内向け】書かなかったこと</strong>：具体的な到着日、返金の可否、お詫びのクーポン

人が確認する点は、次のとおりです。

- 本文の事実が、社内メモと食い違っていないか
- 「調査結果が分かり次第」に期日がなく、顧客が不安にならないか。社内で「明日」と言えるなら、それを追記するかを判断する
- 返金は「14日を過ぎた場合に検討」という規定があるので、顧客に伝えるかどうかは、自分で決める

<strong>「書かなかったこと」を社内向けに出力させる</strong>のが、この設計の検証部分です。
AIが約束を避けたことを、人が確認できます。

### 設計メモ：なぜこの書き方か

| 要素 | 実例での書き方 | 効いた理由 |
| --- | --- | --- |
| 目的 | 「不安な顧客に、次に何をするかを示す」 | 返信の役割が決まり、謝罪だけの文にならない |
| 入力 | メールと社内メモを別々に貼る | 顧客に見せてよい情報と、社内だけの情報が区別できる |
| 制約 | 「メモにない約束をしない」「納期は断定しない」「社内規定の詳細は書かない」 | AIが最もやりがちな失敗を先回りして禁止した |
| 出力形式 | 件名・本文・社内向けの注記 | 返信案と、人が確認する材料を同時に得られる |
| 検証 | 「書かなかったこと」を出力させる | 約束の漏れを、人が数秒で確認できる |

<strong>顧客対応では、「言ってよいこと」より「言ってはいけないこと」のリストのほうが、AIを安全に動かします。</strong>
社内ルールは、暗黙のままにせず、プロンプトに書き出してください。

## 毎回の入力を減らす：社内規定をAIに登録しておく

実例のプロンプトは、制約だけで十数行ありました。
これを問い合わせのたびに打つのは面倒ですし、<strong>貼り忘れた1回が、規定違反の返信につながります</strong>。

そこで、依頼の中身を2つに分けて考えます。

| 種類 | 例 | 扱い方 |
| --- | --- | --- |
| 毎回変わらない情報 | 返金の規定、クーポンの承認ルール、謝罪の回数、出力の型 | <strong>AIにあらかじめ登録しておく</strong> |
| 毎回変わる情報 | 今回の顧客のメール、今回の状況（追跡の状態など） | 依頼のたびに渡す |

社内規定は、前者です。一度登録しておけば、毎回書く必要がなくなります。

### 登録の方法

ここでは、AIのClaudeを例にします。主な方法は2つです。
なお、CLAUDE.mdは、コマンドラインで動くClaude Codeで使われるファイルです。ブラウザで使うClaudeでは、「プロジェクト」の指示欄が近い役割を持ちます。

| 方法 | 置くもの | 読み込まれ方 |
| --- | --- | --- |
| CLAUDE.md | 部署やチーム全体で共通のルール（トーン、個人情報の扱い、AI利用の基本方針など） | そのフォルダ（プロジェクト）で作業するとき、常に読み込まれる |
| スキル（Skills） | 特定の業務だけのルール（通販サポートの規定など） | 依頼の内容が、スキルの説明文に当てはまるときに読み込まれる |

通販サポートの規定は、部署の特定の業務のためのものなので、<strong>スキルに登録する</strong>のが向いています。
部署をまたぐ共通の方針は、CLAUDE.mdに置く、と使い分けます。

ChatGPTのカスタム指示やプロジェクト、Geminiのスキル（2026年11月にGemから切り替わる予定）など、他のAIにも、同じ考え方の仕組みがあります。
名称や設定方法はサービスごとに異なるので、使うサービスの最新の案内を確認してください。

### 登録するルールの例

実例で使った規定を、次のようにまとめます。
これを、CLAUDE.mdの本文、またはスキルの本文として保存します。

```
## サポート対応ルール（ミナト商店・架空）

### 全般
- 返信は敬体。謝罪は1回にとどめ、顧客の不安・不便に共感する一文を入れる
- 状況メモにない納期・返金・クーポンを約束しない。確定していないことは「確認でき次第ご連絡します」とする
- 返信案の後に、【社内向け】として「この返信案で意図的に書かなかったこと」を箇条書きで付ける

### 配送の遅延
- 返品・返金は、商品未着から14日を過ぎた場合に検討する。14日以内は返金を案内しない
- 配送業者に調査を依頼している間は、結果が分かり次第連絡する、と伝える

### 補償（クーポン等）
- お詫びのクーポンは、担当者の判断では提案・約束できない。上長の承認が必要
- 補償案を出すときは、「上長承認が前提の案」として社内向けにのみ示し、顧客向けの本文では確約しない

### 請求トラブル
- 二重請求などは、確認できるまで断定しない。確認できた場合の返金は、確認から5〜7営業日
- 調査結果の回答は、2営業日以内
```

スキルとして保存する場合は、ファイルの先頭に、名前と「どんなときに使うか」の説明を書きます。

```
---
name: ec-support-rules
description: 通販サイト「ミナト商店」の顧客への返信文・お詫び・補償案・返金の可否を作るときに使う、社内のサポート対応ルール。
---
```

この説明文が、AIが「今回はこのルールを使う場面だ」と判断する手がかりになります。
<strong>どんな依頼のときに使うのかを、具体的に書く</strong>のがコツです。

### 短い依頼でも、規定どおりの答えが返る

実例と同じ顧客のメールを使い、次の短い依頼を、Claude Codeで、3つの設定で試しました。

```
この顧客への返答と補償例を提示して。

【顧客のメール】
（実例と同じメール）

【状況】
配送業者の追跡は9/26の配送センター到着以降、更新なし。調査依頼中（回答は最短で明日）。
```

- 設定A：規定を登録していない
- 設定B：規定をCLAUDE.mdに登録した
- 設定C：規定をスキルに登録した

依頼の文章は、3つとも全く同じです。
以下は、実際の出力の抜粋です（1回ずつの実行結果で、実行のたびに文章は変わります）。

設定Aの出力（規定なし）：

> ご提案：調査結果が出次第、明日中に次のいずれかをご案内します。1. <strong>代替品の即時再発送</strong>（在庫を確保済みです。お届け日は確定次第お知らせします）2. <strong>ご注文のキャンセルと全額返金</strong>
>
> お詫び：今回のご迷惑に対するお詫びとして、［補償内容］を差し上げたく存じます。

設定Cの出力（スキルに登録）：

> 【社内向け】この返信案で意図的に書かなかったこと
> - 返金・返品の案内：商品未着から14日を過ぎた場合に検討するルールです。到着予定日（9/25）からは4日目なので、案内していません。
> - クーポンなどの補償：担当者の判断では提案も約束もできないため、顧客向け本文には入れていません。
>
> 補償案（上長承認が前提の案・社内限り）：顧客へは確約しないでください。承認が出てから案内します。

3つの結果を、規定に照らして比べます。

| 確認項目 | A（規定なし） | B（CLAUDE.md） | C（スキル） |
| --- | --- | --- | --- |
| 状況メモにない「在庫を確保済み」を書いていないか | 書いている（誤り） | 書いていない | 書いていない |
| 14日以内なのに、返金を顧客に案内していないか | 案内している（誤り） | 案内していない | 案内していない |
| クーポンを、顧客向け本文で予告していないか | 予告している（誤り） | 予告していない | 予告していない |
| 「書かなかったこと」の注記が付いているか | なし | あり | あり |
| 補償案が、上長承認前提の社内向けとして示されているか | なし | あり | あり |

規定を登録していないAは、短い依頼を、AI自身の常識で補ってしまいました。
BとCは、<strong>依頼が短くても、登録した規定どおりに動いています</strong>。

### 登録するときの注意

規定を登録すれば安心、というわけではありません。次の点に気をつけてください。

- <strong>今回の状況は、毎回渡す</strong>：規定は「変わらない情報」だけです。追跡の状態など、今回の事実は、依頼に添えます
- <strong>規定が曖昧だと、AIも曖昧に解釈する</strong>：設定Bでは、「商品未着から14日」の数え始めの日が規定にないため、AIが「起算日は要確認」と注記しました。「商品の到着予定日から14日」のように、起算点まで書いておきます
- <strong>規定が変わったら、AIのルールも更新する</strong>：規定が二重になるので、更新した日付をルールに書き、見直す担当を決めておきます
- <strong>最終確認は、人が行う</strong>：規定どおりに動くのは、書かれた範囲だけです。規定にない事態は、AIが常識で補います。「規定にないことは、要確認と書く」という一文を入れておくと安全です
- <strong>登録する内容にも、機密の配慮が必要</strong>：規定の中に、顧客の個人情報や、外部に出せない情報を入れないでください。AIのサービスごとに、登録内容の扱いや共有の範囲が異なるので、社内のAI利用ルールを確認します

社内規定のPDFや写真からルールを作らせる方法と、ChatGPT・Claude・Geminiそれぞれの登録手順は、[生成AIに社内ルールを覚えさせるスキル設定のやり方](/method/ai-skill-rules-setup/)で詳しく解説しています。

## 練習問題

進め方は全問共通です。

1. 素材を読み、プロンプト設計シートの5要素を自分で埋める（AIはまだ使わない）
2. 埋めた内容をもとにプロンプトを書き、普段使うAIで実行する
3. 出力をルーブリックで自己採点する
4. 解説を開き、自分の設計と比べる

### 問1 手順書をもとに、問い合わせに答える

<strong>状況</strong>：サービスのサポート窓口です。ログインできないという問い合わせに、公式の手順をもとに返信します。

<strong>成果物</strong>：返信メール（手順は3ステップ以内、300字以内）。

```
【顧客の問い合わせ】
パスワードを忘れてログインできません。どうすればいいですか。

【公式の手順（社内マニュアルより）】
1. ログイン画面の「パスワードを忘れた方はこちら」をクリックする
2. 登録済みのメールアドレスを入力して送信する
3. 届いたメールのリンク（有効期限は1時間）から、新しいパスワードを設定する
※ メールが届かない場合は、迷惑メールフォルダを確認する。それでも届かない場合は、サポートまで連絡してもらう
```

- [ ] リンクの有効期限（1時間）が正しく含まれている
- [ ] 「メールが届かない場合」の案内が含まれている
- [ ] マニュアルにない情報（電話番号、別の方法など）を追加していない

<details>
<summary>よくある失敗と解説</summary>

素材が整っているので、この問題は簡単です。
ただし、AIは親切心から、マニュアルにない「アプリの再インストールをお試しください」のような一般論を足すことがあります。

制約に「マニュアルに書かれた手順・注意のみを使う。書かれていない対処法は書かない」と入れます。
文字数の指定は守られないことがあるので、出力後に数える、または「超えていれば短縮して」と続けて頼みます。

</details>

### 問2 怒っている顧客に、未確定のことを断定せずに返信する

<strong>状況</strong>：請求に関する問い合わせです。顧客は怒っており、事実関係はまだ調査中です。

<strong>成果物</strong>：返信案（件名と本文）と、社内向けの「約束を避けた点」のリスト。

```
【顧客のメール】
件名：二重で請求されています！

9月分の利用料が2回引き落とされていました。1回分は12,800円です。
どういうことですか。すぐ返金してください。今後も使うか考えます。

【社内メモ】
- 請求システムで確認中。二重請求かどうかは未確定
- 二重請求が確認できた場合の返金は、確認から5〜7営業日で処理する（規定）
- 調査結果の回答は、2営業日以内
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 「二重請求です」「こちらのミスです」など、未確定の事実を断定していない
- [ ] 「すぐ返金します」ではなく、「確認できた場合は返金手続きをする」という条件つきの書き方になっている
- [ ] 返金の目安（5〜7営業日）と、調査の回答期日（2営業日以内）が正確に書かれている
- [ ] 顧客の怒りと不安に共感する文が一文ある。謝罪が1回にとどまっている
- [ ] 社内向けの注記に、約束を避けた点が書かれている

</details>

<details>
<summary>よくある失敗と解説</summary>

この問題の難所は、<strong>顧客の怒りに合わせて、AIが確定していない事実を認めてしまう</strong>ことです。
「二重に請求してしまい、申し訳ございません」と書くと、調査の結果が二重請求でなかった場合に、取り消しができません。

使える型は2つです。

- 制約に「事実が確定するまでは、『確認中』『確認できた場合』という表現を使う」と書く
- 出力形式に「約束を避けた点」の注記を入れ、人が確認できる状態にする

もう1点。「返金の日数」を伝えるのは、二重請求が確認できた後に有効になる情報です。
条件つきの書き方（確認できた場合は）にしないと、返金が確定したように読まれます。

</details>

### 問3 問い合わせを分類し、FAQの種を見つける

<strong>状況</strong>：今週届いた問い合わせ10件を、分類してFAQ化する候補を探します。

<strong>成果物</strong>：分類表（カテゴリ・緊急度・理由）と、FAQ候補のリスト。

```
1. 注文した商品がまだ届かない
2. 請求書の宛名を変更したい
3. ログインできない。パスワードは合っているはず
4. 領収書は発行できますか
5. 商品が壊れて届いた。すぐ交換してほしい
6. 二重に引き落とされている
7. 退会の手続きを教えて
8. 新商品の発売予定はありますか
9. アプリの通知が来ない
10. 配送先の住所を変更したい（まだ発送前）
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 10件すべてが表に入っている（漏れ・重複がない）
- [ ] カテゴリを事前に定義し、その定義に沿って分類した（例：配送／請求／使い方／その他）
- [ ] 「破損」「二重請求」「発送前の住所変更」が、緊急度「高」になっている
- [ ] 緊急度の判断基準（時間の制約・金銭の被害など）が、理由の欄に書かれている
- [ ] FAQ候補が、同じカテゴリの質問から抽出されている（1件しかないものを候補にしていない）

</details>

<details>
<summary>よくある失敗と解説</summary>

分類は、AIが得意な作業ですが、<strong>基準を書かないと、実行するたびに結果がばらつきます</strong>。
「カテゴリは配送・請求・使い方・その他の4つ」「緊急度は、時間の制約または金銭の被害があれば高」のように、基準を先に固定します。

もう一つのコツは、出力を表にすることです。
表にすれば、10件が漏れなく入っているかを、行数で確認できます。

FAQの候補は「頻度」で選びます。
1件しかない質問は、まだFAQにする段階ではありません。
「AIに、分類したうえで、2件以上ある質問だけをFAQ候補として挙げさせる」と指示すれば、基準が明確になります。

</details>

### 問4 AIが書いた返信案の、約束の誤りを見抜く

<strong>状況</strong>：後輩がAIに作らせた返信案が、あなたのところに回ってきました。送信前のチェックを頼まれています。

<strong>成果物</strong>：誤りの指摘リストと、AIに修正させるためのプロンプト。

前提の情報：

```
【顧客のメール】
9月分の利用料が2回引き落とされていました。すぐ返金してください。

【社内メモ】
- 二重請求かどうかは調査中で、未確定
- 二重請求が確認できた場合の返金は、確認から5〜7営業日
- 調査結果の回答は2営業日以内
```

AIが作った返信案：

```
このたびは弊社の請求ミスにより、ご迷惑をおかけし申し訳ございません。
明日中に全額を返金いたします。
なお、マイページの「請求履歴」から、ご自身でも取り消し手続きができますので、あわせてご利用ください。
```

<details>
<summary>ルーブリック（自己採点）</summary>

- [ ] 「弊社の請求ミス」は、未確定の事実を断定した誤りだと指摘できた
- [ ] 「明日中に全額を返金」は、規定（5〜7営業日）と食い違う誤りだと指摘できた
- [ ] 「マイページの請求履歴から取り消し」は、社内メモに根拠がない情報だと指摘できた
- [ ] 修正のプロンプトに、前提の情報と返信案の両方を渡し、根拠のない記述を列挙させる指示を入れた
- [ ] 修正後の返信案も、人が社内メモと突き合わせて確認する、と設計した

</details>

<details>
<summary>よくある失敗と解説</summary>

誤りは3つあります。

- 未確定の原因を断定した（請求ミス）
- 規定と違う期日を約束した（明日中）
- 存在が確認できない機能を案内した（マイページからの取り消し）

3つ目は特に危険です。
顧客が実際にその画面を探して見つからなければ、二次のクレームになります。
<strong>AIは、それらしい機能名を、もっともらしく作ってしまう</strong>ことがあります。

修正は、次のように根拠を引用させる形にします。

```
以下の「前提の情報」と「返信案」を突き合わせ、返信案の記述のうち、前提の情報に根拠がないもの・前提と食い違うものをすべて列挙してください。

**制約**
- 各項目について、根拠となる前提の一文を引用すること
- 根拠が見つからない場合は「根拠なし」と書くこと
- 修正案は、列挙が終わってから別の見出しで示すこと
```

ここで、最終確認を人が行うことは、第1章と変わりません。

</details>

## 自分の職場に置き換える

この章の型を、自分の仕事に当てはめます。

1. 直近で対応した（または想像した）問い合わせを1つ選ぶ
2. 顧客名・注文番号・連絡先は、伏せ字にする。使わない場合は、架空のケースを作る
3. 「言ってよいこと」ではなく、「言ってはいけないこと」を5項目書き出す（納期・返金・責任の認定など）
4. その5項目を制約に入れて、返信案をAIに作らせ、「約束を避けた点」の出力を確認する
5. 毎回使うと感じた制約を、AIに登録する規定（CLAUDE.mdやスキルなど）にまとめ、短い依頼だけで同じ品質の返信案が出るかを試す

仕上げに、S.E.L.F.ループの「F（Forge it）」として、<strong>AIに「この返信案の弱点を3つ挙げて」と頼み</strong>、自分の気づきとの差を確かめます。

## この章のまとめ

- 顧客対応の依頼では、「言ってはいけないこと」を制約として書き出す
- AIは、確定していない事実や、存在しない機能をもっともらしく書く。「メモにない約束をしない」を必ず入れる
- 出力に「約束を避けた点」の注記を付けさせると、人の確認が速くなる
- 分類は、カテゴリと緊急度の基準を先に固定し、表で出力させる
- 未確定の事実は、条件つきの表現（確認できた場合は）にする
- 毎回変わらない社内規定は、CLAUDE.mdやスキルなどでAIに登録する。今回の状況だけを、依頼のたびに渡せばよい
- 登録する規定は、起算点まで具体的に書き、規定の更新に合わせてAIのルールも更新する
