## 4. リッチ要素の判定基準

**原則: 文章では伝わりにくい情報を運ぶときだけ足す。飾りの画像・ストック写真は足さない。**

| 要素 | 要る記事（判定の問い） | 要らない記事 | 中身 | `classify.py` の機械判定 |
|---|---|---|---|---|
| **出典** | 変わりうる事実を書いているか（日程・受験料・合格率・合格基準・出題数・制度・法律・統計） | 考え方・勉強法だけの記事、筆者の体験談 | 一次情報（IPA・試験団体・省庁・法令）へのリンクを、その事実の直後に置く。まとめサイトは出典にしない | 日付・金額・％・「合格率」「受験料」などが本文に5回以上 |
| **AIの実行例** | 読者に AI を使わせる記事か（プロンプトを載せている） | AI を話題にしているだけの記事 | プロンプトを実行した**実際の回答**（画面か、回答の引用）。うまくいかなかった例と直し方があればなおよい | コードブロックがあり、本文に ChatGPT・Gemini・Claude・NotebookLM・プロンプトのいずれか |
| **流れ図** | 手順・順番・構成を説明しているか（要素が4つ以上つながる） | 項目が並ぶだけの記事（表で足りる） | Mermaid（`MermaidStyles.astro` あり）か簡単な図。1記事1枚まで | 「手順・流れ・順番・進め方・構成・仕組み」の見出しが2つ以上、または番号付きリストが5項目以上 |
| **全体図** | 資格の入口（ハブ）・ロードマップか | ハブ以外 | どの順で何を取るか・どの記事を読むかの地図。1枚 | slug が `-hub`、またはタイトルに「ロードマップ」 |
| **筆者の体験** | 「やってみると分かる」ことが主張の根拠か（勉強法・ツール・AI の使い方） | 制度・日程・用語の解説 | `[!exp]` などの callout（筆者が書く。AI は創作しない） | カテゴリが method・app、またはタイトルに「勉強法」「やってみ」「ハック」「AIで」「独学」 |

### 筆者の体験の塩梅（2026-10-27 追記・案）

1人で30種類以上の資格を「やってみた」と書くと、かえって作り話に見える。量で決めず、**本当にある体験の種類**で置き場所を決める。

| 体験の種類 | 書ける記事 | 書き方 |
|---|---|---|
| 受験・学習の体験 | 筆者が実際に受けた・学んだ試験の記事だけ | `[!exp]`。点数・かかった時間・つまずいた所など具体的に |
| AI を使った体験 | プロンプトを載せた記事（試験を受けていなくても書ける） | AIの実行例（画面か回答）＋ひとこと（`[!think]`）。うまくいかなかった例があると信頼が増す |
| 調べた体験 | 制度・日程の記事 | 公式を読んで分かりにくかった所を `[!think]` で1つ。なければ書かない |
| なし | 筆者が受けていない資格の解説 | 無理に書かない。「筆者は未受験。公式情報から整理」と明記するほうが信頼される |

- 記事は **0〜2個** を目安にする（コースは `CLAUDE.md` どおり2〜4個）。全記事に入れない
- about に「筆者が受けた・学んだ試験」を書いておくと、記事の体験コメントの裏づけになる
- `CLAUDE.md` の「1記事あたり2〜4個」を記事では0〜2個に変えるかは、ユーザーが決める
