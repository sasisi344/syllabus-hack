# access-data — 週次アクセスデータ取得規約

週報PPDCA用のGA4/GSCエクスポート置き場。`2026/w{NN}/` 配下に週次で格納する。

> **週報作成**: データ格納後に `/weekly-report {wNN}` を実行すると、本READMEの規約に従って分析し `.workspace/.task/w{NN}-weekly-task.md` に週報を書き出す。

## ディレクトリ構成（1週あたり）

```
2026/w{NN}/
├── hikaku-gsc/
│   ├── クエリ.csv    # GSC 過去7日間 vs 前の7日間（比較モード）
│   └── ページ.csv    # 同上
├── gsc-28days/
│   ├── クエリ.csv    # GSC 直近28日間（比較なし・トレンド判断用）
│   └── ページ.csv    # 同上
└── ga4/
    ├── w{NN}-ga4-{MMDD}.csv         # GA4 探索レポート（サイト全体・縦持ち）
    └── w{NN}-ga4-course-{MMDD}.csv  # GA4 探索レポート（コース別モニタリング用。§「コース別モニタリング用GA4設定」参照）
```

## 重要: GSC比較CSVの列の読み方

GSCの比較エクスポートは列名が「過去 7 日間 クリック数」のように**同名で2回並ぶ**仕様。

- **1列目（左） = 直近7日間（今週）**
- **2列目（右） = その前の7日間（前週）**

指標の並び: クリック数×2 → 表示回数×2 → CTR×2 → 掲載順位×2。
前週の掲載順位 `0` は「圏外」ではなく「表示なし（データなし）」を意味する。

## GA4 探索レポートの設定（サイト全体の週報用）

- 行: ランディングページ、セッションの参照元/メディア（＋ページタイトル）
- 列: なし（セグメント適用なし）
- 値: セッション、アクティブユーザー、エンゲージメント率、セッションあたりの平均エンゲージメント時間、キーイベント
- 期間: 前週土曜〜金曜（GSCの7日間と揃える）

> **重要な注意（2026-09-27判明）**: 上記設定の「ランディングページ」はセッションスコープの指標（そのセッションの最初のページに固定され、セッション内で以降のページに遷移しても変わらない）。一方「ページタイトル」はイベントスコープ（実際に見たページごとに変わる）。そのため、同一セッション内で複数章を連続閲覧すると、章タイトルは変わるのに「ランディングページ」列は最初の章のURLのまま複数行に現れる。w39・w40週報でこれを「章送りナビゲーションのpage_view未発火バグ」と誤診断したが、実際はコースの実装バグではなく、**この探索レポートのディメンション設計上の見え方**だった（章を跨いで読み進める＝回遊が深いセッションほどこの現象が目立つ）。ページ単位の正確なPV（閲覧数）を見たい場合は下記「コース別モニタリング用GA4設定」を使うこと。

## コース別モニタリング用GA4設定（20時間学習コース `/course/` の週次検索流入モニタリング、2026-09-27追加）

> 背景: IP/SG/DM/PD-M/PD-Sはいずれも2026-09-13〜09-22の近接した時期に公開・インデックス済み。「公開直後のインデックス待ち」フェーズは終えたため、以降はコース別に毎週の検索流入（GSCのクエリ・表示回数・クリック・掲載順位）とPV（GA4の閲覧数・セッション）を定点観測するフェーズに移行する。

### 0. 前提確認（未連携なら最初に1回だけ実施）

GA4 Admin（管理）→ プロパティ列 → 「Product Links」（プロダクトのリンク）→ 「Search Console のリンク」で、本サイトのSearch Consoleプロパティが連携済みか確認する。未連携の場合はここでリンクを作成する（一度設定すれば以降は自動反映され、毎週の作業は不要）。連携すると、GA4の「レポート」ライブラリに「Search Console」コレクション（クエリ・ランディングページ×表示回数/クリック数/CTR/平均掲載順位）が追加され、GSCのクエリデータとGA4のセッション/PVデータを同じ画面で横断的に見られるようになる。

### 1. コース別「探索」レポート（Page path ベース、事象スコープ）— 標準設定（2026-09-27 w40で確定・以降これを基本とする）

サイト全体用の探索（ランディングページ基準）とは別に、コース専用の探索レポートを新規作成する。`w40-ga4-course-syllabus.csv` の設定を標準テンプレートとする。

- レポート種類: 自由形式（Free form）
- 行ディメンション: 「ページパスとスクリーンクラス」（イベントスコープ。実際に見たページごとに正しく変わる）
- 列（セグメント比較）: 「すべてのユーザー」「ウェブトラフィック」「オーガニックトラフィック」「モバイルトラフィック」の4セグメントを列として並べる（参照元/メディアを行に追加するより、オーガニック流入だけを直接読み取れるため見やすい）
- フィルタ: ディメンション「ページパスとスクリーンクラス」が「/course/」を含む
- 値: 表示回数（Views）、セッション、エンゲージメント率、セッションあたりの平均エンゲージメント時間
- 期間: 通常週は週報と同じ前週土曜〜金曜（GSCの7日間と揃える）。**ただし初回（w40）のみ、コース公開日（2026-08-30）〜取得日（2026-09-26）の累積期間で取得しており、これは「公開からの累積ベースライン」として扱う**。w41以降は単一週（または比較モードで今週/前週）に切り替える

この設定なら、章をまたいで読み進めても各章のPVが個別行として正しく積み上がる（従来のランディングページ基準の設定で起きていた「同一URLへの集約」が起きない）。ファイル名は `w{NN}-ga4-course-{MMDD}.csv` とする。

### 2. コース別の自動集計（任意・推奨）: Content Group設定

毎週手動でURLプレフィックス（`/course/ip`, `/course/sg`, `/course/dm`, `/course/pd-m`, `/course/pd-s`, 今後`/course/sc`等）ごとに正規表現で仕分けるのは手間なので、GA4管理画面でコンテンツグループ（Admin → データ表示 → コンテンツグループ）をルールベースで設定しておくと、探索レポートの1ディメンションとして「コース別」の集計列がそのまま出せる。

- ルール例: ページパスが `/course/ip` で始まる → グループ名 `course-ip`（sg/dm/pd-m/pd-s/scも同様に作成）
- 設定後は今後発生するデータにのみ適用される（過去データには遡及しない）ため、設定は早めに行うこと
- 設定後は探索レポートのディメンションに「コンテンツグループ」を追加するだけで、コース別のPV・セッションが自動で仕分けられる

### 2.5 コース用カスタムイベント（2026-10-06実装、GA4管理画面の設定が必要）

実装: `src/utils/ga.ts`（`trackEvent`）、`src/apps/course-quiz/ChapterQuiz.tsx`、`src/layouts/CourseLayout.astro`。

| イベント名 | 発火タイミング | 主なパラメータ |
| --- | --- | --- |
| `quiz_start` | クイズの最初の選択肢をクリック | course_id, quiz_mode(chapter/diagnosis), chapter_order |
| `quiz_complete` | 答え合わせ | 上記 + correct_count, total_count |
| `chapter_complete` | 章末クイズの初回答え合わせ（同じ章の再回答では発火しない） | course_id, chapter_order |
| `course_complete` | 全章の `chapter_complete` が揃った時（localStorage基準、同一ブラウザ） | course_id, total_chapters |
| `course_nav_click` | 章末の前章/次章リンクのクリック | course_id, direction(prev/next) |

GA4管理画面でやること（デプロイ後。イベントは送信されてから管理画面に現れる）:

1. **キーイベント登録**: 管理 → イベント → `chapter_complete` / `course_complete` の「キーイベントとしてマークを付ける」をオン（現状のキーイベント0件はここが未設定のため）。`quiz_complete` と `course_nav_click` は回遊分析用なのでマーク不要。
2. **カスタムディメンション登録**: 管理 → カスタム定義 → カスタムディメンションを作成。スコープ=イベント、ディメンション名=`コースID`、イベントパラメータ=`course_id`。ほかに必要なら `quiz_mode` / `chapter_order` / `direction` も同様に登録（登録前のデータには遡及しない）。
3. 探索レポートに「コースID」ディメンションと、イベント名フィルタ（`quiz_start` 等）を追加すると、コース別のクイズ開始・章完了数が見られる。

注意: `chapter_complete` は「答え合わせをした」ことを指し、正答率は問わない。`course_complete` は端末のlocalStorageを使うため、別端末・別ブラウザでの進捗は合算されない。

### 3. GSC側のコース別フィルタ方法

GSCエクスポート自体はサイト全体で一括取得したままでよい（現状の`クエリ.csv`/`ページ.csv`運用を継続）。分析時に「上位のページ」のURLを examId ごとのプレフィックス（`/course/ip/`, `/course/sg/`, `/course/dm/`, `/course/pd-m/`, `/course/pd-s/`）で絞り込み、コースごとの表示回数・クリック・掲載順位を集計する。件数が少ないうちはこの後処理で十分だが、対象コースが増えて手間が大きくなった場合は、Search Console UI側で「ページ」フィルタ（URLに `/course/{examId}/` を含む）をコースごとに設定してから個別にエクスポートする方式に切り替えてもよい。

### 週次KPI（コース別モニタリングの見るべき指標）

| 指標 | ソース | 備考 |
| --- | --- | --- |
| 表示回数・クリック数・掲載順位 | GSC（ページ.csv をexamIdプレフィックスで絞り込み） | コーストップ＋章ページ両方を対象 |
| PV（表示回数） | GA4（上記「コース別探索」設定） | ページパスベースなので章単位で正確 |
| セッション・エンゲージメント率 | GA4（同上） | 回遊の深さの参考値。母数が小さいうちは断定しない |

## AI分析時の定型抽出3点（Act候補の安定化）

1. 掲載順位11〜20位で表示回数が多いクエリ → リライト最優先候補
2. CTRが順位相応より低いページ → タイトル・メタ改善候補
3. 前週比で表示回数が伸びたクエリ → 追い風テーマ（横展開候補）
