## n8nなどクラウド駆動自動化システムの基礎知識

n8n / Zapier / Make（旧Integromat）などに代表される「ノーコード〜ローコードのワークフロー自動化（iPaaS: integration Platform as a Service）」の特性整理。

### できること

- **トリガー駆動の連携処理**：Webhook、Slackメッセージ、フォーム送信、メール受信、スケジュール（cron）などをきっかけに一連の処理を自動実行
- **SaaS間のデータ連携**：Slack・Notion・Google Sheets・Airtable・Gmail・Supabase等、数百〜数千のサービスをノード（コネクタ）で繋ぐ
- **簡単なデータ変換・分岐処理**：JSON整形、条件分岐（IF/Switch）、ループ、フィルタリングをGUI上で組める
- **外部APIコール（HTTP Request node）**：任意のREST APIを呼べるので、Claude APIなどLLM呼び出しも組み込める
- **可視化されたワークフロー管理**：非エンジニアでも処理の流れをフローチャート的に把握・修正できる
- **セルフホスト or クラウドの選択**：n8nは特にOSSでセルフホスト可能（データ主権・コスト面で優位）。Zapier/Makeは基本クラウードSaaSのみ

### 向いているシステム・ユースケース

- **軽量なETL/データ同期**：フォーム回答をスプレッドシートに転記、CRM更新をSlack通知、等の「A→B」連携
- **通知・アラート系ワークフロー**：エラー検知、在庫アラート、日次レポート配信
- **社内業務の半自動化（プロトタイピング）**：エンジニアリソースをかけずに1〜数週間で動くものを作りたい場合
- **LLM組み込みの軽量エージェント的処理**：Slack投稿→Claude API分析→結果を別サービスに書き戻す、のような「呼び出して繋ぐだけ」の処理（前回検討したオープンマインドAIパイプラインはこの典型例）
- **MVP検証・PoC**：本実装の前に「本当にこの自動化が価値を生むか」を低コストで検証したいフェーズ

### できないこと・向いていないこと

- **複雑な状態管理・長時間の対話型処理**：マルチターンの会話状態や複雑なセッション管理は苦手（都度ステートレスに近い設計が基本）
- **高頻度・大規模処理でのコストパフォーマンス**：実行回数課金（Zapier/Make）やインスタンスリソース制約（n8nクラウド）があり、秒間多数リクエストのような高スループット処理には不向き
- **厳密なレイテンシ要件のあるリアルタイム処理**：Webhook経由の非同期実行が基本のため、数十ms単位のレイテンシが求められる用途には弱い
- **複雑なビジネスロジック・アルゴリズム実装**：条件分岐が多段に絡み合う複雑な計算処理は、GUIのノードが乱立して可読性・保守性が崩壊しやすい（→コード実装に切り替えるべきサイン）
- **厳格なコンプライアンス・監査要件**：金融・医療等で求められる詳細な監査ログ、権限管理、暗号化要件はSaaS版では制約が出やすい（セルフホストn8n＋自前インフラなら緩和可能）
- **バージョン管理・CI/CDとの統合**：GUIベースのワークフローはGitでの差分管理・レビューと相性が悪い（n8nはJSONエクスポートで多少緩和できるが、コードほど自然ではない）
- **依存先SaaSの仕様変更への耐性**：非公式コネクタや個別カスタムノードは、連携先のAPI変更で突然壊れることがある

### 判断の目安（ざっくり）

| 状況 | 向き不向き |
|---|---|
| 「このサービスとこのサービスを繋ぎたいだけ」 | n8n等が最適 |
| プロトタイプで素早く動くものを見せたい | n8n等が最適 |
| 複雑な条件分岐・独自アルゴリズムが必要 | コード実装（TypeScript/Python等）が適切 |
| 高頻度・低レイテンシが必須 | コード実装＋専用インフラが適切 |
| 厳格な監査・コンプライアンスが必要 | セルフホストn8n＋自前統制、または完全カスタム実装 |

### 次のアクション候補

- n8nをセルフホスト or クラウドのどちらで試すか決める
- 前回設計したSlack→Claude API→知識ベース保存パイプラインをn8nの最小構成（Webhook→HTTP Request→Slack返信）でまず作ってみる
- 複雑化しそうな箇所（persona rotation state管理など）はn8n内で完結させず、外部Function nodeかコード実装に切り出す判断基準を持っておく
