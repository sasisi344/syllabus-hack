# IPA 試験の現在地チェッカー（設計メモ）

- 状態: 提案（inbox I-33）。起票と実装の時期はユーザーが決める。勉強時間の出し方は 2026-11-26 にユーザーが決めた（§4）
- 発案: ユーザー（2026-11-26）。メモ: CC（hq セッション）

## 1. 何を解決するか

勉強時間の見込みは、受ける人の出発点で大きく違う。ITパスポートが入口になることは多いが、必ずではない。プログラミングやセキュリティの知識がある人なら、IP・SG・FE は過去問を解く程度で届くこともある。一方、応用情報や新試験のプロフェッショナルデジタルスキル試験（PD）などの高度な区分では、話が変わる（ユーザーの例）。

そこで、**受ける予定の試験を選ぶ → その試験の問題を中心に、出題範囲が重なるほかの試験の問題も混ぜて出す → 中分類ごとの正答から「合格までの勉強時間の見積もり」と「重点的に学ぶ項目」を出す**チェッカーを作る。

## 2. 流れ

1. 「どの試験を受ける予定ですか」: IP／SG／FE／AP（2026年度まで）／PD-M・PD-S・PD-D／DM／SC から選ぶ
2. 出題: 選んだ試験の問題が中心（目安7割）。残りは、**同じ中分類を出題範囲に持つほかの試験**の問題（下の試験のやさしい問題と、上の試験の深い問題）
3. 結果:
   - 中分類ごとの正答率（◎重点分野を強調）
   - 重点的に学ぶ中分類（正答率が低く、選んだ試験で ◎ のもの）と、その章・記事・演習へのリンク
   - 勉強時間の見積もり（幅で出す。§4）
   - 「この試験より先に、下の試験から始めたほうがよい」／「上の試験も視野に入る」の案内

## 4. 勉強時間の見積もり（2026-11-26 ユーザー決定）

**リサーチで試験ごとの平均の勉強時間を出し、最小値と最大値の幅で見積もる。**

| | 想定 | 中身 |
|---|---|---|
| 最小値 | 事前知識が n% ある | n はリサーチのあとに決める（案: 60%。IPA の多くの区分の合格基準が 60%＝600点/1,000点前後のため） |
| 最大値 | 事前知識がほぼない | まったく初めての人 |
| 見積もり | チェッカーの正答率で、最小値と最大値の間に置く | 中分類ごとの正答率で、重点分野（◎）を重く数える |

### 試験の層で、見積もりの土台を変える

| 層 | 試験 | 見積もりの考え方 |
|---|---|---|
| 入口 | IP・SG・FE・DM | 試験ごとの平均（リサーチ）をそのまま最小値〜最大値に使う。IP は IPA の合格者アンケートの分布（§3）が基準 |
| 応用 | AP（2026年度まで） | IP・FE にかかる時間に**相対して**考える（例: FE の時間 ＋ AP で増える範囲の分）。単独の平均だけで出さない |
| 高度 | PD-M・PD-S・PD-D・SC | **基礎は応用情報に当たる**ので、「AP の過去問で 60% 取れる知識がある」を前提にし、その上に足す時間として出す。チェッカーの AP 相当の問題で 60% に届かない人には、AP 相当の不足分の時間を先に足し、「先に応用情報の範囲から」と案内する |

- 高度の層の前提（AP の過去問 60%）は、新制度の PD・SC の科目A-1（共通知識。`exam-scope-matrix-2027.json` の `pd_a1`）が AP の科目A に近いことから。チェッカーでは `pd_a1` の中分類の問題を AP 相当として使う
- リサーチで集めるもの: 試験ごとの勉強時間の平均（公式の調査があれば最優先。IPA は IP のアンケートだけ。ほかは主催者・公的機関の調査、なければ複数の合格者調査を比べて幅で）。出典と確認日を全部残す。見つからない試験は、IP・FE との相対（上の表）で出し、そう書く
- 結果画面に、見積もりの方法（平均の出典、最小・最大の想定、高度の前提）を書く。「シラバスハックの目安で、合格を保証しない」と明記する。IPA の数字のように見せない

## 5. 段階

1. IP・SG・FE で作る（問題の中分類の付与がほぼ済み。範囲の重なりも大きい）
2. AP（2026年度で終了予定。後期の科目A は 2027年2月）と PD-D を足す
3. SC・PD-M・PD-S・DM の問題に中分類を付けてから足す

## 6. 注意

- 新制度の出題範囲は「案」（改定案 Ver.1.0、シラバス案 Ver.0.1）。IPA の更新で変わる。マトリクスの更新は `syllabus-diff-hack` の仕組みと T-54 の流れで追う
- 新しい問題を作るのではなく、既存の問題を使う。既存の問題の重複・ID の衝突（inbox I-20: FE 演習の ID 重複）を先に直す
- コンポーネント・アプリの追加なので、公開には deploy の承認が要る
